Trade-Offs in Data Systems Architecture

What makes an app data-intensive

Book: Chapter 1, introduction and “Terminology: Frontends and Backends”

An app is data-intensive when its hardest problems are about data: how much there is, how it changes, keeping it consistent through crashes and concurrent writes, and keeping it available. A compute-intensive app is limited by heavy calculation instead.

The standard building blocks

Building blockWhat it's for
DatabaseStore data so you or another app can find it later
CacheKeep the result of an expensive operation to make reads faster
Search indexLook data up by keyword or filter it in many ways
Stream processingReact to events and changes as they happen
Batch processingCrunch a big pile of accumulated data on a schedule

Frontend and backend

  • Frontend: code running on the user's device, such as a browser or mobile app. It deals with one user's data.
  • Backend: server-side code that handles requests, usually over HTTP. It deals with everyone's data, which is where the hard infrastructure problems are.
  • Backend application code is usually stateless. It forgets each request when it finishes, so anything that must persist goes on the client or into the data infrastructure: databases, caches and message queues.
Trade-off 1

Operational vs analytical systems

Book: “Operational Versus Analytical Systems”

The same data serves two very different groups of people. Backend services create and change data. Analysts and data scientists read huge amounts of it and almost never change it. These needs are different enough that they usually get separate systems.

Operational · OLTP

Online transaction processing

  • Built by backend engineers and used by end users
  • Point queries: look up a few records by key
  • Inserts, updates and deletes driven by user actions
  • A fixed set of queries written into the app
Analytical · OLAP

Online analytical processing

  • Used by business analysts (BI) and data scientists (ML/AI)
  • Scans many records and computes aggregates like count, sum and average
  • Holds a read-only copy of the operational data
  • Free-form, exploratory SQL, often written by dashboard tools

Side by side

Operational (OLTP)Analytical (OLAP)
ReadsA few records, fetched by keyAggregates over a huge number of records
WritesCreate, update or delete single recordsBulk loads (ETL) or an event stream
Human userSomeone using the web or mobile appAn internal analyst supporting decisions
Machine usee.g. checking if an action is allowede.g. spotting fraud or abuse patterns
QueriesFixed and predefined by the appAd hoc and exploratory
VolumeMany small queriesFew queries, each one heavy
Data showsThe current stateThe history of events over time
SizeGigabytes to terabytesTerabytes to petabytes
  • Why OLTP users can't run their own SQL: it could expose data they aren't allowed to see, and a costly query slows the database for everyone else.
  • Product analytics, also called real-time analytics (Pinot, Druid, ClickHouse), runs analytical queries inside user-facing products. It ingests data in real time and aims for low latency. Classic OLAP loads data in batches and aims for high throughput.
  • The “online” in OLAP probably just means analysts use it interactively.

Data warehouses and ETL

From the late 1980s, companies stopped running analytics on their OLTP databases and copied the data into a separate data warehouse.

Why not query the OLTP systems directly? Remember the 4 S's
  1. Silos: the data is spread across many systems
  2. Schema: OLTP data layouts don't suit analytics
  3. Speed: heavy queries slow things down for real users
  4. Security: OLTP may sit on a network analysts can't reach
  • ETL means extract from OLTP (periodic dumps or a continuous stream), transform into an analysis-friendly schema and clean it, then load into the warehouse. ELT loads first and transforms inside the warehouse.
  • SaaS sources such as a CRM or payment processor are only reachable through their APIs. Connector services like Fivetran, Singer and Airbyte do the ETL for them.
  • HTAP (hybrid transactional/analytical processing) puts both workloads in one system. Inside, it is often still an OLTP engine plus an analytics engine. It doesn't replace the warehouse: a company may have hundreds of service databases but usually one warehouse. HTAP fits a single app that needs both kinds of query, such as fraud detection.
  • The bigger trend: the larger the scale, the more systems specialize. One size doesn't fit all.

From warehouse to data lake and beyond

Data warehouse

Relational and SQL

  • Built for business analysts and BI tools
  • Data is transformed into a fixed relational schema
  • Awkward for ML feature engineering and for text or image processing
Data lake

Just files, any format

  • Built for data scientists using Pandas, scikit-learn, R or Spark
  • Holds raw files with no imposed schema: Avro, Parquet, text, images, sensor data, vectors and so on
  • Cheaper, because it runs on commodity object storage
  • ETL generalized into data pipelines. A lake is often a stop on the way to the warehouse, keeping the raw data so each consumer can transform it in their own way. This is the sushi principle: raw data is better.
  • What came after the data lake: DataOps and governance (driven by GDPR and CCPA), event streams that react in seconds instead of daily, and reverse ETL, which sends analytics outputs such as trained ML models back into operational systems (tools: TFX, Kubeflow, MLflow).

Systems of record vs derived data

System of record

The source of truth

  • New data is written here first
  • Each fact is stored exactly once, usually normalized
  • If another system disagrees, this one is right by definition
Derived data

Redundant, but fast

  • Produced by transforming data from another system
  • If you lose it, you can rebuild it from the source
  • Duplicates data on purpose to make reads fast, and lets you view the same data in several ways
  • Whether a database is a system of record or derived data depends on how you use it, not on which product it is.
  • Analytical systems are usually derived data. Operational services often contain both kinds.
  • Derived data must be updated when the source changes. Most databases don't help with this, which is why data integration and pipelines (Chapter 11) exist.
Trade-off 2

Cloud vs self-hosting

Book: “Cloud Versus Self-Hosting”

This is build-vs-buy. A common rule of thumb: keep your core competency in-house and outsource what is routine. For software there are two separate questions: who builds it and who runs it.

Self-hosting tends to win when

You know it, and load is steady

  • Your team already knows how to run the system
  • Load is predictable, so owning machines is often cheaper
  • You need to tune it for your specific workload
  • You need full control of the hardware, e.g. high-frequency trading
  • The system is old, or has needs no cloud service meets
Cloud tends to win when

It's new to you, or load is spiky

  • You don't know how to operate it, and hiring for it is expensive
  • Load varies a lot, so you scale up and down and return idle resources
  • Analytics on big datasets, where queries need a burst of parallel compute
  • The provider's experience across many customers can mean better service
The cloud's big downside is lack of control. Six risks to remember
  1. Features: you can only ask the vendor
  2. Outages: you can only wait
  3. Debugging: no access to logs or internals
  4. Lock-in: price hikes, shutdowns, forced migrations, no standard APIs
  5. Geopolitics: sanctions can lock you out
  6. Trust: the vendor holds your data, which complicates compliance

Cloud native architecture

  • Cloud native means designed from the ground up to use cloud services. Compared with self-hostable software moved to the cloud, it gets better performance on the same hardware, faster recovery, faster scaling and support for bigger datasets.
  • Examples. OLTP: self-hosted MySQL, PostgreSQL, MongoDB; cloud native AWS Aurora, Azure SQL DB Hyperscale, Google Cloud Spanner. OLAP: self-hosted Teradata, ClickHouse, Spark; cloud native Snowflake, BigQuery, Azure Synapse.
  • Layering: self-hosted software uses generic CPU, RAM, filesystem and network. Cloud native services are built on other cloud services. Object storage (S3, Azure Blob, Cloudflare R2) stores large files across many machines, Snowflake is built on S3, and other products are built on Snowflake.
  • A higher-level service is less work if it fits your use case. If none fits, build from lower-level parts.

Separation of storage and compute

  • A VM's local disk is treated as an ephemeral cache, because it disappears if the instance fails or is replaced.
  • Virtual block devices (Amazon EBS, Azure managed disks, Google persistent disks) emulate a disk in roughly 4 KiB blocks over the network. They add overhead, and every I/O is a network call, so network glitches hurt.
  • So cloud databases keep small values in a separate service and write large blocks to object storage, which is meant for files from hundreds of KB to several GB.
  • Multitenancy: many customers share the same hardware and service. Utilization and scaling get better, but one tenant must not hurt another's performance or security.

Operations in the cloud era

  • Roles moved from DBAs and sysadmins to DevOps, and SRE is Google's version. The goal is the same as before: a reliable service.
  • Cloud storage replaces fixed disks with metered billing, so capacity planning becomes financial planning and performance optimization becomes cost optimization. You still need to watch quotas.
  • Cloud customers focus on choosing services, integrating them and migrating between them. Integration has no standards yet, so it takes manual effort.
  • You can't outsource security, how your services interact, load monitoring or root-causing outages. Operations is still needed.
What DevOps and SRE emphasize: “Every Engineer Fixes Lost Knowledge”
  1. E: automation over manual one-off jobs
  2. E: ephemeral VMs instead of long-running servers
  3. F: frequent app updates
  4. L: learning from incidents
  5. K: keeping knowledge as people come and go
Trade-off 3

Distributed vs single-node

Book: “Distributed Versus Single-Node Systems”

A distributed system is several machines talking over a network, and each participating process is a node. Sometimes you have no choice. When you do, the advice is to stay on one machine for as long as you can.

Nine reasons to distribute I Rarely Find Systems Less Expensive, So Let's Simplify
  1. Inherent distribution: users on separate devices
  2. Requests between cloud services
  3. Fault tolerance and high availability
  4. Scalability
  5. Latency: servers near users
  6. Elasticity: scale with demand
  7. Specialized hardware (GPUs, many disks)
  8. Legal compliance: data residency laws
  9. Sustainability: run where and when green power is available
Costs of distribution

The network makes everything harder

  • Any request can time out, and then you don't know if it was received. Retrying may not be safe.
  • A network call is vastly slower than a local function call, so it can be better to move the computation to the data.
  • Troubleshooting is hard, so you need observability and tracing (OpenTelemetry, Zipkin, Jaeger).
  • When each service has its own database, consistency across services becomes the application's problem. Distributed transactions are rarely used with microservices.
Case for one machine

Often simpler and cheaper

  • More nodes isn't always faster. A single-threaded program can beat a cluster with over 100 cores.
  • CPUs, RAM and disks keep getting bigger, faster and more reliable.
  • Single-node databases such as DuckDB, SQLite and KùzuDB handle a lot of workloads.

Microservices and serverless

  • Client/server over HTTP. A process can be both a server and a client. SOA was refined into microservices: one well-defined purpose, one API and one owning team per service.
  • Pros: each service deploys independently with less coordination, gets its own resources, and can change its implementation behind a stable API. Each service has its own database. Sharing one would make the schema part of the API and let one service's queries slow another.
  • Cons: hard to test because you must run the dependencies too, every service needs deploy, logging, monitoring and alerting infrastructure (so Kubernetes), and APIs are hard to evolve (OpenAPI and gRPC help).
  • Key line: microservices are a technical solution to a people problem. They're worth it for big companies and are overhead for small ones.
  • Serverless / FaaS: the provider allocates and frees resources per request, so you get metered billing for running code. The catches are time limits, restricted runtimes and cold starts. It still runs on servers. “Serverless” is also used as marketing for anything that autoscales and bills by use (BigQuery, Kafka offerings).

Trade-off 4

Business needs vs users' rights

Book: “Data Systems, Law, and Society”

Architecture isn't only a technical decision. Engineers have a responsibility to society and to the people whose data they store. Everyone needs basic legal and ethical awareness, just as they need basic knowledge of distributed systems.

  • Laws: the GDPR (EU, since 2018), the CCPA (California) and the EU AI Act. Automated decisions about loans, insurance, job interviews and crime suspicion affect real lives.
  • The right to be forgotten (erasure) conflicts with append-only logs and with derived data such as ML training sets. How do you delete from an immutable file?
  • The GDPR deliberately doesn't say which technologies count as compliant. It sets high-level principles that have to be interpreted.
  • The true cost of storing data includes breach liability, reputational damage, fines and legal costs, not just the storage bill.
  • Governments can force companies to hand over data. Location data or IP logs could expose criminalized behavior and put users in real danger.
  • Data minimization (Datensparsamkeit): don't store what isn't worth the risk. It's the opposite of “store everything, it might be useful”. The GDPR requires a specific purpose, no reuse for other purposes, and keeping data no longer than needed.
  • Industry rules: PCI standards for card payment processors and SOC 2 Type 2 for software vendors, both checked by independent auditors.
