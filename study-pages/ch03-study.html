Data Models and Query Languages

The data model shapes the code you write and how you think about the problem. This chapter compares the relational, document, graph, event-sourcing and DataFrame models, and the languages used to query them. Some data is easy to express in one model and awkward in another.

Declarative vs imperative

Book: Chapter 3 introduction and “Terminology: Declarative Query Languages”
Declarative · SQL, Cypher, SPARQL, Datalog

Say what you want

  • Describe the result: its conditions, sorting, grouping and aggregation
  • The query optimizer picks the indexes, join algorithms and order of work
  • The database can get faster, or run the query in parallel, without you changing the query
Imperative · Python, Java

Say how to do it

  • You write the algorithm step by step
  • Longer, and tied to one execution strategy
  • Running it in parallel is your job, and it's a lot of work
Model 1 and 2

Relational vs document

Book: “Relational Versus Document Models” and “The Object-Relational Mismatch”

A short history

WhenWhat happened
1970Edgar Codd proposes the relational model: relations (tables) are unordered collections of tuples (rows). Many doubted it could be made efficient.
1970s–80sThe network and hierarchical models compete and lose.
Mid-1980sRDBMSs and SQL become the default for structured data.
Late 80s–90sObject databases come and go. They're unrelated to today's object storage.
Early 2000sXML databases see only niche adoption.
2010sNoSQL: new models, flexible schemas, scalability, open source. NewSQL: NoSQL-style scale with relational guarantees. Both terms faded as the ideas spread.
TodayThe document model (JSON) stays popular. SQL absorbed XML, JSON and graph support, and the models are converging.

The object-relational mismatch

  • Impedance mismatch: an awkward translation layer between objects in code and tables, rows and columns. The term comes from electronics, where mismatched circuits reflect signals.
  • ORMs (ActiveRecord, Hibernate) cut the boilerplate but get criticized.
ORM problems

Leaky and easy to misuse

  • They can't fully hide both models, so you still think about both
  • OLTP-only. Analysts still query the raw schema, so the schema still matters
  • Mostly relational-only, with no help for search, graph or NoSQL systems
  • Generated schemas can be awkward or inefficient
  • Easy to write slow queries, like N+1
ORM benefits

Handy for the routine cases

  • Less boilerplate for translation you'd have to do anyway
  • Some cache query results
  • Help with schema migrations and admin tasks
The N+1 query problem: what an ORM may do 
-- 1 query for the comments
SELECT * FROM comments WHERE post_id = 7;
-- then 1 query per comment (N of them)
SELECT name FROM users WHERE id = 12;
SELECT name FROM users WHERE id = 31;
SELECT name FROM users WHERE id = 12;
-- … N + 1 round trips in total
What you'd write by hand: one join 
SELECT c.*, u.name
FROM comments c
JOIN users u ON u.id = c.author_id
WHERE c.post_id = 7;
-- 1 round trip
-- (or tell the ORM to fetch authors eagerly)

One-to-many data is a tree, and a document fits it

Relational: shredded into tables 
users     (user_id, first_name, last_name, …)
positions (id, user_id → users, job_title, org)
education (id, user_id → users, school, start, end)
contacts  (id, user_id → users, type, url)

-- read a profile: several queries,
-- or one messy multi-way join
Document: one JSON tree 
{ "user_id": 42,
  "first_name": "Maya",
  "positions": [
    {"job_title": "Engineer", "org": "Acme"},
    {"job_title": "Intern",   "org": "Globex"} ],
  "education": [
    {"school": "MIT", "start": 2014, "end": 2018} ],
  "contact": {"site": "https://maya.dev"} }
  • A JSON document has better locality: everything is in one place, so one fetch is faster and simpler.
  • One-to-many is often one-to-few, like the handful of jobs on a résumé. If there are thousands of related items, such as comments on a celebrity's post, don't embed them. Use separate rows.
Core trade-off

Normalization vs denormalization

Book: “Normalization, Denormalization, and Joins” and “Many-to-One and Many-to-Many Relationships”

Store region_id: "us:91" or the text "Washington, DC"? An ID means nothing to humans, so it never has to change. That's normalized. Copying the human-readable text into every record is denormalized.

Why use a standardized list with IDs? Santa CLAUS normalizes
  1. Consistent style and spelling
  2. Localization: show it in the viewer's language
  3. Ambiguity avoided: which Washington?
  4. Updates in one place, e.g. a city is renamed
  5. Search that is smarter, e.g. knowing Washington is on the East Coast
Normalized · one copy plus IDs

Fast writes, slower reads

  • Writes are fast because there's only one copy to update
  • Reads need joins to turn IDs into readable data
  • No risk of copies drifting out of sync
  • Usually best for OLTP and for small-to-medium scale
Denormalized · copies everywhere

Fast reads, costly writes

  • Reads are fast with fewer joins
  • Writes must update every copy, use more disk, and risk inconsistency if a crash happens mid-update
  • Think of it as derived data: you need a process that keeps the copies updated
  • Often better for analytics: bulk loads, read-heavy, data rarely changes
  • Joins in document databases: some have none, so you join in application code with a second query. MongoDB has $lookup in its aggregation pipeline.
  • X/Twitter timelines store only the post ID and sender ID, not the content. On read they hydrate the IDs, which is a join in application code, because like counts, usernames and avatars change constantly. Hydration parallelizes well, so read-time joins aren't a scaling blocker.
  • The lesson: denormalize some things and keep others normalized. Look at how often the data changes and the read and write costs, including outliers.

Three kinds of relationship

KindExampleNatural fit
One-to-manyOne résumé has several positions, each belonging to one résuméA document tree (embed it)
Many-to-oneMany people live in one regionA reference by ID, i.e. normalized
Many-to-manyPeople ↔ organizations they've worked forA relational join table (associative table) with secondary indexes on both ID columns, so you can query in both directions. In documents, either reference both ways (denormalized, can drift) or index the IDs inside the array
Analytics schemas

Stars, snowflakes and one big table

Book: “Stars and Snowflakes: Schemas for Analytics”
  • Fact table: one row per event, such as a sale, page view or click. It can reach petabytes. Its columns are attributes like price and cost, plus foreign keys to dimensions.
  • Dimensions describe an event's who, what, where, when, how and why. Even dates get a dimension table so holidays can be encoded.
  • Snowflake schema: dimensions split into sub-dimensions, e.g. brand and category tables. It's more normalized, but analysts usually prefer the simpler star.
  • Tables are wide: a fact table can have 100+ columns.
  • Mostly many-to-one relationships. A multi-item basket is just several fact rows sharing a customer, store and timestamp.
  • One big table (OBT): fold the dimensions into the fact table, effectively pre-joining them. It takes more storage but can be faster. Denormalization is fine here because historical events don't change.
Decision

When to use which model

Book: “When to Use Which Model” and its subsections
Pick documents when

Data is a tree, loaded whole

  • One-to-many trees you usually load all at once
  • You want schema flexibility for varied or externally defined data
  • You want locality and a closer match to your objects
  • You have user-ordered lists: a JSON array keeps the order for free
Pick relational when

Data is interconnected

  • There are many many-to-one and many-to-many relationships, and you need joins
  • You need to refer to a nested item directly by its own ID
  • Records share one structure and the schema documents and enforces it
  • Avoid shredding a document-like tree into many tables
  • Reorderable lists in SQL need tricks: an integer column (renumber on insert), a linked list of IDs, or fractional indexing.

Schema-on-read vs schema-on-write

Schema-on-write · relational

Like static type checking

  • An explicit schema the database enforces on every write
  • Change the format with a migration: ALTER TABLE, then UPDATE
  • Adding a column with a default is fast. Rewriting every row is slow, and tools like gh-ost and pgroll help
Schema-on-read · documents

Like dynamic type checking

  • Not really “schemaless”: the reading code still assumes a structure (an implicit schema)
  • Write new fields as you go, and handle old formats in code when reading
  • Downside: every reader must cope with every historical format
Schema-on-read: fix it up when reading 
// old docs only have `name`
if (doc.name && !doc.given_name) {
  doc.given_name = doc.name.split(" ")[0];
}
Schema-on-write: migrate the table 
ALTER TABLE people ADD COLUMN given_name text;
-- slow on big tables: rewrites every row
UPDATE people SET given_name = split_part(name, ' ', 1);
  • Schema-on-read wins for heterogeneous data: many object types, or structure set by outside systems. When all records share a shape, an explicit schema is useful documentation and enforcement.
  • There's no clear winner, just like static vs dynamic typing.

Locality, query languages and convergence

  • Locality: a document is stored as one string (JSON, XML or BSON). That's great when you need most of it, wasteful when you need a small part, and every update rewrites the whole document. Keep documents small.
  • Locality isn't unique to documents: Spanner interleaves child rows inside parent tables, Oracle has multi-table index cluster tables, and Bigtable, HBase and Accumulo have column families.
  • Document query options: key-value by primary key only, secondary indexes, or rich languages: XQuery/XPath for XML, JSON Pointer/JSONPath, and the MongoDB aggregation pipeline (roughly a subset of SQL written as JSON).
  • Convergence: relational databases added JSON types, operators and indexes. MongoDB, Couchbase and RethinkDB added joins, secondary indexes and declarative queries. Hybrids are powerful.
  • Codd's 1970 paper already allowed nonsimple domains, i.e. nested relations inside a value, an idea close to JSON columns.
Model 3

Graph-like data models

Book: “Graph-Like Data Models” and “Property Graphs”

When anything can relate to anything and many-to-many links are everywhere, model the data as a graph of vertices (nodes, entities) and edges (relationships, arcs).

  • Examples: social graphs (people who know each other), the web graph (pages and links, ranked with PageRank), and road or rail networks (shortest-path navigation).
  • Graphs can hold different kinds of things in one database: Facebook stores people, places, events, check-ins and comments in a single graph. Search engines build knowledge graphs, and Wikidata publishes one.
  • Representations: an adjacency list (each vertex lists its neighbors), which suits traversal, or an adjacency matrix (a 0/1 grid), which suits ML.
Property graph vertex

5 parts

  • Unique ID
  • Label (type)
  • Outgoing edges
  • Incoming edges
  • Properties (key-value pairs)
Property graph edge

5 parts

  • Unique ID
  • Tail vertex (where it starts)
  • Head vertex (where it ends)
  • Label (kind of relationship)
  • Properties (key-value pairs)
  • It can be stored as two SQL tables, vertices and edges, with indexes on both tail and head so you can traverse forward and backward. The edges table is a join table generalized to many relationship types.
  • There's no schema limiting which vertices may connect. Labels keep different kinds of data tidy in one graph.
  • Graphs handle irregular data: different regional structures per country (French départements vs US counties), a country inside a country, and mixed granularity (born in a state, living in a city). They're great for evolvability.
  • Limitation: an edge joins exactly two vertices. For three-way relationships, add an extra vertex or use a hypergraph.
  • Property graph databases: Neo4j, Memgraph, KùzuDB. Triple stores: Datomic, AllegroGraph, Blazegraph. Amazon Neptune supports both.

Triple stores and RDF

    
    
      
  • Everything is a (subject, predicate, object) triple: (Jim, likes, bananas).
    • 
      
  • If the object is a value, the triple is a property: (lucy, birthYear, 1989). If the object is another vertex, it's an edge: (lucy, marriedTo, alain).
    • 
      
  • Real systems add metadata: Neptune uses quads (adds a graph ID). Datomic uses 5-tuples (adds a transaction ID and a deleted flag).
    • 
      
  • Turtle (a subset of Notation3) is a readable text format. ; lets you say several things about one subject. RDF/XML is the verbose form, and Apache Jena converts between them.
    • 
      
  • RDF uses URIs as namespaces, e.g. urn:example:within, so your within never clashes with someone else's. The URI doesn't have to resolve to anything.
    • 
      
  • The Semantic Web (early 2000s) failed as a vision, but it left JSON-LD, biomedical ontologies, Facebook's Open Graph (link previews), Wikidata and Schema.org.
    • 
    


    
Datalog in three ideas

    
    
      
  • Facts are rows: location(2, "France", "country"), within(5, 2).
    • 
      
  • Rules derive virtual tables, like SQL views: head :- body. A rule fires when every pattern in the body matches.
    • 
      
  • Rules can call other rules and themselves, like recursive functions. That's how graph traversal works.

      Model 4
      
Event sourcing and CQRS

      Book: “Event Sourcing and CQRS”
    

    
Write data in the form that's best for writing: an append-only log of immutable events. Then derive separate forms that are best for reading, called materialized views, projections or read models.

    
    
      
  • Event sourcing: the event log is the source of truth, and every state change is an event.
    • 
      
  • CQRS (command query responsibility segregation): keep separate read-optimized representations, derived from the write-optimized one. Both terms come from the DDD community.
    • 
      
  • A command (a user request) is validated first. Only if it's valid does it become an event. Views may not reject events.
    • 
      
  • Name events in the past tense (“SeatsBooked”). A later cancellation is a new event and the old fact stays true.
    • 
      
  • Compared with a star schema's fact table: both record past events, but event types vary in shape, and their order matters.
    •

      Model 5
      
      DataFrames, matrices and arrays
      
      Book: “DataFrames, Matrices, and Arrays” and “Summary”
    
      
    
        
      
      • Mostly used in analytics and science, rarely in OLTP. Found in R, Pandas, Spark, ArcticDB and Dask.
        •

        • 
      
      • You manipulate them with a series of commands, not one declarative query. That matches how data scientists “wrangle” a private copy of the data step by step.

      • A key use is turning relational data into a matrix for ML.
