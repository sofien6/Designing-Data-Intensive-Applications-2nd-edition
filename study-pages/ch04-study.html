Start here

A log, and why we need indexes

Book: “Storage and Indexing for OLTP”

The simplest database appends key,value lines to a file. Writes are as fast as they can be. Reads scan the whole file, which is O(n). An index fixes reads, and every index costs you on writes.

My own toy version of the idea (Python) 
def put(key, value):
    with open("data.log", "a") as f:
        f.write(f"{key},{value}\n")   # append only

def get(key):
    found = None
    for line in open("data.log"):       # scan everything
        k, v = line.rstrip("\n").split(",", 1)
        if k == key:
            found = v                   # keep the LAST match
    return found
What the file looks like after an update 
7,{"city":"Lisbon","sights":["Belém"]}
9,{"city":"Oslo","sights":["Opera"]}
9,{"city":"Oslo","sights":["Opera","Vigeland"]}
# key 9 appears twice: the old value is never
# overwritten, so get() must return the last one
  • A log here means any append-only sequence of records on disk. It can be binary and isn't meant for humans, unlike application logs.
  • Real logs must also handle concurrent writes, reclaim disk space, and survive half-written records after a crash.
  • An index is extra data derived from the primary data. Adding or dropping one never changes the data itself, only query speed.
  • The core trade-off: good indexes speed up reads, but each one uses disk space and slows writes, because every write must update it too. That's why databases make you choose indexes based on your query patterns.

First attempt: an in-memory hash map

Keep the append-only file and add a hash map in memory from each key to the byte offset of its latest value. A read becomes one seek, or no disk I/O at all if that part of the file is in the filesystem cache.

Four problems with the hash map index: “Don't Rely on Memory, Really”
  1. Disk fills up: overwritten entries are never freed
  2. Restarts are slow: the map isn't persisted, so you rescan the log to rebuild it
  3. Memory bound: every key must fit in RAM, and on-disk hash maps perform badly (random I/O, costly growth, fiddly collisions)
  4. Range queries are slow: keys 10000–19999 means 10,000 separate lookups
Family 1 · log-structured

SSTables and LSM-trees

Book: “The SSTable file format” and “Constructing and merging SSTables”

Keep the data sorted by key. An SSTable (Sorted String Table) holds each key once, in order, so you need only a sparse index and can scan short ranges.

  • Group the key-value pairs into blocks of a few KB. Index only the first key of each block. That's a sparse index. It's stored inside the SSTable, e.g. as an immutable B-tree or a trie.
  • Looking up a key that isn't in the sparse index? Because of the sort order, it must sit between two indexed keys. Seek to the earlier one and scan a few KB.
  • Blocks can be compressed: less disk space and I/O bandwidth, a little more CPU.
  • In practice, databases rarely use hash tables for indexes. Sorted structures are far more common.
The LSM write and read cycle: “Mom Folds Socks Carefully”
  1. Memtable: each write goes into a sorted in-memory structure (red–black tree, skip list or trie)
  2. Flush: past a few MB, write it out as a new SSTable segment, then start a fresh memtable
  3. Search: read the memtable first, then segments from newest to oldest
  4. Compact: merge segments in the background, dropping overwritten and deleted values
  • Merging works like mergesort: read the input files side by side, always copy out the lowest key, and keep only the newest value when a key repeats. It uses little memory because it walks one key at a time.
  • Crash safety: every write is also appended to a separate, unsorted log (a WAL). It exists only to rebuild the memtable after a crash, and is discarded once that memtable is flushed. Checksums catch half-written records.
  • Deletes append a tombstone. During merges it hides older values for that key. Once it reaches the oldest segment, it can be dropped.
  • Segments are written once and then immutable. Merges run in a background thread while reads keep using the old segments. Then reads switch over and the old files are deleted. A crash mid-write just means deleting the unfinished file.
  • Immutable files suit object storage too (SlateDB, Delta Lake).
  • History: Google's Bigtable paper named SSTable and memtable. The algorithm itself is the LSM-tree (Log-Structured Merge-tree, 1996), building on log-structured filesystems. Used by RocksDB, Cassandra, ScyllaDB, HBase.

Speeding up LSM reads

Bloom filters

Book: “Bloom filters”

A Bloom filter answers “is this key in this SSTable?” with either “definitely not” or “probably yes”. That lets reads skip most segments for old or missing keys.

  • Each key is hashed to a few bit positions in a bit array, and those bits are set to 1. The bitmap is stored in the SSTable next to the sparse index. It's small.
  • To check a key, hash it the same way. Any 0 bit → definitely absent, skip the segment. All 1s → probably present, so check the sparse index and block.
  • All 1s for a key that isn't there is a false positive. It only costs a little wasted work, so it's harmless in LSM storage.
  • Bit checks are cheap bitwise CPU operations.
Bits per keyFalse-positive rate
10≈ 1%
15≈ 0.1%
20≈ 0.01%

Rule of thumb from the chapter: 10 bits per key gives about 1%, and every extra 5 bits per key cuts the rate tenfold.

Tuning LSM storage

Compaction strategies

Book: “Compaction strategies” and the “Embedded Storage Engines” sidebar
Size-tiered · e.g. HBase, Cassandra option

Small files merge into bigger ones

  • Newer, smaller SSTables are merged into older, larger ones
  • Four 256 MB files might become one ~900 MB file, smaller than 1 GB because of overwrites, deletes and TTL expiry
  • Big old files need lots of temporary disk space to merge
  • Best for write-heavy workloads: data is rewritten only a few times, in big sequential merges
Leveled · e.g. RocksDB

Fixed-size files in growing levels

  • Levels L0, L1, L2…; L0 holds the newest data
  • Beyond L0, each level's SSTables are split by key range (e.g. a–m, n–z)
  • Each level is bigger than the one before. When a level is over its limit, files move down from level i into i+1
  • More incremental, less disk space, fewer files to check per read. Best for read-heavy workloads, or when a few keys are written very often and many keys rarely

Memory hook: size-tiered for writes, leveled for reads.

Embedded storage engines

  • Embedded databases are libraries running inside your application's process, with no network API. You call functions and they read and write local files. Examples: RocksDB, SQLite, LMDB, DuckDB, KùzuDB.
  • Very common in mobile apps. On servers they fit data that suits one machine with modest concurrency, e.g. one embedded database per tenant when tenants never need cross-tenant queries.
  • Everything in this chapter applies to both embedded and client/server databases.
Family 2 · update-in-place

B-trees

Book: “B-Trees”, “Making B-trees reliable”, “Using B-tree variants”

The most widely used index. Introduced in 1970 and called “ubiquitous” by 1979, it's the standard in almost every relational database. Like SSTables it keeps keys sorted. Unlike them, it splits the data into fixed-size pages and overwrites pages in place.

Log-structured

Variable-size segments

  • Several MB or more each
  • Written once, then immutable
  • Only appends files and deletes old ones
B-tree

Fixed-size pages

  • Traditionally 4 KiB; PostgreSQL uses 8 KiB, MySQL 16 KiB
  • Each page has a number, so pages refer to each other like on-disk pointers. Offset = page number × page size
  • Pages are overwritten in place, and their location never changes
  • Lookups start at the root page. Each child covers a continuous key range, and the keys between references mark the boundaries. You descend to a leaf page, which holds the values inline or references to them. (Sometimes called a B+ tree.)
  • Branching factor = references per page, typically several hundred.
  • Update a key: find its leaf and overwrite that page. Insert: find the page whose range covers the key and add it. If the page is full, split it into two half-full pages and add the new boundary to the parent.
  • Splits can cascade up to the root. When the root splits, a new root grows above it, so the tree stays balanced: depth is O(log n). Deletes, which may merge pages, are more complex.
  • Most databases fit in 3 or 4 levels. The chapter's figure: 4 levels of 4 KiB pages with branching factor 500 stores up to about 250 TB.

Roughly branching factorlevels pages × page size. Each lookup reads one page per level, so the depth is the number of page reads.

Making B-trees crash-safe

  • A split overwrites several pages. A crash halfway can leave an orphan page (no parent points to it). Hardware that can't write a whole page atomically can leave a torn page.
  • Fix: a write-ahead log (WAL), an append-only file that receives every modification before it's applied to the tree. After a crash, replay it to restore a consistent tree. Filesystems call this journaling.
  • For speed, modified pages are buffered in memory and written later. Data is durable once it's in the WAL and flushed with fsync.

B-tree variants

Four variants: “Copy Short Leaves Sideways”
  1. Copy-on-write (LMDB): write the changed page elsewhere and new parent versions above it. No WAL needed, and it helps concurrency (snapshot isolation, Chapter 8)
  2. Shortened keys: interior pages store just enough of each key to act as a boundary, giving a higher branching factor and fewer levels
  3. Leaves laid out in order on disk for faster range scans. Hard to keep as the tree grows
  4. Sibling pointers: each leaf links to its left and right neighbors, so scans don't climb back to parents
Core trade-off

LSM-trees vs B-trees

Book: “Comparing B-Trees and LSM-Trees” and the SSD sidebar

Rule of thumb: LSM-trees suit write-heavy workloads and B-trees are faster for reads. Benchmarks are workload-sensitive, so test with your own. Some engines blend the two, e.g. several B-trees merged LSM-style.

Write amplification

  • Definition: total bytes written to disk ÷ bytes you'd write with a plain append-only log and no index. (Sometimes counted in I/O operations instead.)
  • When disk bandwidth is the bottleneck, higher amplification means fewer writes per second. It also wears out SSDs faster.
  • Benchmark for long enough: an empty LSM-tree has no compactions yet, so its early write speed is flattering.

Sequential vs random writes, on HDDs and SSDs

Spinning disk (HDD)

Seeks are the cost

  • A random write moves the head and waits for the platter: several milliseconds
  • So sequential writes win by a large margin
SSD, including NVMe

Erase blocks and garbage collection

  • Flash is read and written per page (~4 KiB) but erased per block (~512 KiB)
  • Before erasing a block, the controller moves its still-valid pages elsewhere: garbage collection
  • Sequential writes tend to fill whole blocks with one file, so deleting it frees the block with no GC
  • Random writes mix valid and stale pages, causing more GC, less bandwidth for you and more wear
  • NVMe on the PCIe bus can run many reads in parallel; engines must be designed to use that
Beyond primary keys

Secondary indexes and where values live

Book: “Multicolumn and Secondary Indexes” and “Storing Values Within the Index”
  • Primary key: uniquely identifies a row, document or vertex. Other records refer to it by this ID.
  • Secondary index (CREATE INDEX): search by other columns, e.g. user_id. Its keys aren't unique, so either store a list of matching row IDs per key (like a postings list) or make each key unique by appending the row ID. Both B-trees and LSM storage can implement one.
Clustered index

The row lives in the index

  • MySQL InnoDB: the primary key is always clustered
  • SQL Server: one clustered index per table
Covering index

Some columns copied in

  • Also called an index with included columns
  • Some queries are answered from the index alone: the index covers the query
  • Costs more disk space and slower writes
Reference

Points somewhere else

  • To the primary key (InnoDB secondary indexes)
  • Or to a location in a heap file: rows in no particular order (Postgres)
  • Heap file updates: a value that's the same size or smaller can be overwritten in place. A larger one may move, so either update every index or leave a forwarding pointer at the old spot.
  • Querying several columns at once needs multidimensional indexes (see below).
No disk layout to worry about

Keeping everything in memory

Book: “Keeping Everything in Memory”

The structures above exist to cope with disks. Disks win on durability and cost per GB. As RAM gets cheaper and many datasets turn out to be small, in-memory databases become practical.

  • Cache only: Memcached. Losing data on restart is acceptable.
  • Durable in-memory: battery-backed RAM, or more commonly an append-only log of changes, periodic snapshots, or replication to other machines. The disk is only for durability; reads are served from memory. Files on disk are also easy to back up and inspect.
  • Relational in-memory: VoltDB, SingleStore, Oracle TimesTen. RAMCloud is log-structured in memory and on disk. Redis and Couchbase give weak durability by writing to disk asynchronously.
  • The surprise: they aren't faster because they skip disk reads. With enough RAM, the OS cache means a disk-based engine rarely reads the disk either. They're faster because they skip encoding in-memory structures into an on-disk format.
  • They can also offer data models that are hard on disk, like Redis's priority queues and sets.
Analytics

Data warehouses, old and cloud

Book: “Data Storage for Analytics” and “Cloud Data Warehouses”
  • Warehouses are usually relational with SQL. Analysts explore with drill-down and slicing and dicing.
  • Same SQL surface as OLTP databases, very different internals. Most vendors now specialize in one workload.
  • HTAP products (SQL Server, SAP HANA, SingleStore) do both, but increasingly as two engines behind one SQL interface.
  • On-premises vendors: Teradata, Vertica, SAP HANA. Cloud-native: BigQuery, Redshift, Snowflake. They use object storage and serverless compute, integrate with services like Dataflow and Kinesis, and decouple storage from compute so each scales on its own (elasticity).
  • Open source (Hive, Trino, Spark) has broken apart into separate pieces:
The four pieces of an unbundled warehouse: “Queries Scan Tables via Catalogs”
  1. Query engine: parse, optimize and run SQL in parallel. Trino, DataFusion, Presto (may run on Spark or Flink)
  2. Storage format: how rows become bytes in a file. Parquet, ORC, Lance, Nimble
  3. Table format: which immutable files make up a table, plus its schema. Enables inserts and deletes, time travel, GC, transactions. Iceberg, Delta
  4. Catalog: which tables exist in a database; create, rename, drop. Often a REST service. Polaris, Unity Catalog, Iceberg's catalog. Lets governance tools read the metadata
Analytics storage

Column-oriented storage

Book: “Column-Oriented Storage”, “Column compression”, “Sort order in column storage”, “Writing to column-oriented storage”

Fact tables can be 100+ columns wide, but an analytics query reads maybe 4 or 5 of them across millions of rows. Store each column together and the query reads only what it needs.

Try it: row store vs column store

Columns the query needs
Row-oriented · whole rows are loaded
Column-oriented · only needed columns load

My own six-row example. Real fact tables have hundreds of columns and billions of rows, so the gap is far bigger.

  • Row-oriented (most OLTP databases, and documents): one row's values sit together. Even with indexes, you still load and parse whole 100-column rows.
  • Columns must keep rows in the same order: the 23rd entry of every column belongs to row 23.
  • In practice tables are cut into blocks of thousands to millions of rows, each storing its columns separately. Blocks often cover a time range, so date-limited queries skip whole blocks.
  • It works for nested data too: Parquet uses Dremel-style shredding (striping).
  • Used almost everywhere in analytics: Snowflake, DuckDB, Pinot, Druid; formats Parquet, ORC, Lance, Nimble; in-memory Arrow, Pandas/NumPy; time series InfluxDB IOx, TimescaleDB.
  • Not the same as wide-column (column-family) databases like Bigtable, HBase and Accumulo. Those are row-oriented, despite the name.

Sort order and writes

    

      

        Sorting
        
Sort whole rows, store by column

        
    
          
  • Sorting each column on its own would break row alignment
    • 
          
  • The admin picks sort keys from common queries, e.g. date_key first, then product_sk
    • 
          
  • Acts as an index: a date-range query scans only that range
    • 
          
  • Long runs in the first sort key compress to a few KB. Later keys compress less well
    • 
        

      

      

        Writing
        
Batch it, LSM-style

        
    
          
  • Inserting one row mid-table would rewrite every compressed column from that point
    • 
          
  • Warehouses get bulk imports (ETL), which amortize the cost
    • 
          
  • Writes go to a row-oriented, sorted in-memory store, then merge into new immutable column files, which suit object storage
    • 
          
  • Queries combine disk and memory, so new data shows up at once (Snowflake, Vertica, Pinot, Druid)

      CPU efficiency
      
Query compilation vs vectorization

      Book: “Query Execution: Compilation and Vectorization”
    

    
    
      
  • A query becomes a query plan of stages called operators, possibly spread across machines. The planner chooses which operators, their order, and where they run.
    • 
      
  • Scanning millions of rows makes CPU time matter, not just disk reads. A naive operator acts like an interpreter, consulting the query structure for every row. Too slow.
    • 
    

    

      

        Query compilation
        
Generate code for this query

        
    
          
  • Generate code that loops over rows, tests conditions and copies matches to an output buffer
    • 
          
  • Compile to machine code, often with LLVM
    • 
          
  • Like JIT compilation in the JVM
    • 
        

      

      

        Vectorized processing
        
Interpret, but in batches

        
    
          
  • Still interpreted, but each operator handles many values of a column at once
    • 
          
  • A fixed set of built-in operators: e.g. equality on product_sk returns a bitmap, the same on store_sk returns another, then a bitwise AND combines them
    • 
        

      

    

    

      How both win on modern CPUs: “Stop The Pointless Copying”
      
    
        
  1. Sequential memory access: fewer cache misses
    2. 
        
  2. Tight inner loops: few instructions, no function calls, so the pipeline stays full and branches predict well
    3. 
        
  3. Parallelism: multiple threads and SIMD instructions
    4. 
        
  4. Compressed data processed directly, with no decoding into a separate copy

      Precomputing
      
Materialized views and data cubes

      Book: “Materialized Views and Data Cubes”
    

    

      

        Materialized view
        
A stored copy of query results

        
    
          
  • Must be updated when the underlying data changes. Some databases do it automatically; Materialize specializes in it
    • 
          
  • More work on writes, faster repeated reads
    • 
        

      

      

        Virtual view
        
Just a saved query

        
    
          
  • A shortcut: the engine expands it into the underlying query each time you read it
    • 
          
  • Nothing is stored
    • 
        

      

    

    
A data cube (OLAP cube) is a materialized grid of aggregates, like SUM, grouped by dimensions. Totals along any row or column come for free.

    
    

      

        Upside
        
Precomputed answers

        
  • “Total sales per store yesterday” is a lookup, not a scan of millions of rows

      

      

        Downside
        
Only the dimensions you chose

        
  • “Share of sales from items over $100” is impossible if price isn't a dimension. So keep raw data and use cubes only as a speed boost

      

    

  






  

    

      Advanced indexes
      
Multidimensional and full-text indexes

      Book: “Multidimensional and Full-Text Indexes” and “Full-Text Search”
    

    

      

        Concatenated index
        
Fields glued into one key, in order

        
    
          
  • Like a paper phone book sorted by (last name, first name)
    • 
          
  • Works for last name, or last + first. Useless for first name alone
    • 
          
  • On (lat, lon): gives a latitude band at any longitude, not a box
    • 
        

      

      

        Multidimensional index
        
Query several columns at once

        
    
          
  • Map-viewport search: lat and lon in range together
    • 
          
  • R-trees and Bkd-trees group nearby points in the same subtree (PostGIS: R-trees via PostgreSQL's GiST)
    • 
          
  • Or a space-filling curve into one number, then a normal B-tree
    • 
          
  • Or regular grids of triangles, squares or hexagons (Uber's H3)
    • 
        

      

    

    
    
      
  • Not just maps: (red, green, blue) to find products by color, or (date, temperature) to find warm days in a given year without scanning the whole year.
    • 
    


    
Full-text search

    
    
      
  • Search documents by keywords anywhere in the text. Real systems also handle languages without spaces, typos, grammatical forms and synonyms.
    • 
      
  • Think of it as a multidimensional query where every term is a dimension: 1 if the document contains it, 0 if not.
    • 
      
  • An inverted index maps term → postings list (IDs of documents containing it). With sequential IDs, a postings list can be a sparse bitmap, so “x AND y” is a bitwise AND, just like the warehouse bitmaps.
    • 
      
  • Lucene (behind Elasticsearch and Solr) keeps term → postings in SSTable-like files merged log-structured style. PostgreSQL's GIN indexes use postings lists for full text and JSON.
    • 
      
  • n-grams: index every substring of length n. Trigrams allow substring and even regex search, but the index is big.
    • 
      
  • Typos: Lucene finds words within an edit distance (1 = one letter added, removed or replaced) by storing terms as a trie-like automaton and turning it into a Levenshtein automaton.
    •

      Semantic search
      
Vector embeddings and vector indexes

      Book: “Vector Embeddings”
    

    
Semantic search matches meaning, not words: “close my account” should find “canceling your subscription”. An embedding model turns each document into a vector of floats, and similar meanings land close together.

    
    
      
  • Used in AI apps, e.g. retrieval-augmented generation (RAG), which feeds search results into an LLM's output.
    • 
      
  • Real embeddings have 1,000+ dimensions. The individual numbers have no meaning to us; they just locate a point in space.
    • 
      
  • Distance: cosine similarity (the angle between vectors) or Euclidean distance (the straight line between points).
    • 
      
  • Models: Word2Vec, BERT, GPT (text), then images, audio and video, and now multimodal models.
    • 
      
  • At query time the query (plus context, like location) is embedded too, and a vector index finds the nearest documents.
    • 
      
  • Don't mix this up with vectorized processing: there a vector is a batch of column values for fast CPU code. Here it's a point in space.
    • 
    

    

      

        
My toy 3-D vectorsvs query “caring for a kitten” [0.80, 0.24, 0.28]

    2. 
        
  2. IVF (inverted file): split the town into neighborhoods around centroids; search only the nearest few (probes). More probes = more accurate but slower. Approximate

  3. HNSW (hierarchical navigable small world): highway, then main roads, then streets. Layers of proximity graphs, sparse at the top and dense at the bottom; greedily move closer at each layer. Approximate

  • R-trees don't work well with this many dimensions, hence these specialized indexes.
    • 
      
  • Implementations: Facebook's Faiss (variants of both), PostgreSQL's pgvector (IVF and HNSW).
