Encoding and Evolution

Code changes, and so does the shape of the data it stores. During a rolling upgrade, old and new code run side by side and read each other's data. This chapter compares the ways of turning objects into bytes and asks one question about each: what happens when the schema changes?

Backward vs forward compatibility

Book: Chapter 5 introduction

You can't upgrade everything at once. Servers get a rolling upgrade, a few nodes at a time, and users update client apps whenever they feel like it. So old and new code, and old and new data, coexist. Compatibility has to work in both directions.

Backward · new code reads old data

Look back at the past

  • Usually easy: the author of the new code knows the old format
  • Worst case, keep the old decoding code around
Forward · old code reads new data

Data arrives from the future

  • Trickier: old code must ignore additions it doesn't understand
  • It must also keep them intact when it writes the record back
Memory hook

The direction names where the data comes from

  1. Backward: data from the past (older writer)
  2. Forward: data from the future (newer writer)

      The landscape
      
Formats for encoding data

      Book: “Formats for Encoding Data”, “Language-Specific Formats” and “JSON, XML, and Binary Variants”
    

    
Encoding is also called serialization or marshaling. Decoding is also called parsing, deserialization or unmarshaling. The book says “encoding” because serializable means something else in transactions (Chapter 8).

    
    
      
  • Pointers mean nothing to another process, so encoded bytes look very different from in-memory structures.
    • 
      
  • Zero-copy formats (Cap'n Proto, FlatBuffers) use the same layout in memory and on disk or the wire, so there is no conversion step.
    • 
    


    
Language-specific formats: avoid them

    
Java Serializable, Python pickle, Ruby Marshal, Kryo. They're convenient, but only for very short-lived data.

    

      Four problems: Language-Specific Formats are LSVE (“Least Safe, Very Expensive”)
      
    
        
  1. Lock-in to one language
    2. 
        
  2. Security: decoding can instantiate arbitrary classes, leading to remote code execution
    3. 
        
  3. Versioning is an afterthought
    4. 
        
  4. Efficiency is an afterthought (Java's is notoriously slow and bloated)
    5. 
      

    


    
Textual formats: JSON, XML, CSV

    

      

        
PitfallWhat goes wrong

        
          
VerbosityXML is criticized as too verbose and complicated

          
NumbersXML and CSV can't tell a number from a string of digits. JSON can, but doesn't separate integers from floats and has no precision. Integers above 253 get rounded by JavaScript. Try it: 9007199254740993 parses as …. That's why X's API returns post IDs twice, as a number and as a string.

          
Binary dataNo byte strings, so people use Base64, which is hacky and makes data about a third bigger

          
SchemasXML Schema and JSON Schema are powerful but hard to learn. Without them, decoding logic gets hardcoded

          
CSVNo schema at all, and it's vague: what if a value contains a comma or a newline? RFC 4180 exists, but not every parser follows it

        
      

    

    
Still, they're good enough for data interchange between organizations. Getting organizations to agree on anything matters more than prettiness or efficiency.


    
JSON Schema

    
    
      
  • Used in OpenAPI, schema registries (Confluent, Apicurio) and databases (PostgreSQL pg_jsonschema, MongoDB $jsonSchema).
    • 
      
  • Primitive types (string, number, integer, object, array, boolean, null) plus validation constraints, e.g. a port between 1 and 65,535.
    • 
      
  • Open content model (additionalProperties: true, the default): unknown fields are allowed, so a schema mostly says what isn't permitted. Closed: only the listed fields.
    • 
      
  • Conditionals (if/else), named types and remote references make it powerful, but hard to evolve compatibly.
    • 
    

    

    
Binary JSON: small win, big readability loss

    
MessagePack, CBOR, BSON, Smile and friends (and WBXML or Fast Infoset for XML) keep the JSON data model. With no schema, every record still carries all its field names, so they save only a little space. See them side by side in the byte lab below.

  • MessagePack: the first byte says “map with 3 entries”. Each string is preceded by a byte combining type and length, so no terminator or escaping is needed.
    •

      Schema-driven format 1
      
Protocol Buffers and field tags

      Book: “Protocol Buffers” and “Field tags and schema evolution”
    

    
Developed at Google; Facebook's Thrift works much the same way. You write a schema in its IDL, a code generator makes classes, and the encoded data identifies each field by its tag number, never by its name.

    
    

      Golden rule
      
Names are labels; tags are identity

      
    
        
  1. Rename freely
    2. 
        
  2. Never change a tag
    3. 
        
  3. Never reuse a tag: reserve it
    4. 
      

    

    

      

        
ChangeBackward (new reads old)Forward (old reads new)Why

        
          
Rename a field✓✓Encoded data never contains names

          
Change a field's tag✗✗All existing data becomes invalid

          
Add a field (new tag)✓ missing → default (“” or 0)✓ unknown tag is skippedThe type annotation tells the parser how many bytes to skip, and it can preserve them

          
Remove a field✓✓Only if the tag is never used again (reserve it)

          
int32 → int64✓ pad with zeros⚠ truncationOld code holds the value in a 32-bit variable

        
      

    

    
    
      
  • The schema language is much simpler than JSON Schema: fields and types only, no value constraints.
    • 
      
  • Unset fields are simply omitted from the encoding.
    • 
    

  






  

    

      Schema-driven format 2
      
Avro: writer's schema meets reader's schema

      Book: “Avro”, “The writer's schema and the reader's schema”, “Schema evolution rules”, “But what is the writer's schema?”, “Dynamically generated schemas”
    

    
Started in 2009 as a Hadoop subproject. There are no tag numbers, and the bytes are just concatenated values. To decode, Avro uses two schemas: the writer's schema (exactly the one used to encode) and the reader's schema (what the application expects). It resolves the differences by field name.

    

      

        Avro IDL · for humans
        
record Profile {
  string               nickname;
  union { null, long } luckyNumber = null;
  array<string>        hobbies;
}

      

      

        JSON schema · for machines
        
{"type": "record", "name": "Profile",
 "fields": [
  {"name": "nickname", "type": "string"},
  {"name": "luckyNumber",
   "type": ["null", "long"], "default": null},
  {"name": "hobbies",
   "type": {"type": "array", "items": "string"}}
 ]}

Evolution rules

    

      

        
ChangeBackwardForwardNote

        
          
Add a field with a default✓✓New reader fills in the default

          
Add a field, no default✗✓New reader can't fill old records

          
Remove a field with a default✓✓Old reader fills in its default

          
Remove a field, no default✓✗Old reader can't fill new records

          
Rename (reader has alias)✓✗Only the reader knows the alias

          
Add a union branch✓✗Old reader can't decode the new branch

          
Change type✓ if Avro can convert it

        
      

    

    
    
      
  • In Avro, forward compatibility means the writer's schema is newer than the reader's. Backward means it's older.
    • 
      
  • null is not a default for everything. A nullable field needs a union, e.g. union {null, long}, and null can be the default only if it's the first branch. Being explicit prevents null bugs.
    • 
    


    
So where does the reader get the writer's schema?

    

      

        
ContextAnswer

        
          
Big file, millions of recordsPut the schema once at the start of the file: an Avro object container file

          
Database, records written over timePrefix each record with a schema version number and keep a table of versions. Confluent Schema Registry and LinkedIn Espresso work this way

          
Network connectionNegotiate the version at connection setup and use it for the whole connection (Avro RPC)

        
      

    

    
A version can be an incrementing integer or a hash of the schema. A registry of versions doubles as documentation and lets you check compatibility before deploying.


    
Why no tags? Dynamically generated schemas

    

      

        Avro
        
Generate the schema from the database

        
    
          
  • Each table becomes a record and each column a field, matched by name
    • 
          
  • Columns change? Just regenerate and export. The export process doesn't care
    • 
        

      

      

        Protocol Buffers
        
Someone has to assign tags

        
    
          
  • Column-to-tag mapping is maintained by hand
    • 
          
  • Automation must never reuse an old tag. This wasn't a design goal

      Wrap-up of formats
      
The merits of schemas

      Book: “The Merits of Schemas”
    

    
Schema-driven binary encoding isn't new. ASN.1 (standardized 1984) uses tag numbers too, and its DER encoding still encodes X.509 certificates. But it's complex and badly documented. Database wire protocols (read through ODBC or JDBC drivers) are proprietary binary encodings too.

    

      Why schemas pay off: “3 Cs and a D”
      
    
        
  1. Compact: field names are left out
    2. 
        
  2. Documentation that can't go stale, because decoding needs it
    3. 
        
  3. Check compatibility before deploying, using a schema database
    4. 
        
  4. Code generation: compile-time type checking in static languages
    5. 
      

    

    

      

        
FormatSchemaField identity in bytesHuman-readableEvolution

        
          
Language-specificClass definitionsClass / field infoNoAfterthought

          
JSON / XML / CSVOptional (none for CSV)Field names (CSV: column position)YesDepends on how you use them

          
Binary JSONNoneField namesNoLike JSON

          
Protocol BuffersRequired (IDL)Tag numbersNoClear rules, by tag

          
AvroRequired (IDL or JSON)None: schema orderNoClear rules, by name + defaults

        
      

    

    
Schema evolution gives you the flexibility of schema-on-read JSON databases, plus better guarantees and tooling. Keep the number of schema formats in use small.

  






  

    

      Part 2
      
Modes of dataflow

      Book: “Modes of Dataflow” and “Dataflow Through Databases”
    

    
Compatibility is a relationship between the process that encodes and the process that decodes. Who those are depends on how the data travels.

    

      

        Mode 1
Databases

        
writer encodes → disk → reader decodes

        
Like sending a message to your future self.

      

      

        Mode 2
Services: REST and RPC

        
client encodes request → server decodes, encodes response → client decodes

        
Synchronous request and response.

      

      

        Mode 3
Workflow engines

        
tasks call services · journal every result

        
Durable execution replays from a log.

      

      

        Mode 4
Event-driven

        
sender encodes → broker / actor → recipient decodes

        
Asynchronous: fire and forget.

      

    


    
Dataflow through databases

    
    
      
  • Backward compatibility is obviously required: your future self must decode what you wrote.
    • 
      
  • Forward compatibility is often required too. During a rolling upgrade, a newer instance writes a value that an older instance still reads. That's where the unknown-field trap from the top of the page bites.
    • 
      
  • Data outlives code. You can replace all the code in minutes, but five-year-old rows stay in their original encoding unless rewritten.
    • 
      
  • Migrating (rewriting) a big dataset is expensive, so databases do it lazily. LSM-trees rewrite during compaction. Relational databases add a column with a null default without touching old rows and fill in null on read.
    • 
      
  • The result: the database looks as if it has one schema, even though storage holds many historical versions.
    • 
      
  • Complex changes (single-valued to multivalued, moving data to another table) still need application-level rewrites. Keeping them compatible is still a research problem.
    • 
      
  • Archival snapshots (backups, warehouse loads) are written once and immutable, so encode them consistently in the latest schema. Avro object container files or column-oriented Parquet fit well.
    • 
    

  






  

    

      Mode 2
      
Services: REST vs RPC

      Book: “Dataflow Through Services: REST and RPC”, “Web services”, “The problems with remote procedure calls”, “Load balancers, service discovery, and service meshes”, “Data encoding and evolution for RPC”
    

    
A service is the API a server exposes. Unlike a database, which accepts arbitrary queries, a service allows only the inputs and outputs its business logic defines. That encapsulation lets each team deploy its service independently, as long as the API stays compatible.

    
    
      
  • Web service = a service spoken over HTTP. It's used by apps on users' devices, between services in one organization (microservices), and between organizations (payment APIs, OAuth).
    • 
      
  • REST builds on HTTP: simple formats, URLs identify resources, and HTTP handles caching, auth and content-type negotiation. Such an API is RESTful.
    • 
      
  • An IDL describes the endpoints and data models: OpenAPI (Swagger) for JSON web services, and Protocol Buffers for gRPC.
    • 
      
  • Service frameworks (Spring Boot, FastAPI, gRPC) handle routing, metrics, caching and auth so you write just the business logic. FastAPI generates the IDL from code; gRPC generates code from the IDL. Both can generate client SDKs.
    • 
    

    

      

        OpenAPI definition · my example
        
openapi: 3.0.0
info: { title: Weather, version: 2.1.0 }
paths:
  /forecast/{city}:
    get:
      summary: Tomorrow's forecast
      responses:
        '200':
          content:
            application/json:
              schema:
                type: object
                properties:
                  tempC: { type: number }

      

      

        FastAPI implementation · my example
        
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI(title="Weather", version="2.1.0")

    tempC: float

@app.get("/forecast/{city}",
         response_model=Forecast)
async def forecast(city: str):
    return Forecast(tempC=18.5)

      

    


    
Why RPC's big idea is flawed

    
EJB and Java RMI (Java only), DCOM (Microsoft only), CORBA (complex, no compatibility), SOAP and WS-* (complex). All tried location transparency: making a remote call look like a local function call. But a network call is a different beast.

    

      Network calls are slow and odd, like a TURTLE
      
    
        
  1. Timeouts: no result, and you don't know if it happened
    2. 
        
  2. Unpredictable: lost packets, slow or dead remote machines
    3. 
        
  3. Retries can duplicate actions without idempotence
    4. 
        
  4. Types differ across languages (JavaScript and 253)
    5. 
        
  5. Latency is high and wildly variable
    6. 
        
  6. Encode every parameter: no pointers, which hurts for big or mutable objects
    7. 
      

    

    
REST's appeal: it treats state transfer over a network as its own thing, not as a function call.


    
Finding and spreading the load

    

      

        
ApproachHowWatch out for

        
          
Hardware load balancerAn appliance in the datacenter. Clients hit one host:port; it routes and fails overSpecial equipment

          
Software load balancerNGINX or HAProxy on an ordinary machine, behaving the same wayAnother hop to run

          
DNSOne domain name, many IP addresses; the client picks oneSlow propagation and caching mean stale IPs when servers move often

          
Service discoveryRegistry like etcd or ZooKeeper. Instances register host, port and metadata (shards, datacenter), then send heartbeats. Clients look up endpoints and connect directlyA registry to operate. Gives richer metadata for smarter balancing

          
Service meshA sidecar or library on both client and server (Istio, Linkerd). Local connections only, so the mesh handles TLS and observabilityComplexity. Popular with Kubernetes

        
      

    


    
Evolving a service API

    
    
      
  • Assume servers upgrade first, clients second: backward compatibility on requests, forward on responses.
    • 
      
  • Compatibility is inherited from the encoding: gRPC follows Protocol Buffers' rules and Avro RPC follows Avro's. For JSON REST APIs, adding optional request parameters and new response fields is usually safe.
    • 
      
  • Across organizations you can't force clients to upgrade, so compatibility may last forever, and breaking changes mean running several API versions side by side.
    • 
      
  • Versioning has no standard: a version in the URL, in the HTTP Accept header, or stored per API key on the server and changed through an admin console (Stripe's approach).
    • 
    

  






  

    

      Mode 3
      
Durable execution and workflows

      Book: “Durable Execution and Workflows”
    

    
A workflow is a graph of tasks (Temporal calls them activities; others say durable functions). A workflow engine runs it: an orchestrator schedules tasks and executors run them. Workflows are triggered by a schedule, a web service or a human.

    

      

        
Kind of engineExamplesFocus

        
          
Data / ETL orchestrationAirflow, Dagster, PrefectIntegrating data systems

          
Graphical (BPMN)Camunda, OrkesNon-engineers can define workflows

          
Durable executionTemporal, RestateExactly-once workflows across services

        
      

    

    
Durable execution gives exactly-once semantics without a cross-service transaction. Every RPC result and state change is logged durably, like a write-ahead log. After a crash the task is re-run, but completed calls are not repeated: their logged results are returned instead.

      Three gotchas: durable execution needs “IDO”

      Mode 4
      
    Event-driven architectures
    
      Book: “Event-Driven Architectures”, “Message brokers” and “Distributed actor frameworks”
    
    
    
    An event (or message) goes through a message broker (event broker, message queue, message-oriented middleware) that stores it temporarily. The sender doesn't wait: communication is asynchronous. You can still build request/response by waiting for a reply on a separate channel.
    
    
    
      Why use a broker instead of direct RPC? Brokers bake BR3D
      
      
        
    1. Buffer when the recipient is down or overloaded
      2. 
        
    2. Redeliver to a process that crashed
      3. 
        
    3. Discovery not needed: no recipient IP addresses
      4. 
        
    4. Distribute one message to many recipients
      5. 
        
    5. Decouple sender and recipient
      6. 
      
    
    
    
    
    
      
    
        Queue
        
    One consumer gets it
    
        
    • A message added to a named queue goes to one of the consumers
    • Good for sharing work
    
      
    
      
    
        Topic (publish/subscribe)
        
    Every subscriber gets it
    
        
    • A message published to a topic goes to all subscribers
    • Good for broadcasting
    
      
    
    
    
    
      
      
    • Brokers: the commercial era (TIBCO, IBM WebSphere, webMethods), then open source (RabbitMQ, ActiveMQ, HornetQ, NATS, Redpanda, Kafka), then cloud (Kinesis, Azure Service Bus, Google Cloud Pub/Sub). Compared in Chapter 12.
      • 
      
    • A message is just bytes plus metadata, in any encoding. A common setup is Protocol Buffers, Avro or JSON with a schema registry. AsyncAPI is the messaging counterpart of OpenAPI.
      • 
      
    • Many brokers delete messages once consumed. Keeping them forever is needed for event sourcing.
      • 
      
    • A consumer that republishes to another topic must preserve unknown fields, the same trap as with databases.
      • 
    
    
    
    Distributed actor frameworks
    
    
      
      
    • The actor model: logic lives in actors with private state that exchange async messages, one message at a time, so there are no threads, locks or deadlocks to manage. Delivery isn't guaranteed.
      • 
      
    • Akka, Orleans, Erlang/OTP spread actors across nodes. Messages to remote actors are encoded transparently.
      • 
      
    • Location transparency works better here than in RPC, because actors already expect lost messages, even locally.
      • 
      
    • Rolling upgrades still need forward and backward compatibility between nodes.
      •
