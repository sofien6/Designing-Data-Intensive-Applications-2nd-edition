Replication

Keep a copy of the same data on several networked machines. Copying static data is easy. The hard part is handling changes: who accepts writes, how they spread, and what readers see while copies disagree. Almost every distributed database uses one of three families.

Why replicate?

Book: chapter introduction, “Backups and Replication”, and the Summary

All the difficulty lies in handling changes to replicated data. The core principles date from the 1970s, because the constraints of networks haven't changed.

Mnemonic · five purposes
Happy Dogs Don't Lose Sticks
  1. High availability: keep running when machines, a zone or a region go down
  2. Durability: don't lose data when a machine dies for good
  3. Disconnected operation: keep working through a network interruption
  4. Latency: put data close to users
  5. Scalability: serve more reads by reading from replicas
Replication

Copies the present, fast

  • Writes on one node quickly appear on the others
  • An accidental delete is replicated too, so it can't undo mistakes
  • Archived replication logs can feed a backup process
Backups

Keeps the past

  • Old snapshots let you go back in time and restore deleted data
  • A snapshot is often step 1 when setting up a new replica
  • Cheaper in an object store tuned for rarely read data

You need both. This chapter assumes every machine holds the whole dataset. Chapter 7 drops that assumption with sharding.

Family 1

Single-leader replication

Book: “Single-Leader Replication”, “Synchronous Versus Asynchronous Replication”, “Setting Up New Followers”

Also called leader-based, primary-backup or active/passive. The leader is also called primary or source. Followers are also called read replicas, secondaries or hot standbys. Avoid the old term master–slave.

Used by PostgreSQL, MySQL, Oracle Data Guard, SQL Server Always On, MongoDB, DynamoDB, Kafka, DRBD, and consensus systems built on Raft (CockroachDB, TiDB, etcd, RabbitMQ quorum queues), which also elect a new leader automatically.

Synchronous vs asynchronous

Synchronous

Leader waits for the follower's OK

  • The follower is guaranteed up to date. If the leader dies, the data survives
  • If that follower is slow or down, all writes block
  • So never make every follower synchronous
Asynchronous (nonblocking)

Leader sends and moves on

  • Leader keeps accepting writes even if every follower lags
  • If the leader dies unrecoverably, unreplicated writes are lost, even confirmed ones
  • Widely used anyway, especially with many or far-away followers
  • Semisynchronous: one follower is synchronous, the rest asynchronous. If the sync one fails, an async one is promoted to sync. Up-to-date data is on at least two nodes.
  • Majority quorum: e.g. 3 of 5 replicas (leader included) updated synchronously. Common with consensus-based leader election.
  • Lag is usually under a second, but there is no upper bound: recovery, near-capacity load or network trouble can push it to minutes.

Try it: what does failover lose?

Setting up a new follower without downtime

  1. Snapshot the leader consistently, ideally without locking (e.g. Percona XtraBackup for MySQL).
  2. Copy the snapshot to the new node.
  3. Request every change since the snapshot. The snapshot must map to an exact log position: PostgreSQL's log sequence number, MySQL's binlog coordinates or GTIDs.
  4. Caught up: the backlog is applied, so it now streams changes live.

A plain file copy fails because the data is changing during the copy. Archiving snapshots plus the log to an object store (WAL-G for PostgreSQL, MySQL and SQL Server; Litestream for SQLite) gives you backups and steps 1–2 for free.

Databases backed by object storage

Benefits

Cheap, durable, shared

  • Cheap tier for cold data; working set stays in memory, SSD or NVMe
  • Built-in multi-zone or multi-region durability, and no inter-zone fees
  • Conditional writes (compare-and-set) can implement transactions and leader election
  • Open formats (Parquet, Iceberg) ease data integration
Trade-offs

Slow, billed per call, immutable

  • Much higher latency than local disk or EBS
  • Per-request fees force batching, which adds more latency
  • Immutable objects make random writes expensive
  • FUSE mounts often lack POSIX features such as symlinks
  • Tiered storage: cold data on object storage, hot data on fast disks or memory.
  • Low-latency WAL beside object storage: e.g. EBS or Neon's Safekeepers.
  • Zero-disk architecture (ZDA): everything persisted in object storage; disks and memory are only caches, so nodes hold no state. Examples: WarpStream, Confluent Freight, Bufstream, Redpanda Serverless, Turbopuffer, SlateDB, most cloud warehouses.
When nodes die

Catch-up recovery vs failover

Book: “Handling Node Outages”
Follower fails

Catch-up recovery: easy

  • Its local log shows the last transaction it applied
  • It asks the leader for everything since then, applies it, and resumes
  • Cost: heavy load on both nodes if the backlog is big
  • Leader's dilemma for a long outage: keep the log (risk filling the disk) or delete it (the follower must restore from a backup)
Leader fails

Failover: tricky

  • Promote a follower, point clients at it, and make other followers consume from it
  • Manual (an administrator acts) or automatic
  • Pick the most up-to-date follower: the sync one, or the highest log sequence number

Automatic failover in three steps

  1. Detect the failure, usually by timeout (say 30 s without a response). A planned shutdown can hand off safely instead.
  2. Choose a new leader by election among a majority, or appoint one via a controller node. Agreeing is a consensus problem (Chapter 10).
  3. Reconfigure clients to write to the new leader, and make sure a returning old leader steps down and becomes a follower.
Mnemonic · what goes wrong in failover
Lose · Leak · Split · Spike
  1. Lose: async writes not yet on the new leader are usually discarded, so “committed” wasn't durable
  2. Leak: GitHub promoted a lagging MySQL follower that reused auto-increment keys also stored in Redis, exposing private data to the wrong users
  3. Split brain: two nodes both think they lead. Shutdown mechanisms can kill both, or act too late. Guarding against it is fencing
  4. Spike: a too-short timeout fails over on a load spike or network glitch, making things worse. Too long means slow recovery

Because these problems have no easy fix, some teams fail over manually even when automatic failover is available.

Mnemonic · why statements break
Clock, Counter, Side effect
  1. Clock / random: NOW() or RAND() give each replica a different value
  2. Counter / order: auto-increment and UPDATE … WHERE need the same execution order everywhere
  3. Side effects: triggers, stored procedures and UDFs must be fully deterministic

Fix: the leader substitutes fixed values for nondeterministic calls. Running deterministic statements in a fixed order is state machine replication, the same idea as event sourcing. MySQL now switches to row-based replication when a statement is nondeterministic.

Reading from followers

Problems with replication lag

Book: “Problems with Replication Lag” and “Solutions for Replication Lag”

Read scaling means adding async followers to serve reads. It only works asynchronously, so stale reads are the price. If writes stop, followers eventually catch up: that is eventual consistency, and “eventually” has no upper bound.

The term was coined by Douglas Terry and colleagues and popularized by Werner Vogels. It applies to async relational followers too, not just NoSQL.

Mnemonic · three guarantees
See mine, never go back, keep order
  1. Read-after-write (read-your-writes): you always see your own updates. No promise about other users
  2. Monotonic reads: once you've seen newer data, you never see older data. Stronger than eventual, weaker than strong
  3. Consistent prefix reads: writes are seen in the order they happened, so no answer before its question
GuaranteeAnomaly it preventsWays to provide it
Read-after-writeYou post a comment, reload, and it's gone (stale follower)Read your own editable data from the leader · read from the leader for a minute after your last write · refuse followers lagging over a minute · remember your last write's timestamp (logical, like an LSN, or a synced clock) and only read from replicas at least that fresh · route to the leader's region. Cross-device: centralize the timestamp and route all of a user's devices to one region
Monotonic readsA comment appears, then vanishes on refresh (fresh replica, then a staler one)Always read from the same replica, e.g. chosen by a hash of the user ID. Reroute if it fails
Consistent prefixAn observer sees the answer before the question (shards replicating at different speeds)Write causally related data to the same shard, or track causal dependencies explicitly

Regions and availability zones

  • A zone (availability zone) is one datacenter with its own power and cooling. A region is several zones in one geographic location.
  • Zones in a region are linked by fast networks; multi-zone survives a zone outage but not a regional one.
  • Multi-region survives regional outages but costs latency, throughput and networking fees.

So what should you do?

  • Ask how your app behaves if lag grows to minutes or hours. Pretending async is sync causes trouble later.
  • Handling it in application code is complex and easy to get wrong.
  • Simplest model: a database with linearizability (Chapter 10) and ACID transactions (Chapter 8), so it acts like one node. That's the NewSQL trend, which followed the early-2010s NoSQL view that scale required eventual consistency.
  • Weaker models are still chosen for better resilience to network interruptions and lower overhead.
Family 2

Multi-leader replication

Book: “Multi-Leader Replication”, “Geographically Distributed Operation”, “Sync Engines and Local-First Software”

Several nodes accept writes, and each leader also follows the others. Also called active/active or bidirectional. Synchronous multi-leader behaves like single-leader, so the interesting case is asynchronous.

One leader vs a leader per region

ConcernSingle-leaderMulti-leader
PerformanceEvery write crosses the internet to the leader's regionWrites are local; inter-region delay is hidden from users
Regional outageFailover promotes a follower in another regionEach region carries on; replication catches up later
Network problemsVery sensitive to the inter-region linkEach leader keeps working through an interruption
ConsistencyCan offer strong guarantees, e.g. serializable transactionsMuch weaker: can't enforce “balance ≥ 0” or unique usernames

Supported by MySQL, Oracle, SQL Server and YugabyteDB; as add-ons in Redis Enterprise, EDB Postgres Distributed and pglogical. Often retrofitted, so auto-increment keys, triggers and constraints misbehave. Many consider it dangerous territory to avoid if possible. It rarely pays off within a single region.

Replication topologies

Circular and star

Sparse: one failure blocks the flow

  • Writes hop through several nodes, so nodes forward what they receive
  • Loop prevention: each write is tagged with the IDs of nodes it passed; a node ignores writes carrying its own ID
  • Rerouting around a dead node is usually manual
All-to-all

Dense: messages can overtake

  • Multiple paths, no single point of failure
  • A fast link can deliver an update before its insert to some leader: a causality problem
  • Timestamps can't fix it (clocks drift). Version vectors can, but many systems don't use them, so test yours

Sync engines and local-first software

Offline-capable apps are multi-leader taken to the extreme: every device is a “region” with a local replica that accepts writes, and the network between them is extremely unreliable. Lag can be days. Real-time collaboration (Google Docs and Sheets, Figma, Linear) is multi-leader too: each open browser tab is a replica.

  • Sync engine: a library that captures local changes, sends or queues them, receives others' changes, merges them, and updates the UI.
  • Offline-first: you keep editing while offline.
  • Local-first: offline-first and still works if the developer shuts down its servers, via an open sync protocol with several providers. Git is local-first, though not real-time.
Pros

Fast, offline, simpler code

  • Local data: respond in the next frame (16 ms at 60 Hz)
  • Offline is just a very long network delay; no separate offline mode
  • Local reads and writes almost never fail, so code is more declarative
  • Pairs well with reactive programming for live updates
Cons and examples

Only for data a user can hold

  • Works best when all the user's data is downloaded up front: a user's own files yes, a store's whole catalog no
  • Pioneered by Lotus Notes (1980s)
  • Proprietary backends: Firestore, Realm, Ditto. Open: PouchDB/CouchDB, Automerge, Yjs
  • Games call it netcode, which is too game-specific to reuse
The big problem

Dealing with conflicting writes

Book: “Dealing with Conflicting Writes” through “Types of conflict”

Two writes are concurrent when neither was aware of the other, however far apart in time they happened. Concurrent writes on different leaders conflict, e.g. one user retitles a page to B while another retitles it to C.

Mnemonic · the ladder of strategies, cheapest first
Avoid, Last-write-wins, Manual, Automatic: ALMA
  1. Avoid: route all writes for a record to one leader (a user's “home” region); odd/even ID generators. Breaks when the designated leader changes; impossible offline
  2. LWW: highest timestamp wins, the rest are silently dropped. Converges, but loses data
  3. Manual: keep all values as siblings and let the app or user merge them (CouchDB)
  4. Automatic: merge algorithms (CRDTs, OT) that converge with no data loss
Last write wins

Really “random write wins”

  • For concurrent writes, which is “last” is undefined, so the timestamp order is essentially random
  • Ties broken by comparing values (e.g. alphabetical)
  • Fine if you only insert unique keys and never update
  • Real-time clocks make it fragile: a node with a fast clock wins even against later writes. A logical clock fixes that
Manual resolution (siblings)

Nothing lost, but four problems

  • The API changes: a title becomes a set of strings
  • Merge UIs are work for developers and confusing for users
  • Naive auto-merge surprises: unioning carts brings deleted items back (Amazon's cart)
  • Concurrent resolutions can conflict again: B/C vs C/B merges to B/C/C/B

Automatic resolution

Replicas converge: any replicas that processed the same writes have the same state, in any arrival order. Eventual consistency plus convergence is strong eventual consistency.

  • Text: keep every insertion and deletion; order same-position inserts deterministically.
  • Collections (to-do list, cart): track insertions and deletions the same way.
  • Counters: sum each sibling's increments and decrements without double counting.
  • Key-value maps: merge per key with one of the above; different keys are independent.
  • Limit: invariants such as “at most five items” may force dropping data.

OT vs CRDT on one example

Both replicas start with hat. Replica A types c at the front (“chat”). Replica B concurrently adds s at the end (“hats”). Both must end with chats.

Operational transformation

Ops carry indexes, which get transformed

c0h1a2s3t4

Applying B's insert(3, "s") as is on A gives chast. Wrong.

c0h1a2t3s4

Shift it by one for A's earlier insert: insert(4, "s") gives chats.

CRDT

Characters carry permanent IDs

c4Ah1Aa2At3As4B

A sends “insert c (ID 4A) after nil”. B sends “insert s (ID 4B) after 3A”. Positions are IDs, not indexes, so both ops apply unchanged on every replica. Same-position ties are ordered by ID.

  • OT: mostly real-time text editing, e.g. Google Docs; ShareDB for JSON.
  • CRDTs: Redis Enterprise, Riak, Azure Cosmos DB; Automerge and Yjs for JSON.
  • Hybrid algorithms (e.g. Eg-walker) combine the advantages of both.

Subtle conflicts

A room-booking app inserts a new row per booking, so no field is overwritten. Two bookings for the same room and time can still both pass an availability check and conflict. Chapter 8 and Chapter 13 return to this.

Family 3

Leaderless replication

Book: “Leaderless Replication”, “Writing to the Database When a Node Is Down”, “Catching up on missed writes”

Any replica accepts writes. The client (or a coordinator acting for it) sends each write to several replicas and reads from several in parallel. Nobody enforces an order of writes. There is no failover.

  • Some of the earliest replicated systems were leaderless. Amazon's Dynamo paper (2007) revived the idea, hence Dynamo-style: Riak, Cassandra, ScyllaDB.
  • DynamoDB is not Dynamo-style. It is single-leader, using Multi-Paxos.
  • Every value carries a version number or timestamp; the reader keeps the newest one even if only one replica returned it.
Mnemonic · how a replica catches up
Repair on read, Hints on write, Anti-entropy in the background
  1. Read repair: a reader sees a stale version on one replica and writes the newer value back. Good for frequently read values
  2. Hinted handoff: another replica stores hints for the down node and hands them over when it returns. Covers values nobody reads
  3. Anti-entropy: a background process compares replicas and copies missing data, in no particular order and possibly much later
The arithmetic

Quorums: w + r > n

Book: “Using quorums for reading and writing”, “Understanding the limitations of quorum consistency”, “Monitoring staleness”

With n replicas, a write needs w OKs and a read queries r nodes. If w + r > n, the read set and write set must overlap, so at least one node you read has the latest value.

  • Requests go to all n in parallel; w and r say how many replies to wait for. Fewer reachable nodes than w or r means an error.
  • Common: odd n (3 or 5), w = r = ⌈(n + 1) / 2⌉. Read-heavy: w = n, r = 1, but one dead node blocks all writes.
  • Writes tolerate n − w unavailable nodes; reads tolerate n − r.
  • Quorums needn't be majorities; any overlapping sets work (e.g. Flexible Paxos). A cluster may have more than n nodes; each value lives on n of them.

Why quorums still aren't a guarantee

  • A node with the new value fails and is restored from a stale replica, so fewer than w hold the new value.
  • During rebalancing, nodes disagree about which n hold a value, so quorums may not overlap.
  • A read concurrent with a write may or may not see it; a later read may see the older value.
  • A write that succeeded on fewer than w nodes is reported failed but not rolled back, so later reads may return it.
  • Real-time-clock timestamps (Cassandra, ScyllaDB) can silently drop writes when another node's clock runs fast.
  • Concurrent writes can be applied in different orders on different replicas: a conflict.

Smaller w and r (w + r ≤ n) means more stale reads but lower latency and higher availability. Dynamo-style databases target workloads that tolerate eventual consistency; w and r tune the probability of staleness.

Monitoring: leader-based

Easy: subtract positions

  • Same write order everywhere, so lag = leader's log position − follower's log position
Monitoring: leaderless

Hard: no fixed order

  • Stored hint counts are one signal, but hard to interpret. Still, quantify “eventual”

Single-leader vs leaderless performance

Reading from a single leader

Fresh, but fragile

  • Read throughput capped by the leader
  • Leader failure means waiting for detection and failover
  • A slow leader slows every user
  • Must decide whether a degraded leader warrants failover
Leaderless

Resilient, with its own costs

  • No failover; slow replicas are simply ignored: request hedging cuts tail latency
  • Treats normal and failure cases the same, which helps with gray failures
  • Hinted handoff adds load when the system is already strained
  • Bigger quorums raise the chance of hitting a slow node; rarely beyond 4 of 7 or 5 of 9
  • Sloppy quorum (Riak, Dynamo) / consistency level ANY (Cassandra, ScyllaDB): any reachable node accepts writes, with no read guarantee

Multi-leader is even more tolerant of network interruptions (one nearby leader), but reads can be arbitrarily stale. Quorums are the compromise.

Multi-region

  • Cassandra / ScyllaDB: the client picks a local coordinator node; it writes to all local replicas and to one replica per other region, which fans out locally. Consistency levels: a global quorum, a quorum in each region, or a local quorum (fast but staler).
  • Riak: n counts replicas within one region; cross-region replication is asynchronous, in a multi-leader style.
Who knew about whom

Detecting concurrent writes

Book: “Detecting Concurrent Writes”, “The happens-before relation and concurrency”, “Capturing the happens-before relationship”, “Version vectors”

A happens before B if B knew about, depended on or built on A. Two operations are concurrent if neither happens before the other. Only three cases exist: A → B, B → A, or concurrent. Later overwrites earlier; concurrent means a conflict.

  • If replicas simply overwrite on arrival, writes arriving in different orders leave them permanently inconsistent.
  • LWW (Cassandra, ScyllaDB) converges but can't tell concurrent from sequential. Riak uses CRDTs.
  • Physical time doesn't matter. As in relativity, what counts is whether information could have reached the other event, and a slow network can make events seconds apart concurrent.

The single-replica version-number algorithm

  1. The server keeps a version number per key and bumps it on every write.
  2. A read returns all siblings (values not yet overwritten) plus the latest version. Clients must read before writing.
  3. A write carries the version it was based on and the client's merge of all siblings it saw.
  4. The server overwrites values with version ≤ that number and keeps higher ones as concurrent siblings. A write with no version overwrites nothing.

Version vectors

  • With several replicas accepting writes, keep a version number per replica, per key. The set of them is a version vector.
  • Sent to clients on read and returned on write (Riak calls it the causal context), so the database can tell overwrites from concurrent writes.
  • Reading from one replica and writing to another is safe: at worst it creates siblings.
  • Dotted version vectors are used in Riak 2.0.
  • Version vectors are not quite vector clocks. To compare replica states, version vectors are the right structure.
