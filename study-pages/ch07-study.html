Sharding

When one machine can't hold the data or absorb the writes, split the dataset into shards and spread them over many nodes. Each record lives in exactly one shard, and each shard is usually replicated too. The hard parts are picking the split, keeping load even, moving shards around, finding the right node, and indexing across shards.

Replication vs sharding

Book: Chapter 7 introduction, “Sharding and Partitioning” sidebar, “Pros and Cons of Sharding”
Replication · Chapter 6

Same data, many copies

  • Fault tolerance, offline operation, read scaling
  • Useful at any scale
  • If only reads are the bottleneck, this is enough
Sharding · this chapter

Different data, different nodes

  • For when data volume or write throughput is too much for one node
  • The main tool for horizontal scaling (scale-out, shared-nothing)
  • Heavyweight. If one machine copes, stay with a single shard
  • They combine: every record is in one shard, but that shard is stored on several nodes. With single-leader replication, a node can lead some shards and follow others. Each shard still has one leader.
  • The sharding scheme is mostly independent of the replication scheme, so the chapter ignores replication.
  • A partition key decides the shard: records with the same partition key land in the same shard. Know the key and lookup is fast. Don't know it and you search every shard.
  • Costs: the scheme is hard to change; relational data needs secondary indexes and joins across shards; writes touching several shards need distributed transactions, which are slower and can bottleneck the system.
  • Sharding also works inside one machine: Redis, VoltDB and FoundationDB run one single-threaded process per CPU core, which also suits NUMA memory layouts.
  • In PostgreSQL, partitioning splits a table into files on one machine, while sharding spreads data across machines. Elsewhere the words are synonyms. Neither has anything to do with network partitions (Chapter 9).
  • Where the word comes from: possibly Ultima Online's shattered crystal (parallel game worlds), or the rumored 1980s “System for Highly Available Replicated Data”.
A common use

Sharding for multitenancy

Book: “Sharding for Multitenancy”

In SaaS, each tenant (customer business) has a self-contained dataset. Give each tenant its own shard, or group small tenants into one shard.

Seven advantages: Real Programmers Can Build Robust Distributed Games
  1. Resource isolation: one tenant's heavy job doesn't slow others
  2. Permission isolation: an access-control bug is less likely to leak data
  3. Cell-based architecture: services + storage per cell, so faults stay in one cell
  4. Backup and restore per tenant
  5. Regulatory compliance: GDPR/CCPA export or delete is one shard
  6. Data residence: pin a tenant's shard to a jurisdiction
  7. Gradual schema rollout, one tenant at a time
Works well when

Tenants are separate and modest

  • Each tenant fits on one node
  • Tenants rarely need each other's data
  • Shards can be separate databases or managed portions of one logical database (e.g. Citus schema-based sharding)
Challenges

Size and cross-tenant features

  • A tenant too big for one node needs sharding within it again
  • Many tiny tenants: one shard each is too much overhead; grouping them means moving tenants as they grow
  • Features that join data across tenants become cross-shard work
  • Rolling out a schema per tenant is hard to do transactionally
The core choice

Key range vs hash of key

Book: “Sharding of Key-Value Data”, “Sharding by Key Range”, “Sharding by Hash of Key”

Goal: spread data and query load evenly, so 10 nodes handle 10× the data and throughput. Uneven sharding is skew; an overloaded shard is a hot spot; one overloaded key is a hot key.

Key-range sharding

Contiguous keys, like encyclopedia volumes

  • Each shard owns keys from a min to a max. Boundaries adapt to the data, so ranges aren't evenly spaced
  • Keys sorted within a shard (B-tree or SSTables), so range scans are cheap
  • Risk: writes to nearby keys (e.g. timestamps) all hit one shard
  • Boundaries set manually (Vitess) or automatically (Bigtable, HBase, MongoDB range option, CockroachDB, RethinkDB, FoundationDB). YugabyteDB does both
Hash sharding

Hash first, then map to a shard

  • A good hash turns skewed keys into uniformly spread numbers, deterministically
  • Need not be cryptographic: MongoDB uses MD5, Cassandra/ScyllaDB use Murmur3
  • Avoid Java Object.hashCode() and Ruby Object#hash: the value can differ between processes
  • Cost: range queries over the partition key become scatter-gather

  • Each shard owns a range of hash values, not keys. Consecutive timestamps scatter, so no hot shard from nearby keys.
    • 
      
  • Shards can still be split when too big or too hot, so the shard count adapts to the data.
    • 
      
  • Compound keys rescue range queries: hash only the first column (the partition key), sort by the rest. All rows with the same partition key share a shard, so a range over the second column is efficient. E.g. key (user_id, timestamp).
    • 
      
  • Used by YugabyteDB and DynamoDB, optional in MongoDB. Data warehouses do something similar: BigQuery partition key + cluster columns, Snowflake micro-partitions + cluster keys, Delta Lake cluster keys.
    • 
      
  • Cassandra / ScyllaDB variant: split the hash space into ranges with random boundaries, several per node (16 per node by default in Cassandra, 256 in ScyllaDB). Uneven ranges average out. A new node takes parts of existing ranges.

      Skew
      
Hot keys and relieving hot spots

      Book: “Skewed Workloads and Relieving Hot Spots”
    

    
Even key distribution ≠ even load. A celebrity's viral post sends a storm of reads and writes to one key, and no hash function can spread a single key.

    

      

        Write: salt the hot key with a random suffix
        
// only for keys flagged as hot
key = "post:9001#" + randInt(0, 99)
// writes now spread over 100 keys
// → can land on different shards

      

      

        Read: now you must fan out and combine
        
parts = [0..99].map(i =>
  get("post:9001#" + i))
total = combine(parts)
// reads per shard are NOT reduced,
// only the write load is split

      

    

    
    
      
  • Bookkeeping: salt only the few hot keys, track which keys are split, and have a process to convert a normal key into a managed hot key.
    • 
      
  • Load changes over time: a viral post cools after a couple of days. Some keys are hot for writes, others for reads, needing different strategies.
    • 
      
  • Range-based systems can give one hot key its own shard, even its own machine.
    • 
      
  • Cloud services automate it: Amazon calls it heat management (S3) or adaptive capacity (DynamoDB). Meta uses Shard Manager.
    • 
    

  






  

    

      Operations
      
Automatic vs manual rebalancing

      Book: “Operations: Automatic Versus Manual Rebalancing”
    

    

      

        Fully automatic · e.g. DynamoDB
        
Convenient, can autoscale

        
    
          
  • Less routine operational work
    • 
          
  • Adds and removes shards within minutes as load changes
    • 
          
  • But unpredictable: moving data reroutes requests and can overload network and nodes
    • 
          
  • Near max write throughput, splitting may not keep up with incoming writes
    • 
        

      

      

        Human in the loop
        
Slower, fewer surprises

        
    
          
  • Avoids rebalancing storms
    • 
          
  • Lets you rebalance ahead of known spikes (Cyber Monday, World Cup tickets)
    • 
          
  • Middle ground: Couchbase and Riak suggest an assignment that an admin commits
    • 
        

      

    

    
Cascading failure: node A is overloaded and slow → others think A is dead → automatic rebalancing moves A's load onto them → they slow down too → they are suspected dead → … Automatic rebalancing plus automatic failure detection can make things worse.

  






  

    

      Finding the node
      
Request routing

      Book: “Request Routing”
    

    
Which IP and port holds this key? Like service discovery, except a request can go only to a node that holds that key's shard, not to any stateless instance. The router must know key → shard and shard → node.

    

      

        Approach 1
        
Any node forwards

        
client → random node (round-robin LB)
→ owns it? answer : forward to owner

      

      

        Approach 2
        
Routing tier

        
client → shard-aware router
→ correct node
(router stores no data)

      

      

        Approach 3
        
Smart client

        
client knows the shard map
→ connects straight to the node

      

    

    
Three hard questions

    
    
      
  • Who decides the shard → node assignment? A single coordinator is simplest, but must fail over without split brain (two coordinators making contradictory assignments).
    • 
      
  • How do routers learn about assignment changes?
    • 
      
  • During a shard move there's a cutover period: what about requests still in flight to the old node?

      The awkward part
      
Local vs global secondary indexes

      Book: “Sharding and Secondary Indexes”, “Local Secondary Indexes”, “Global Secondary Indexes”
    

    
A secondary index finds all records with a value (all red cars), not one record by key. Those records are spread across shards, so the index doesn't map neatly onto them.

    

      

        Local · document-partitioned
        
Each shard indexes its own records

        
    
          
  • Write: touch one shard only
    • 
          
  • Read: scatter/gather to all shards (unless you know the partition key, or need only some results)
    • 
          
  • Tail latency amplification; more shards add storage but not query throughput
    • 
          
  • Used by MongoDB, Riak, Cassandra, Elasticsearch, SolrCloud, VoltDB
    • 
        

      

      

        Global · term-partitioned
        
One index over all data, sharded by term

        
    
          
  • Read one term: one index shard holds the whole postings list, but fetching records still hits the data shards
    • 
          
  • AND of terms on different shards: ship postings lists over the network and intersect; slow if long
    • 
          
  • Write: may touch several index shards; keep in sync with a distributed transaction, or accept async staleness (DynamoDB)
    • 
          
  • Used by CockroachDB, TiDB, YugabyteDB; DynamoDB has both
    •
