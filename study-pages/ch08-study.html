Transactions

A transaction groups several reads and writes into one unit that either commits completely or aborts completely, so the application can retry instead of cleaning up half-done work. This chapter covers what ACID really promises, the race conditions that weak isolation levels let through, three ways to get true serializability, and how to commit atomically across several nodes.

Why transactions exist

Book: Chapter 8 introduction, “What Exactly Is a Transaction?”

Transactions are not a law of nature. They are a tool that simplifies the programming model: the database handles a whole class of faults and concurrency problems, so the application doesn't have to. These are called safety guarantees.

Six things that go wrong: Hardware And Networks Cause Partial Races
  1. Hardware or database software fails mid-write
  2. Application crashes halfway through a series of operations
  3. Network cuts the app off from the database, or one node from another
  4. Clients overwrite each other's concurrent writes
  5. Partially updated data gets read
  6. Race conditions between clients cause surprising bugs
1975 → today

The System R style

  • IBM System R, the first SQL database, set the model in 1975
  • MySQL, PostgreSQL, Oracle and SQL Server are still uncannily similar to it
  • Outcome is commit (all writes stick) or abort / rollback (none do), then retry safely
Late 2000s → now

NoSQL, then NewSQL

  • NoSQL dropped transactions, or redefined the word to mean something much weaker
  • Popular belief: transactions can't scale
  • Proven wrong by CockroachDB, TiDB, Spanner, FoundationDB and YugabyteDB: sharding + consensus gives ACID at scale
  • Not every app needs transactions. Weakening or dropping them can buy performance or availability, and some safety properties can be had without them.
  • But they prevent a lot of grief: the UK Post Office Horizon scandal was probably caused, technically, by a lack of ACID transactions in the accounting system.
  • To decide whether you need them, first learn exactly what they guarantee and what they cost. That is the rest of this chapter.
The four promises

What ACID really means

Book: “The Meaning of ACID” (Atomicity, Consistency, Isolation, Durability, “Replication and Durability” sidebar)

Coined by Härder and Reuter in 1983. In practice one database's ACID is not another's, and “ACID compliant” has become mostly a marketing term. The vaguer opposite, BASE (basically available, soft state, eventual consistency), effectively just means “not ACID”.

A

Atomicity

A fault partway through several writes aborts the transaction, and every write made so far is discarded. Safe to retry.

Not about concurrency. Better name: abortability.
C

Consistency

Application invariants (e.g. the ledger balances) hold before and after each transaction. They may break briefly mid-transaction.

A property of the app, not the database. Doesn't really belong in ACID.
I

Isolation

Concurrent transactions can't step on each other. In textbooks, isolation means serializability: same result as running one after another.

Most databases ship something weaker.
D

Durability

Once committed, data isn't forgotten, even after a crash. On one node: written to disk (fsync, WAL, checksums). In a replicated system: copied to enough nodes.

Perfect durability doesn't exist.

“Consistency” has at least five meanings

PhraseMeaningWhere
Replica / eventual consistencyReplicas converge on the same data in asynchronous replicationCh. 6

Consistent hashingA sharding scheme that moves few keys on rebalancingCh. 7

  • The database enforces only invariants you declare as constraints: foreign keys, uniqueness, check constraints, sometimes triggers or materialized views. Anything else is up to how the app writes its transactions.
  • Durability is risk reduction, not a guarantee. Disks die and take data offline. A correlated fault can wipe every replica's memory. Async replication can lose recent writes on failover. SSDs can break fsync on power loss, firmware has bugs, and data can rot silently, spreading to replicas and recent backups. So combine disk writes, remote replication and backups.
Scope

Single-object vs multi-object

Book: “Single-Object and Multi-Object Operations”, “Handling errors and aborts”
Almost every storage engine

Single object, one node

  • No torn 10 kB fragment of a 20 kB JSON doc, no old/new value spliced together, no half-written value seen by a reader
  • Atomicity via a crash-recovery log; isolation via a lock per object
  • Extras: atomic increment, conditional write (compare-and-set)
  • Useful, but not transactions. Cassandra/ScyllaDB “lightweight transactions” and Aerospike's strong consistency mode cover one object only
Needs real transactions

Several objects kept in sync

  • Foreign keys and graph edges must point at valid rows
  • Denormalized copies (e.g. a cached count) must match the source
  • Secondary indexes must match the data they index
  • Relational DBs group statements by TCP connection, between BEGIN and COMMIT. A multi-put API is not necessarily a transaction

My example: a shop stores orders rows and a denormalized orders_today counter. Without isolation, a dashboard can see the new order but the old count. Without atomicity, a crash after the insert leaves the counter permanently wrong.

Retrying aborted transactions isn't free

Five caveats: Did Overload Permanently Send Crashes?
  1. Duplicate: it actually committed but the ack was lost, so a retry runs it twice (dedupe needed)
  2. Overload: retrying makes contention worse. Limit retries, use exponential backoff
  3. Permanent errors (constraint violation) aren't worth retrying, only transient ones
  4. Side effects outside the DB (sending an email) happen even on abort
  5. Client crash while retrying loses what it was trying to write
  • ACID databases would rather abandon a transaction than leave it half-finished. Leaderless datastores do “best effort” and won't undo work, so recovery is the app's job.
  • Rails ActiveRecord and Django don't retry aborted transactions. The error bubbles up and user input is lost, which defeats the purpose of rollback.

Anomaly lab

Book: “Weak Isolation Levels”, Table 8-1

Concurrency bugs only show up with unlucky timing, so testing rarely finds them. They have bankrupted a Bitcoin exchange, and attackers can trigger them deliberately with bursts of concurrent requests. Pick an anomaly, then an isolation level, and see whether it can happen.

  • Read committed is the default in Oracle, PostgreSQL and SQL Server. Dirty writes are stopped with row-level write locks. Dirty reads are usually stopped by remembering the old committed value and serving it until the writer commits. Read locks also work (Db2, SQL Server with read_committed_snapshot=off), but one slow writer then stalls every reader.
  • Read uncommitted blocks dirty writes only. A dirty read can also force cascading aborts: anyone who read rolled-back data must abort too.
  • Read skew (a nonrepeatable read) is “acceptable” under read committed: each value was committed when read. It is fatal for backups (the inconsistency becomes permanent on restore) and for analytics and integrity checks.
  • “Use an ACID database for money” misses the point. Popular “ACID” databases default to weak isolation too.
How snapshot isolation works

Snapshots and MVCC

Book: “Snapshot Isolation and Repeatable Read”, “Multiversion concurrency control”, “Visibility rules…”, “Indexes and snapshot isolation”

Each transaction reads from a consistent snapshot: all data committed when it started, frozen. The database keeps several committed versions of each row side by side, which is multiversion concurrency control (MVCC). Key principle: readers never block writers, and writers never block readers.

Writers: 31, 32 committed early · 34 committed after 35 started · 36 aborted · 38 still running

Visibility rules: ignore writes that were Running, Later or Aborted
  1. Running: by a transaction still in progress when I started, even if it commits later
  2. Later: by a transaction with a higher ID than mine, committed or not
  3. Aborted: by any aborted transaction, whenever it aborted
  4. Everything else is visible. Applies to both inserts (inserted_by) and deletes (deleted_by)
  • Each transaction gets an always-increasing txid. An update is really a delete + insert. Deleted rows stay until garbage collection knows nobody can see them. (PostgreSQL txids are 32-bit; vacuum handles the wraparound.)
  • Versions of a row live in the same heap and form a linked list. An index entry points at one version; queries walk the list to the visible one.
  • Alternative: immutable copy-on-write B-trees (CouchDB, Datomic, LMDB). Each write creates a new root, and each root is a snapshot. No txid filtering, but needs compaction and GC.
  • Supported by PostgreSQL, MySQL/InnoDB, Oracle, SQL Server; Oracle, TiDB and Aurora DSQL use it as their highest level. BigQuery uses it for point-in-time analytics.

Write-write conflicts

Preventing lost updates

Book: “Preventing Lost Updates”

Two transactions each read, modify, write the same value. The second write clobbers the first, because it doesn't include it. Counters, balances, editing a JSON list, two people saving the same wiki page.

Five fixes: All Engineers Detect Concurrent Conflicts
  1. Atomic write operations
  2. Explicit locking (FOR UPDATE)
  3. Detect lost updates automatically and abort
  4. Conditional write (compare-and-set)
  5. Conflict resolution / commutative merges in replicated DBs
1 · Atomic operation (best when it fits) 
UPDATE stock
   SET qty = qty - 1
 WHERE sku = 'MUG-07';

Implemented with an exclusive lock on the object, or by running all atomic ops on one thread. MongoDB and Redis have their own. ORMs make it easy to write an unsafe read-modify-write by accident.

2 · Explicit lock (logic too complex for SQL) 
BEGIN;
SELECT * FROM seats
 WHERE flight = 'QF9' AND seat = '14C'
   FOR UPDATE;  -- lock the rows returned
-- app checks the fare rules here
UPDATE seats SET holder = 'u_552'
 WHERE flight = 'QF9' AND seat = '14C';
COMMIT;

Easy to forget a lock somewhere. Locking several objects risks deadlock; the DB aborts one, so retry.

4 · Conditional write / optimistic locking 
UPDATE profiles
   SET bio = 'new text', version = 8
 WHERE user_id = 552 AND version = 7;
-- 0 rows updated? someone beat you: re-read, retry

Like a CPU's CAS instruction. Under MVCC, many DBs let the WHERE of an UPDATE/DELETE see concurrent writes. If yours doesn't, it may be unsafe.

3 · Automatic detection 
detects lost updates and aborts:
  PostgreSQL repeatable read
  Oracle serializable
  SQL Server snapshot isolation
does NOT detect them:
  MySQL/InnoDB repeatable read

Works efficiently with snapshot isolation and needs no special app code, but you must retry aborts. Some authors say a DB that misses lost updates isn't really snapshot isolation.

  • Replicated DBs (multi-leader, leaderless) have no single up-to-date copy, so locks and conditional writes don't apply. Instead keep conflicting siblings and merge them. Commutative operations (counter increments, set adds) merge safely, which is the idea behind CRDTs.
  • Last write wins, the default in many replicated DBs, is prone to lost updates.
The subtle one

Write skew and phantoms

Book: “Write Skew and Phantoms”

Two transactions read the same data, decide based on it, then write different objects. Each write is fine alone; together they break an invariant. It generalizes lost updates (same object = dirty write or lost update).

The phantom pattern: Check, Decide, Write
  1. Check: a SELECT tests a condition over matching rows
  2. Decide: app code chooses to proceed or abort
  3. Write: INSERT, UPDATE or DELETE that changes the step-1 result
  4. A write that changes another transaction's search result = a phantom
Scenario (my examples)CheckWriteFix
Lifeguards on duty≥ 2 lifeguards on this shift?UPDATE my row: off dutyRows exist, so SELECT … FOR UPDATE works
Tennis court bookingNo overlapping booking?INSERT bookingSerializable, or materialize slots

Doesn't help

Lost-update tools

  • Atomic single-object operations: several objects are involved
  • Automatic lost-update detection: PostgreSQL RR, MySQL RR, Oracle serializable and SQL Server SI all miss write skew
  • FOR UPDATE when the check looks for the absence of rows: nothing to lock
Does help

From best to last resort

  • Serializable isolation: the real fix
  • Multi-object constraints via triggers or materialized views, where supported
  • Lock the rows you depend on, if they exist
  • Materializing conflicts: pre-create a lock table (e.g. room × 15-minute slot) and lock its rows. Ugly and error-prone: concurrency control leaks into the data model
  • Snapshot isolation avoids phantoms in read-only queries, but not phantoms that cause write skew in read/write transactions. ORM-generated SQL is prone to it too.
The strongest level

Serializability, three ways

Book: “Serializability”, “Actual Serial Execution”, “Two-Phase Locking”, “Serializable Snapshot Isolation”

Serializable isolation guarantees the result equals some serial order, so if each transaction is correct alone, they stay correct together. It prevents all race conditions. Researchers have recommended it since the 1970s; the question is cost.

Pessimistic, extreme

Actual serial execution

one thread · one txn at a time · stored procedures

VoltDB/H-Store, Redis, Datomic. Feasible since the 2000s: RAM holds the active data, and OLTP transactions are short. Analytics run on a snapshot outside the loop.

Pessimistic

Two-phase locking (2PL)

shared + exclusive locks · held to commit · predicate / index-range locks

The only widely used option for ~30 years. MySQL/InnoDB and SQL Server serializable, Db2 repeatable read.

Optimistic

Serializable snapshot isolation (SSI)

snapshot reads · track conflicts · abort at commit

First described in 2008. PostgreSQL serializable, SQL Server Hekaton, HyPer, CockroachDB, FoundationDB, BadgerDB.

Serial execution: interactive vs stored procedure

Interactive

One statement per round trip

  • Query, read result, query again… across the network
  • A single thread would sit idle waiting for the app, so throughput would be dreadful
  • Transactions never wait for a human: on the web, one transaction per HTTP request
Stored procedure

Whole transaction sent up front

  • With data in memory, runs without network or disk waits
  • Bad reputation: vendor languages (PL/SQL, T-SQL, PL/pgSQL), hard to debug, test, deploy, monitor; a bad one hurts a shared DB; security risk for untrusted tenant code
  • Modern ones use real languages: Java/Groovy (VoltDB), Java/Clojure (Datomic), Lua (Redis), JavaScript (MongoDB)
  • VoltDB replicates by running the deterministic procedure on each replica: state machine replication
When serial execution fits: Small, Memory, one Core, rare Cross-shard
  1. Small and fast transactions: one slow one stalls everything
  2. Active dataset fits in memory
  3. Write throughput fits one CPU core, or shards cleanly, one per core
  4. Cross-shard transactions run in lockstep and scale badly (VoltDB: ~1,000 writes/s)
Pessimistic vs optimistic

2PL vs SSI

Book: “Implementation of 2PL”, “Performance of 2PL”, “Predicate locks”, “Index-range locks”, SSI subsections
Pessimistic · wait if anything might go wrong

Two-phase locking

  • Read → shared lock. Write → exclusive lock. A shared lock can be upgraded.
  • Writers block readers and readers block writers
  • Locks held until commit/abort: growing phase, then shrinking phase
  • Deadlocks are frequent; the DB aborts one and the app retries
  • Slow: lock overhead, little concurrency, unstable high-percentile latency. A full-table read blocks all writes to that table.
Optimistic · carry on, check at commit

Serializable snapshot isolation

  • Reads from a snapshot; nothing blocks
  • Tracks when a transaction's premise may be outdated
  • Aborts at commit only if the execution wasn't serializable
  • Predictable latency; read-only queries need no locks
  • Suffers under high contention (many aborts) and with long read/write transactions. Commutative ops reduce contention.

Stopping phantoms under 2PL

Predicate lock: precise but slow 
-- lock everything matching, even rows
-- that don't exist yet
SELECT * FROM court_bookings
 WHERE court = 4
   AND ends   > '2026-05-02 18:00'
   AND starts < '2026-05-02 19:00';

Readers take a shared predicate lock; writers check old and new values against all predicate locks. Checking many locks is slow.

Index-range (next-key) lock: coarser, cheap 
lock index entry   court = 4      (any time)
   or index range  18:00–19:00    (any court)
no usable index?   lock the whole table

Safe to lock a superset of the predicate. Any conflicting insert must touch the same index part and hits the lock.

How SSI spots an outdated premise

Write happened before my read

Stale MVCC read

  • I ignored an uncommitted write because of the visibility rules
  • At my commit, the DB checks whether that ignored write has since committed. If so: abort me
  • Why wait? I might be read-only (no skew possible), or the other writer might still abort
Write happens after my read

Write affecting a prior read

  • Like index-range locks, but they don't block: they act as a tripwire
  • A writer notifies transactions that recently read that index range (or table)
  • The first to commit wins; the other aborts when it commits
  • Read tracking is kept until all concurrent transactions finish
  • Trade-off: fine-grained tracking means fewer needless aborts but more bookkeeping. PostgreSQL uses theory to skip some aborts that are provably still serializable.
  • Not limited to one core: FoundationDB spreads conflict detection over many machines. Whether SSI's overhead over plain snapshot isolation is worth it is still debated.

Two-phase commit (2PC)

Book: “Distributed Transactions”, “Two-Phase Commit”, “A system of promises”, “Coordinator failure”, “Three-phase commit”

On one node, the commit hinges on one disk finishing the commit record (data first, then the record). Across nodes, just sending “commit” to everyone can commit on some and abort on others, and committed data can't be taken back because others may already have read it. That is the atomic commitment problem.

Coordinator
Participant A · orders DB
Participant B · payments DB
    Point of no return 1

    A participant votes yes

    • Before voting it writes all data to disk and checks constraints and conflicts
    • It gives up the right to abort, without committing yet
    • From now on it is in doubt until it hears the decision
    Point of no return 2

    The coordinator decides

    • Commit only if all voted yes; write the decision to its log: the commit point
    • Then retry sending it forever until every participant has it
    • No commit record in the log after a crash → abort
    • 2PC is blocking: if the coordinator dies after the votes, participants can only wait. Neither a timeout-abort nor a timeout-commit is safe. Lost coordinator log means manual resolution.
    • Three-phase commit is nonblocking only with bounded network delay and response times, which real systems don't have. Better: make the coordinator fault-tolerant with consensus (Chapter 10).
    • Coordinators (transaction managers): Narayana, JOTM, BTM, MSDTC. Often a library inside the app process.
    • 2PL ≠ 2PC. Two-phase locking gives serializable isolation; two-phase commit gives atomic commit across nodes.
    In practice

    Heterogeneous vs database-internal

    Book: “Distributed Transactions Across Different Systems”, “XA transactions”, “Holding locks while in doubt”, “Database-Internal Distributed Transactions”, “Exactly-Once Message Processing Revisited”
    Different technologies

    XA transactions

    • X/Open XA (1991): a C API, not a network protocol. Java uses JTA via JDBC and JMS drivers
    • Supported by PostgreSQL, MySQL, Db2, SQL Server, Oracle, ActiveMQ, HornetQ, MSMQ, IBM MQ
    • Coordinator usually a library in the app; its log on the app server's disk is now critical state
    • The DB can't contact the coordinator; everything goes through the app's driver, so the app is a single point of failure
    • Lowest common denominator: no cross-system deadlock detection, no SSI
    Same database software

    Internal distributed transactions

    • CockroachDB, TiDB, Spanner, FoundationDB, YugabyteDB; Kafka too
    • Often still 2PC, but free to use better protocols
    • Fixes: replicate the coordinator with failover; coordinator talks to shards directly; replicate shards; couple commit with distributed concurrency control (deadlock detection, consistent reads)
    • Snapshot isolation and SSI possible across shards
    • Why in-doubt hurts: the transaction keeps its row locks (and 2PL read locks). A 20-minute coordinator restart means 20 minutes of blocked rows; a lost log means forever. Rebooting the DB doesn't help: correct 2PC keeps the locks across restarts.
    • Orphaned in-doubt transactions need an admin to check every participant and apply one outcome, usually mid-outage. Heuristic decisions let a participant decide alone: a euphemism for probably breaking atomicity, for emergencies only.
    • 2PC's cost comes from extra fsyncs and network round trips. Many cloud services skip distributed transactions altogether.

    Exactly-once without distributed transactions

    Goal: a message's effects happen effectively once, even with retries. XA could atomically commit the broker ack and the DB writes, but a plain database transaction plus an idempotency table is enough:

    BEGIN;
INSERT INTO handled_msgs (msg_id) VALUES ('evt-9f3');  -- unique constraint
-- already there? it was processed before: ack the broker and stop
UPDATE wallets SET credits = credits + 50 WHERE user_id = 552;
COMMIT;
-- then: ack 'evt-9f3' to the broker
-- then, in a separate transaction: DELETE FROM handled_msgs WHERE msg_id = 'evt-9f3';
    Crash pointWhat happens on retry
    Before DB commitTransaction aborted; broker redelivers; processed fresh
    After commit, before ackRedelivered; ID found; just ack and drop
    After ack, before deleteA stale ID costs a little storage, nothing else
    Concurrent retryUniqueness constraint stops a second insert of the same ID
    • Recording the ID makes processing idempotent. Kafka Streams uses a similar idea (Chapter 12). Internal distributed transactions still help it scale, e.g. IDs on one shard and data on others.
    • A side effect outside the transaction, such as an email from a server without 2PC, can still be sent twice.
