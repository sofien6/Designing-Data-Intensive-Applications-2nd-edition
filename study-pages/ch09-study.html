The Trouble with Distributed Systems

On one computer, things mostly either work or crash. Across a network, some parts fail while others keep going, and you often can't even tell which. This chapter lists everything you can't rely on, so that Chapter 10 can build guarantees on top of it.

Start here

One computer vs many computers

Book: Chapter 9 introduction, “Faults and Partial Failures”
Single machine

Works fully or fails fully

  • Same operation, same result: deterministic
  • Hardware faults usually mean a total crash (kernel panic, blue screen)
  • Designed that way on purpose: a crash is better than a wrong answer
  • Presents an idealized, mathematically perfect model (silent corruption exists, but is rare enough to ignore)
Distributed system

Some parts broken, others fine

  • Partial failure: some nodes or links fail while the rest work
  • Nondeterministic: the same operation may work one time and fail the next
  • You may not even know whether something succeeded
  • Faults happen too often to ignore. You have to face the physical world
  • In a big enough system, a one-in-a-million event happens every day. Anything that can go wrong will go wrong.
  • The upside: if you tolerate partial failure, you can build a system more reliable than any one node, e.g. a rolling upgrade that restarts one node at a time with no downtime.
  • So test for unlikely faults on purpose. In distributed systems, suspicion, pessimism and paranoia pay off.
Trouble #1

Unreliable networks

Book: “Unreliable Networks”, “The Limitations of TCP”, “Network Faults in Practice”

Datacenters and the internet are asynchronous packet networks: no promise about when a message arrives, or whether it arrives. If you get no reply, you can't tell why.

Six things that can happen to a request: Lazy Queues Can Pause Really Late
  1. Lost request (unplugged cable)
  2. Queued request, delivered later (overload)
  3. Crashed remote node
  4. Paused remote node (long GC), back later
  5. Response lost (misconfigured switch)
  6. Late response (network or your own machine overloaded)

What TCP gives you

“Reliable” inside one connection

  • Splits big messages into packets and reassembles them
  • Retransmits lost packets, reorders, checks a simple checksum
  • Congestion control / flow control / backpressure: sends as fast as the network and receiver allow
  • Length-prefixed messages over one connection: how HTTP and many RPC protocols work
What TCP can't give you

Knowledge of what happened

  • Can't tell a lost packet from a lost ack; can't plug a cable back in
  • Eventually times out and reports an error
  • Dedup only works within one connection. Reconnect and resend, and data may be duplicated
  • An ack means the remote kernel got it, not that the application handled it. You need a reply from the application itself

The same applies to QUIC, SCTP (WebRTC), BitTorrent uTP and other transports.

Network faults are common

  • One medium datacenter: about 12 network faults a month, half cutting off one machine, half a whole rack.
  • Redundant network gear helps less than expected, because it doesn't stop human error (misconfigured switches).
  • Fiber cuts blamed on cows, beavers and sharks, plus misconfiguration, scavenging and sabotage.
  • Round trips of several minutes across cloud regions at high percentiles; over a minute inside one datacenter during a switch reconfiguration. Assume arbitrary delay.
  • Faults can be partial or one-way: A↔B and B↔C work but A↔C doesn't; a NIC that drops all inbound packets but sends fine.
  • A short blip can have effects that last much longer than the blip itself.
  • A network partition (netsplit) is just one kind of network fault. It has nothing to do with sharding.
  • Untested error handling can deadlock a cluster or even delete all data. Handling faults can mean just showing an error, but you must know how the system reacts, and test it with fault injection.
Detecting faults

Timeouts and unbounded delays

Book: “Fault Detection”, “Timeouts and Unbounded Delays”, “Network congestion and queueing”, “Variability of network delays”

Sometimes you get explicit feedback, but usually all you have is silence. So you pick a timeout, and every timeout trades slow detection against false accusations.

Lucky cases: explicit feedback

Someone tells you it's down

  • Machine reachable, no process on the port: OS replies with RST or FIN
  • Process died but OS alive: a script notifies the others (HBase does this)
  • Query the datacenter switches' management interface for link failures
  • A router replies ICMP Destination Unreachable, though it can be wrong too
Usual case: silence

Retry, wait, declare dead

  • Too short: live nodes declared dead; work done twice (e.g. an email sent twice)
  • Moving a “dead” node's load to others can cause a cascading failure when it was only overloaded
  • Too long: users wait or see errors while a dead node is still trusted
The ideal that doesn't exist: if every packet arrived within d or was lost, and every live node answered within r, then 2d + r would be the perfect timeout. Real networks have unbounded delays, and most servers can't promise r.

Where queueing delay comes from: Slow Orders Via Truck
  1. Switch queue: several senders, one output port (network congestion); full queue drops packets
  2. OS queue: all cores or threads busy, request waits
  3. VM monitor buffers data while the VM is paused for another VM
  4. TCP sender holds data back to avoid congestion
  • TCP retransmission hides the loss but not the delay.
  • Queues grow fastest near full capacity. In clouds, a noisy neighbor can saturate shared links, NICs and CPUs.
  • Choose timeouts experimentally: measure round-trip distributions over time and many machines.
  • Better: adapt automatically to measured response times and jitter. The Phi Accrual failure detector (Akka, Cassandra) does this, and TCP's retransmission timeout works similarly.
  • UDP vs TCP: UDP skips flow control and retransmission, so delays vary less. It suits cases where late data is worthless, like VoIP: fill the gap with silence and move on. The retry happens at the human level (“could you repeat that?”).
Why not fix it in hardware?

Circuit switching vs packet switching

Book: “Synchronous Versus Asynchronous Networks”, “Latency and Resource Utilization”, “Combining circuit switching and packet switching”
Telephone network · synchronous

Reserve bandwidth for the whole call

  • A circuit reserves fixed bandwidth along the whole route
  • ISDN: 4,000 frames/s, 16 bits per call per frame, so 16 bits every 250 µs
  • No queueing, so bounded delay
  • Static partitioning: your slot is reserved even when the wire is empty
Ethernet / IP · asynchronous

Grab whatever bandwidth is free

  • Built for bursty traffic: web pages, email, files just want to finish fast
  • With a circuit you'd have to guess the bandwidth: too low is slow, too high can't be set up
  • Idle TCP connection uses no bandwidth (except keepalives)
  • Dynamic sharing: high utilization, cheaper per byte, but queueing and unbounded delay
  • The same trade-off appears with CPUs: threads share cores dynamically and wait in the run queue. Clouds put several customers' VMs on one machine for the same reason.
  • Latency guarantees are possible with static resource partitioning, but they cost utilization, so they cost money. Variable delay is a cost/benefit choice, not a law of nature.
  • Hybrids: ATM (lost to Ethernet), InfiniBand (link-level flow control), QoS + admission control, L4S, Linux traffic control. BGP peering with dedicated bandwidth is closer to circuits.
  • None of this is enabled in multitenant clouds or over the internet. Assume congestion and unbounded delay. There's no “correct” timeout.
Trouble #2

Time-of-day clocks vs monotonic clocks

Book: “Unreliable Clocks”, “Monotonic Versus Time-of-Day Clocks”, “Clock Synchronization and Accuracy”

Apps ask clocks two kinds of question: durations (has this timed out? p99 latency?) and points in time (when was this published? when does the cache entry expire?). Each machine's quartz clock has its own idea of the time, and NTP can only partly line them up.

Time-of-day (wall-clock)

“What date and time is it?”

  • clock_gettime(CLOCK_REALTIME), Java System.currentTimeMillis()
  • Seconds since the epoch (1970-01-01 UTC), ignoring leap seconds
  • Synced by NTP, so values are comparable across machines (ideally)
  • Can jump backward when reset, or on leap seconds. DST jumps are avoided by using UTC
  • Unsuitable for measuring elapsed time
Monotonic

“How much time has passed?”

  • CLOCK_MONOTONIC / CLOCK_BOOTTIME, Java System.nanoTime()
  • Always moves forward; only the difference between two readings means anything
  • Absolute value is arbitrary (e.g. time since boot); never compare across machines
  • NTP can slew its rate by up to 0.05%, but can't make it jump
  • Good for timeouts in a distributed system

Error = drift rate × time since the last sync. 200 ppm is the figure Google assumes for its servers. NTP's own error (network delay, bad servers) comes on top of this.

Why clocks are wrong: Don't Rely Fully, Networks Will Lie Very Unpredictably
  1. Drift: quartz runs fast or slow, depends on temperature
  2. Reset: too far from NTP, so refused or forcibly stepped (time jumps)
  3. Firewalled from NTP, unnoticed while the drift adds up
  4. Network delay limits NTP accuracy (≈35 ms over the internet, spikes to ~1 s)
  5. Wrong NTP servers, off by hours (clients query several and drop outliers)
  6. Leap seconds: 59 or 61-second minutes; smearing helps; abolished from 2035
  7. VMs: paused VM sees the clock jump forward
  8. User devices: clocks set wrong on purpose, e.g. to cheat in games
  • High accuracy is possible if you pay for it: MiFID II requires high-frequency traders to stay within 100 µs of UTC, using GPS, atomic clocks and PTP. GPS can be jammed.
  • A broken clock fails silently. A bad CPU or network gets noticed fast; a drifting clock causes quiet data loss. Monitor clock offsets and remove nodes that drift too far.
Relying on synchronized clocks

Ordering events by timestamp

Book: “Relying on Synchronized Clocks”, “Timestamps for ordering events”, “Clock readings with a confidence interval”, “Synchronized clocks for global snapshots”

Last write wins keeps the value with the highest timestamp. If the timestamps come from skewed clocks, a write that clearly happened later can lose and silently disappear.

My own example. Real-time order: alice sets x = 1 on node A; it reaches node C 2 ms later; 1 ms after that, bob increments x on node C. Both writes then replicate to node B, which keeps the highest timestamp.

Problems with last write wins on client clocks (Cassandra, ScyllaDB)

  • Writes vanish: a node with a slow clock can't overwrite a fast-clock node's value until the skew has passed. No error is reported.
  • It can't tell sequential writes from truly concurrent ones. You need causality tracking such as version vectors.
  • Equal timestamps (millisecond resolution) need a tiebreaker such as a random number, which can also violate causality.
  • Even good NTP can make a packet look like it arrived before it was sent (sent at 100 ms, received at 99 ms). NTP accuracy is itself limited by round-trip time, so it can never be good enough to order events by.
  • Alternative: logical clocks, counters that track only relative order (Chapter 10). Time-of-day and monotonic clocks are physical clocks.

  • A reading with microsecond digits isn't microsecond-accurate. Over the public internet, expect tens of ms at best and 100+ ms during congestion.
  • Uncertainty ≈ quartz drift since last sync + server's uncertainty + round-trip time. Most APIs (clock_gettime) don't report it.
  • TrueTime (Spanner) and Amazon ClockBound return [earliest, latest].
  • Distributed MVCC snapshots need transaction IDs that respect causality. A global counter is a bottleneck, so Spanner uses TrueTime timestamps and waits out the interval before committing. GPS or atomic clocks in each datacenter keep it to about 7 ms.
  • The interval is what matters. Accurate clocks only make it smaller. YugabyteDB can use ClockBound on AWS.
Trouble #3

Process pauses

Book: “Process Pauses”, “Providing response time guarantees”, “Limiting the impact of garbage collection”

A leader holds a lease (a lock with a timeout) and renews it. The danger is the gap between checking the lease and acting on it. A thread can freeze in that gap for seconds without knowing.

Looks safe (my own sketch) 
loop:
  job = queue.next()
  if lease.expires_at - now() < 5s:
      lease = lease.renew()
  if lease.still_mine():
      // ← 12 s GC pause here
      storage.write(job)
Two separate problems 
1. expires_at was set by ANOTHER
   machine's clock, compared to OURS
   → skewed clocks break it
2. Even with a monotonic clock:
   check → pause → act
   lease expired, someone else is
   leader, and we write anyway
Eight reasons a thread freezes: Cats Get Very Lazy, Cows Doze Softly Sometimes
  1. Contention on locks or queues (worse with many cores)
  2. Garbage collection, “stop-the-world” (once minutes long)
  3. VM suspended and resumed, or live migration
  4. Laptop lid closed, phone suspended
  5. Context switch or hypervisor steal time under load
  6. Disk I/O, including surprise I/O such as lazy class loading or network disks like EBS
  7. Swapping / paging, and in the extreme, thrashing
  8. SIGSTOP (Ctrl-Z) until SIGCONT
  • Like thread-safety on one machine, you can't assume anything about timing. But mutexes, semaphores and atomics don't exist across machines: no shared memory, only an unreliable network.
  • A paused node may be declared dead by the others and resume as if nothing happened, until it next checks the clock.
Eliminate pauses

Hard real-time systems

  • Airbags, aircraft, rockets, robots: a missed deadline is a failure
  • Needs an RTOS, documented worst-case times, restricted memory allocation, huge testing effort
  • Very expensive, limited tools; “real-time” ≠ high-performance (often lower throughput)
  • Not economical for most server-side systems
Live with pauses

Reduce the impact of GC

  • Modern collectors (Java G1, ZGC, Shenandoah; Go's concurrent GC) usually pause only a few ms
  • No GC at all: Swift (reference counting), Rust and Mojo (lifetimes in the type system)
  • Object pools, off-heap memory
  • Treat GC as a planned outage: drain traffic from the node, collect, return it. Or restart processes before a full GC is needed, like a rolling upgrade

“Real-time” on the web (pushing data to clients) is a looser meaning than in embedded systems.

Knowledge, truth and lies

Majorities, leases and fencing tokens

Book: “Knowledge, Truth, and Lies”, “The Majority Rules”, “Distributed Locks and Leases”, “Fencing off zombies and delayed requests”, “Fencing with multiple replicas”

A node can only guess about other nodes from the messages it gets. It can't even trust its own judgment. So decisions, including “that node is dead”, are made by a quorum.

Three nightmares

Wrongly declared dead

  • Node hears everything, but its replies are dropped: buried while shouting “I'm not dead!”
  • Node notices its messages aren't acked, but can't do anything about it
  • Node pauses for a minute and wakes up in the coffin, unaware that any time has passed
The rule

The majority decides

  • If a quorum says you're dead, you are dead. Step down.
  • Usual quorum: more than half the nodes (3 nodes tolerate 1 fault, 5 tolerate 2)
  • Safe because there can only be one majority at a time
  • More on this with consensus in Chapter 10
  • Use a lease when there must be only one: one leader per shard (avoid split brain), one writer per object, one worker per input file. The first two can corrupt data; the third only wastes work.
  • Two ways to get two leaseholders: a paused holder whose lease expired (HBase once had this bug), or a delayed write sent just before a crash that arrives after the lease moved.
  • A former leaseholder that doesn't know it lost the lease is a zombie. Shutting it down (STONITH) is weak: it doesn't stop delayed packets, nodes may shoot each other, and it may already be too late.

    • Also called sequencers (Chubby), epoch numbers (Kafka), ballot number (Paxos), term number (Raft).
    • ZooKeeper: use zxid or cversion. etcd: revision + lease ID. Hazelcast FencedLock generates one.
    • A new holder should write immediately, so zombies are fenced off from then on. Like optimistic concurrency control, but fencing is permanent, not retried.
    • Storage can instead offer conditional writes (write only if unchanged since I read it): S3 conditional writes, Azure conditional headers, GCS request preconditions. Then a separate lock service may be unnecessary.
    • Multiple replicas: put the token in the high-order digits of the LWW timestamp. Any write from token 8 beats any write from token 7, even if the zombie wrote later. A stray zombie write on one replica gets overwritten by read repair.
    When nodes lie

    Byzantine faults

    Book: “Byzantine Faults”, “The Byzantine Generals Problem”, “Uses of Byzantine fault tolerance”, “Weak forms of lying”

    This book assumes nodes are unreliable but honest: slow or stale, but never lying. A node that sends deliberately false or corrupted messages (say, a fake fencing token) is a Byzantine fault.

    • Two generals problem: agree on a plan using messengers who may be lost. Byzantine generals: n generals, some of them secret traitors.
    • Named for “byzantine” meaning overly complicated and devious. Lamport was warned off calling it the “Albanian Generals Problem”.
    • Most BFT algorithms need more than two-thirds of nodes correct (4 nodes tolerate 1).
    BFT makes sense

    Radiation or untrusted parties

    • Aerospace: radiation flips bits in memory and registers. Flight control must tolerate it
    • Mutually untrusting parties: Bitcoin and other blockchains agree without a central authority
    • Peer-to-peer networks with no central authority
    Usually not worth it

    Your own datacenter

    • You control all the nodes; radiation is low (orbital datacenters are being considered)
    • Multitenancy uses firewalls, VMs and access control instead
    • Web clients: just make the server the authority and validate input (SQL injection, XSS)
    • Doesn't help with bugs (you'd need 4 independent implementations) or attackers (compromise one, compromise all). Use authentication, access control, encryption, firewalls

    Cheap protection against weak lying

    • Corrupted packets that slip past TCP/UDP checksums: add application-level checksums, or use TLS.
    • Sanitize input: escape characters, check value ranges, limit string sizes (denial of service). Do basic checks even behind a firewall.
    • NTP with several servers: the majority's time range wins and a wrong server is dropped as an outlier.
    Reasoning about it

    System models, safety and liveness

    Book: “System Model and Reality”, “Defining the correctness of an algorithm”, “Distinguishing between safety and liveness”, “Mapping system models to the real world”

    A system model writes down which faults an algorithm assumes can happen. An algorithm is correct in a model if its properties hold in every situation that model allows.

    Safety · “nothing bad happens”

    Must hold always

    • If broken, you can point to the moment it broke
    • Damage can't be undone
    • Must hold even if every node crashes or the whole network fails
    • Fencing examples: uniqueness, monotonic sequence
    Liveness · “something good eventually happens”

    Allowed caveats

    • Often contains the word “eventually”
    • May not hold yet, but can still become true later
    • Can depend on e.g. a majority being up and the network eventually healing
    • Fencing example: availability. Also: eventual consistency

    Try it: safety or liveness?

    • Models are simplifications. Crash-recovery assumes the disk survives, but disks get corrupted or wiped, or firmware fails to see them after a reboot.
    • A node with amnesia breaks quorum algorithms that rely on nodes remembering what they stored.
    • Real code still has to handle the “impossible”, even if only by stopping and calling a human. That is one difference between computer science and software engineering.
    Checking the algorithm

    Formal methods and randomized testing

    Book: “Formal Methods and Randomized Testing”, “Model checking and specification languages”, “Fault injection”, “Deterministic simulation testing”, “The Power of Determinism”

    Concurrency, partial failure and delay create far too many states to test by hand. Combine proofs about the algorithm with randomized testing of the implementation (AWS, FoundationDB and TigerBeetle do both).

    TechniqueRunsStrengthWeaknessExamples
    Model checkingA spec of the algorithmExplores states systematically; finds nonobvious bugs (data loss found in Viewstamped Replication's prose spec)Bounded state space, not a proof; spec can drift from the codeTLA+, Gallina, FizzBee; used by CockroachDB, TiDB, Kafka
    Fault injectionThe real system, in a production-like environment or even productionTests real failure handling: kills, unmounts, firewall cutsMany tools needed; can't control exact ordering, so hard to replayJepsen; Netflix Chaos Monkey (chaos engineering)
    Deterministic simulation (DST)The real code, with network, I/O and clocks mockedMany random runs, any failure replays exactly, can run faster than real timeAll nondeterminism must be controlledFoundationDB, TigerBeetle, Antithesis
    Three ways to make code deterministic for DST: ARM
    1. Application-level: designed in (FoundationDB's Flow, TigerBeetle's single event loop)
    2. Runtime-level: sequential async runtime (FrostDB patches Go; Rust MadSim replaces Tokio, S3 and Kafka libraries)
    3. Machine-level: a deterministic hypervisor (Antithesis)
    • Determinism is a recurring idea: event sourcing replays a log; workflow engines need deterministic workflows; state machine replication runs the same deterministic transactions on every replica (statement-based replication, stored procedures).
    • Hidden nondeterminism remains: hash-table iteration order, running out of memory or stack.
    Summary: packets get lost or delayed, clocks are off by unknown amounts, and processes pause. That is partial failure. Detection relies on timeouts, which can't tell a network fault from a node fault. Decisions need a quorum. If one machine is enough, stay on one machine. Distribute when you need fault tolerance, low latency near users, or scale.
