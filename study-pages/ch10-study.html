Eventual consistency vs strong consistency

Book: Chapter 10 introduction

Replication gives fault tolerance but creates copies that can disagree: stale reads, and conflicts when several replicas take writes. There are two ways to deal with it.

Eventual consistency

The app sees the replication

  • You, the developer, handle inconsistencies and conflicts
  • Typical of multi-leader and leaderless replication
  • Unavoidable if users can edit while offline (local-first, sync engines)
  • Keeps working through faults that would stop a strongly consistent system
Strong consistency

Behave like a single node

  • Replication details are hidden from the app. Simpler to program against
  • Costs performance
  • Some faults cause outages that an eventually consistent system would survive
  • A good fit when replicas sit in datacenters with fast, reliable links
The chapter's path: Linear Ideas Consent
  1. Linearizability: a precise meaning for “strong consistency”
  2. ID generators and timestamps: closely tied to consistency
  3. Consensus: how to get linearizability and still tolerate faults
  • These are notoriously hard to implement. Systems that are fine without faults fall apart under an unlucky mix of faults and message orderings. The theory exists to cover those edge cases.
  • The chapter stays informal. Real work on consensus systems needs the formal theory and the references.
Definition

Linearizability

Book: “Linearizability”, “What Makes a System Linearizable?”

Make the system look as if there is only one copy of the data, and every operation on it is atomic. Once any client sees a new value, every later read, on any client, must see it too. It is a recency guarantee.

  • Also called atomic consistency, strong consistency, immediate consistency, external consistency.
  • The object being read and written is called a register: one key, one row or one document.
  • A client only knows its request took effect somewhere between sending it and getting the reply.
  • Reads before a write starts return the old value. Reads after it finishes return the new one. Reads concurrent with it may return either…
  • …but there is one instant when the value flips. Once any read returns the new value, no later read may return the old one, even if the write hasn't finished.
  • Draw a point inside each operation's bar where it “really” happened. Joining the points must give a valid sequential history that always moves forward in time.

Serializability

Transactions, many objects

  • An isolation level for transactions that touch multiple objects
  • Result equals some serial order, which may differ from the real order
  • Stale reads are allowed
Linearizability

Recency, one object

  • A guarantee on reads and writes of one register
  • No grouping into transactions, so it doesn't prevent write skew
  • If op 1 finishes before op 2 starts, op 2 sees a state at least as new
  • Both together: strict serializability (or strong one-copy serializability, strong-1SR). Spanner and FoundationDB offer it. CockroachDB offers serializability plus some recency, but not strict serializability, because that would need costly coordination.
  • Single-node databases are typically linearizable. Isolation level and consistency model can be chosen largely independently.
  • Weaker models include read-after-write, monotonic reads and consistent prefix reads (Chapter 6). Linearizability includes them all and is the strongest model in common use. Sequential consistency is something else again.
  • Testing for it is possible but expensive: record every request's timing and search for a valid order (Knossos, Elle).
When it matters

Relying on linearizability

Book: “Relying on Linearizability”, “Locking and leader election”, “Constraints and uniqueness guarantees”, “Cross-channel timing dependencies”

A stale sports score harms nobody. But some things break without linearizability. Remember them as LUC: Locks and leaders, Uniqueness, Cross-channel timing.

UseWhy it needs linearizabilityDetails
Locks and leader electionTwo nodes must never hold the same lease, or you get split brainZooKeeper and etcd use consensus for this; Curator adds recipes. Oracle RAC takes a lock per disk page, so it uses a dedicated interconnect network
Uniqueness constraintsTwo people claiming the same username, file path or seat at the same time: exactly one must winWorks like a lock or an atomic CAS. A hard uniqueness constraint needs it; foreign keys and attribute checks don't
Cross-channel timingA second channel (a queue, a push notification, a voice) can overtake replicationUpload a file, then queue a job: the worker may fetch an old version or nothing at all
  • ZooKeeper's writes are linearizable but its reads may be stale (served by any node). etcd v3 makes reads linearizable by default.
  • Constraints like “balance never negative” or “don't oversell stock” all need one up-to-date value that every node agrees on, unless the business can apologize and compensate (overbooking, Chapter 13).
  • If you control the second channel, there are alternatives like read-your-writes techniques, at the cost of extra complexity.

Trade-offs

The cost of linearizability

Book: “The Cost of Linearizability”, “The CAP theorem”, “The Unhelpful CAP Theorem”, “Linearizability and network delays”

Cut the link between two regions. Replicas that can't reach the others must either stop (stay linearizable) or keep going (stay available). Any linearizable system faces this choice, not just multi-region ones.

CP · consistent when partitioned

Require linearizability

  • Single-leader: clients in the follower region can't write or do linearizable reads
  • They wait or get errors: unavailable until the link heals
  • They may still read the follower, but those reads may be stale
AP · available when partitioned

Don't require it

  • Multi-leader: each region keeps accepting writes
  • Writes queue up and are exchanged when the link returns
  • Available, but behavior is not linearizable

Why CAP isn't much help

  • “Pick two of three” is misleading. Partitions are faults: they happen, you don't pick them. Better: either consistent or available when partitioned.
  • Narrow: one consistency model (linearizability) and one fault (partitions, under 8% of Google's incidents). Nothing about delays or dead nodes.
  • Its “availability” doesn't match the usual meaning. Many systems are neither CP nor AP.
  • Credit where due: named by Eric Brewer in 2000, it pushed engineers toward shared-nothing designs and helped start NoSQL. Now of mostly historical interest, replaced by more precise results.
  • PACELC: if Partitioned, choose Availability or Consistency; Else, choose Latency or Consistency. Inherits CAP's fuzzy definitions.
The real reason to drop it

Performance, not faults

  • Even RAM on a multi-core CPU isn't linearizable: per-core caches and store buffers, unless you use a memory barrier / fence
  • Cores don't keep working when cut off, so CAP doesn't explain it. Speed does
  • Same for many distributed databases: linearizable systems are slower all the time
A lower bound

Attiya and Welch

  • Linearizable reads and writes take time at least proportional to the uncertainty of network delay
  • Highly variable networks mean slow linearizable operations
  • No faster algorithm exists. Weaker models can be much faster
Ordering

ID generators

Book: “ID Generators and Logical Clocks”

An autoincrementing counter on one node gives compact, unique IDs whose order matches creation order. It's linearizable: atomic fetch-and-add. But it is a single point of failure, slow from far regions, and a bottleneck.

Counting events, not seconds

Logical clocks

Book: “Logical Clocks”, “Lamport timestamps”, “Hybrid logical clocks”, “Lamport/hybrid logical clocks versus vector clocks”

A physical clock measures time. A logical clock is an algorithm that counts events. Its timestamps don't say what time it is, but you can compare any two and say which came first.

A logical clock's timestamps are: CUTE
  1. Compact (a few bytes)
  2. Unique
  3. Totally ordered: any two can be compared
  4. Earlier causes get smaller numbers: consistent with causality
Lamport clock (my own sketch) 
timestamp = (counter, nodeId)

on generate:
  counter += 1
  return (counter, nodeId)

on see(ts from another node):
  counter = max(counter, ts.counter)

compare: counter first, then nodeId
What it does and doesn't give 
✓ if A happened before B, ts(A) < ts(B)
✓ total order, unique, compact
✗ not linearizable: says nothing
  about timestamps a node hasn't seen
✗ can't tell concurrent from ordered
  (different counters look the same)
✗ no link to real time

Hybrid logical clock

Physical time + Lamport ordering

  • Counts real seconds or microseconds, like a physical clock
  • Seeing a bigger timestamp moves your own clock forward to match
  • Incremented on every timestamp, so it's monotonic even if NTP steps back
  • Close to wall-clock time, so you can query “posts on this date”. Needs only rough sync. Used by CockroachDB
Vector clock

Detect concurrency

  • One counter per node, all stored with each write
  • If A is ahead on one node's entry and B on another's, they are concurrent
  • Lamport and HLC order concurrent events arbitrarily, so you can't tell
  • Cost: much bigger timestamps, up to one integer per node
  • Lamport limits: no relation to physical time, and nodes that never talk can have wildly different counters for events at the same moment. HLC fixes both.
  • Lamport clocks and HLCs make good MVCC transaction IDs for snapshot isolation, because the snapshot then respects causality.
Stronger than causal

Linearizable ID generators

Book: “Linearizable ID Generators”, “Implementing a linearizable ID generator”, “Enforcing constraints using logical clocks”

Linearizability says: if A finished before B started, B gets the higher ID, even if A and B never communicated. A Lamport clock only beats timestamps its node has seen.

My own example: Maya marks her calendar entry “private” on her laptop (calendar shard, HLC timestamp 120). Then on her phone she attaches a scan of her medical letter to it (files shard, whose clock is behind: timestamp 115). A coworker's MVCC snapshot at 118 sees the attachment but still sees the entry as public. The order she did things in was lost.
Option 1

Single-node timestamp oracle

  • Atomic increment, persist, and replicate (single-leader) for fault tolerance
  • TiDB/TiKV call it a timestamp oracle, after Google's Percolator
  • Optimization: persist and replicate a batch of IDs at a time. A crash skips some IDs but never repeats or reorders them
  • Can't be sharded or spread across regions; but its job is tiny, so one node handles a lot
Option 2

Spanner's clock uncertainty

  • The clock returns an interval, not a point
  • Wait out the interval before returning
  • Linearizable IDs with no communication, even across regions
  • Needs tightly synced clocks and a correct uncertainty bound
  • Are timestamps enough for a lock or a unique username? Not quite. Lowest timestamp wins, but a node only knows it is lowest after hearing from every node. One unreachable node and everything stalls. That is not fault-tolerant. We need consensus.
The core problem

Consensus

Book: “Consensus”, “The Impossibility of Consensus”, “Single-value consensus”

Failover without split brain, a fault-tolerant counter, a fault-tolerant CAS: all easy on one node, all hard with fault tolerance, and all the same problem: getting several nodes to agree on one value.

  • Best known: Viewstamped Replication, Paxos, Raft, Zab. Similar but not identical.
  • They assume a non-Byzantine model: messages may be delayed or lost and nodes may crash, but nobody lies. Byzantine-tolerant versions (blockchains) usually assume fewer than a third are faulty.
Properties of single-value consensus: All In, Very True
  1. Agreement (uniform): no two nodes decide differently
  2. Integrity: once decided, no changing your mind
  3. Validity: the decided value was proposed by someone (rules out “always null”)
  4. Termination: every node that doesn't crash eventually decides
Safety properties

Agreement, integrity, validity

  • Easy on their own: make one node the dictator
  • Kept even if a majority fails or the network is badly broken
  • An outage can stop progress but can't cause inconsistent decisions
Liveness property

Termination

  • This is fault tolerance: you can't wait forever for a dead dictator
  • Assume the crashed node is buried “under 30 feet of mud”
  • Needs a majority of nodes working (a quorum)
FLP impossibility: Fischer, Lynch and Paterson proved no deterministic algorithm in the asynchronous model (no clocks, no timeouts) can always terminate if a node may crash. Real systems escape it: timeouts to suspect crashes (even wrongly), or randomness, make consensus solvable.

The many faces of consensus

Shared log properties

Every Reader Agrees, Always Valid
  1. Eventual append: a live node eventually reads its own value
  2. Reliable delivery: if one node reads an entry, every live node eventually does
  3. Append-only: entries never change; new ones go after
  4. Agreement: same entries in the same order before any shared entry
  5. Validity: every entry was requested by some node
Consensus

Any proposed value is fine

  • Agreement, integrity, validity, termination
  • Decided value just has to have been proposed
Atomic commitment

Must abort if anyone says abort

  • Validity: commit only if all voted commit
  • Nontriviality: if all vote commit and nothing times out, must commit
  • From consensus: everyone broadcasts votes, then proposes “commit” only if all votes were yes
  • To consensus: each proposer runs a transaction that CASes a register on a quorum
  • Fetch-and-add solves consensus for two nodes: swap proposals first, then fetch-and-add. Reading 0 means decide yours; reading 1 means decide the other's.
  • Fetch-and-add from CAS: read, CAS(old, old + 1), retry on failure. Slower under contention but equivalent.
How Raft, Paxos, Zab and VR work

Consensus in practice

Book: “Consensus in Practice”, “Using shared logs”, “From single-leader replication to consensus”, “Subtleties of consensus”, “Pros and cons of consensus”

Most systems expose a shared log (Raft, VR, Zab, Multi-Paxos). Consensus is single-leader replication done right: automatic failover with no lost commits and no split brain.

  • State machine replication: every replica applies the same log of deterministic writes in the same order. This is also the idea behind event sourcing and serial execution of stored procedures.
  • From a log: first entry for a seat number decides that seat; a counter of entries gives fencing tokens (ZooKeeper's zxid).
  • Sharded databases often keep one log per shard: more scalable, weaker cross-shard guarantees.
  • The chicken-and-egg problem: you need consensus to elect a leader, and a leader for consensus. The way out is an epoch number (ballot in Paxos, view in VR, term in Raft). Only one leader per epoch, and a higher epoch wins.
Two rounds of voting: (1) a quorum elects a leader for a new, higher epoch. (2) For every log entry, the leader asks a quorum to accept it; nodes refuse if they know a higher epoch. The two quorums overlap, so if round 2 succeeds, no newer leader exists.

    Consensus voting

    Any node, a quorum

    • Any node can start an election
    • Needs only a quorum to respond
    Two-phase commit

    One coordinator, everyone

    • Only the coordinator asks for votes
    • Needs a yes from every participant

    The subtle parts

    • A new leader must honor entries the old one already appended. Raft: only a node whose log is at least as up to date as a majority can win. Paxos: anyone can win, but must catch up first.
    • Weakening this (Kafka's unclean leader election, async replication failover) recovers faster but the theory no longer applies: data loss under faults.
    • Linearizable reads also need a quorum round, to confirm the leader is still leader (etcd does this).
    • Reconfiguration lets you add or remove voting nodes, e.g. to migrate regions.
    Pros

    Safe automatic failover

    • No committed data lost, no split brain, despite all of Chapter 9's faults
    • Automatic failover without a proven algorithm is likely unsafe
    • Not a full correctness guarantee, but a good start
    Cons

    It costs you

    • Strict majority: 3 nodes for 1 failure, 5 for 2
    • Every op talks to a quorum; more nodes make it slower, not faster
    • Minority side of a partition is blocked
    • Timeout tuning is hard: too long is slow recovery, too short is constant elections
    • Raft can flap on one bad link (fixed with pre-vote). EPaxos is leaderless and more robust
    Consensus as a service

    Coordination services

    Book: “Coordination Services”, “Allocating work to nodes”, “Service discovery”, “Managing Configuration with Coordination Services”

    ZooKeeper, etcd and Consul look like key-value stores, but they hold small, slow-changing data in memory, replicated by consensus, to coordinate another system. Modeled on Google's Chubby. Kubernetes uses etcd; Spark and Flink HA use ZooKeeper.

    What they offer: Lucky Foxes Find Carrots
    1. Locks and leases: fault-tolerant CAS, only one acquirer wins
    2. Fencing tokens: monotonically increasing IDs (zxid, cversion, etcd revision)
    3. Failure detection: sessions with heartbeats; leases released on timeout (ZooKeeper ephemeral nodes)
    4. Change notifications: watch keys instead of polling

    Failure detection and notifications don't need consensus; locks and fencing do.

    UseHowWatch out
    Leader / primary electionLease + ephemeral node; another node takes over on failureSingle-leader databases, job schedulers
    Shard assignmentAtomic ops, ephemeral nodes and notifications to rebalance when nodes join or leaveStill hard; Curator helps. Much better than writing your own consensus
    Service discoveryServices register endpoints; clients watchOften overkill: doesn't need linearizability; caching (DNS, TTLs) is usually better. ZooKeeper observers serve stale but available reads
    ConfigurationKey-value settings, loaded at start, updated via notificationsDoesn't need consensus; polling a file or URL also works
    • Runs on a fixed 3 or 5 nodes however big the system is: “outsource” consensus instead of running it over thousands of nodes.
    • Data changes over minutes or hours (“node 10.1.1.23 leads shard 7”), not thousands of times a second. For fast-changing state use a database or Apache BookKeeper.
    Summary: linearizability makes replicas look like one copy, but it's slow and can't stay available in a partition. Logical clocks order by causality, not by real time. Linearizable CAS, locks, uniqueness constraints, shared logs, atomic commit and (for two nodes) fetch-and-add are all consensus in disguise. Raft and Paxos are single-leader replication with safe automatic failover, at the price of a quorum on every write and linearizable read. When you need one of these things fault-tolerantly, use a coordination service. When you don't need strong consistency, leaderless or multi-leader replication with logical clocks may serve better.
