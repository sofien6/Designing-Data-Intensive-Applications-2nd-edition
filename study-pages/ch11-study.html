Batch Processing

Online systems answer one request as fast as they can. Batch jobs work differently: they read a big, read-only input, compute for minutes or hours, and write a brand-new output. If the output is wrong, you throw it away and run the job again.

Online systems vs batch processing

Book: Chapter 11 introduction

A batch job treats its input as immutable and produces derived data from scratch on every run, with no side effects. That one rule is where most of its benefits come from.

Online system

Request in, response out

  • Web servers, APIs, databases, caches, search indexes
  • Measured by response time
  • Needs fault tolerance for high availability
  • Read/write transactions mutate data in place
Batch (offline) system

Big input in, new output out

  • Train models, transform data, run analytics on huge datasets
  • Measured by throughput: data processed per unit of time
  • Runs for minutes, hours or days, often on a schedule (say, nightly)
  • On faults, either restart the whole job or retry just the failed parts
Why immutable inputs pay off: FIRE
  1. Fix by rerunning: roll back buggy code and rerun, or switch to the old output (human fault tolerance, time travel)
  2. Irreversibility minimized: mistakes are cheap, so teams ship faster (good for Agile)
  3. Reuse inputs: the same files feed many jobs, including monitoring jobs that compare runs
  4. Efficient: uses far fewer resources than pushing the same work through an OLTP database
  • Downsides: other jobs usually can't see the output until the whole job finishes, and changing even one input byte means reprocessing the whole input.
  • The line between the two is blurry: a long analytic query looks a lot like a batch job. Batch is also key to data integration, ETL being the classic example.
  • Stream processing (Chapter 12) is the alternative: the job never finishes and reacts to new input shortly after it arrives.
  • History: Google published MapReduce in 2004 (later implemented by Hadoop, CouchDB, MongoDB). It's now largely obsolete. Today's tools are Spark, Flink and cloud warehouses (BigQuery, Snowflake), with orchestration by Airflow, Dagster and Prefect instead of Oozie or Azkaban. Storage is moving from HDFS to object stores like S3.

      Same answer, different execution
      
Sorting vs in-memory aggregation

      Book: “Chain of Commands Versus Custom Program”, “Sorting Versus In-Memory Aggregation”
    

    
A short Python script gives the same top five. The difference shows on big inputs: the script keeps a hash table of counters, while the pipeline sorts so that equal keys sit next to each other.

    

      

        Hash table (my own sketch)
        
counts = {}            # url → count
for line in log:
    url = line.split()[6]
    counts[url] = counts.get(url, 0) + 1
top = sorted(counts.items(),
             key=lambda kv: -kv[1])[:5]

      

      

        Sort, then count neighbours
        
extract url  → one line per request
sort         → equal urls are adjacent
uniq -c      → count each run of equals
sort -r -n   → biggest count first
head -n 5    → top five

      

    

    

      

        In-memory hash table
        
Fine if the working set fits

        
    
          
  • Working set = memory needed for random access = one entry per distinct URL
    • 
          
  • A million hits on one URL still cost one entry
    • 
          
  • Most small and mid-sized sites fit in about 1 GB, even on a laptop
    • 
        

      

      

        Sorting
        
Scales past memory

        
    
          
  • Sort chunks in memory, write sorted segments to disk, then merge them (like log-structured storage, Chapter 4)
    • 
          
  • Mergesort reads and writes sequentially, which disks handle well
    • 
          
  • GNU sort spills to disk and uses all CPU cores automatically. The bottleneck is reading the input
    • 
        

      

    

    
The catch with both: one machine. When the data doesn't fit on one machine's memory or disk, you need a distributed batch framework.

  






  

    

      The key analogy
      
Batch frameworks are distributed operating systems

      Book: “Batch Processing in Distributed Systems”
    

    
The Unix example relied on three things in one machine: a filesystem, a scheduler and pipes. A distributed batch framework has the same three, spread over a cluster.

    

      

        
RoleOne machine (Unix)Cluster (batch framework)

        
          
StorageDisks behind the OS filesystemDistributed filesystem (HDFS, JuiceFS) or object store (S3)

          
Running programsKernel scheduler gives processes CPU and memoryJob orchestrator (YARN, Kubernetes) places tasks on nodes

          
Moving dataPipes between stdin and stdoutFiles in the DFS, or tasks streaming data over the network (shuffle)

          
Common interfaceVirtual filesystem (VFS)A storage protocol, such as the S3 API

        
      

    

  






  

    

      Storage, part 1
      
Distributed filesystems

      Book: “Distributed Filesystems”, sidebar “Distributed Filesystems and Network Storage”
    

    
A local filesystem is layered: block device drivers → page cache → filesystem (ext4, XFS) → VFS. A DFS has a counterpart for every layer, with files split into blocks spread across machines.

    

      

        
LayerLocal (Linux)Distributed

        
          
BlocksRaw blocks on disk, 4 KB in ext4Blocks of 128 MB (HDFS) or 4 MB (JuiceFS, many object stores), stored as files on data nodes (HDFS DataNode, GlusterFS glusterfsd)

          
CachePage cache in RAMEach data node's OS page cache, plus extra tiers like JuiceFS's client and local-disk caches

          
MetadataInodes, directories, free space, permissionsA metadata service: HDFS NameNode; DeepSeek's 3FS stores it in FoundationDB

          
InterfaceVFSA protocol: the S3 API (MinIO, R2, Tigris, B2), or POSIX via FUSE or NFS (Amazon EFS, Archil)

        
      

    

    
    
      
  • Why big blocks? Less metadata to track (it adds up at petabyte scale), and seek time is small compared with read time.
    • 
      
  • Disks can't write partial blocks, but a DFS sits on top of an OS filesystem, so its last block can be short.
    • 
      
  • Shared-nothing: just commodity machines on a normal datacenter network. Compare NAS and SAN, which are shared-disk appliances with special hardware such as Fibre Channel.
    • 
      
  • Commodity hardware fails more, so blocks are protected by replication or erasure coding (Reed–Solomon): RAID-like, but across machines. Replicas also let the scheduler run a task on any node holding its input.
    •

      Storage, part 2
      
Object stores

      Book: “Object Stores”
    

    
S3, Google Cloud Storage, Azure Blob Storage and OpenStack Swift are now a popular alternative to a DFS. They look similar (FUSE can mount S3, and JuiceFS and Ceph offer both APIs), but their APIs, performance and consistency differ, so check before you rely on them.

    
Addressing: s3://bakery-logs/2026/03/14/access.log → bucket bakery-logs (globally unique name), key /2026/03/14/access.log (unique within the bucket). The slashes are just characters in the key.

    

      

        Distributed filesystem
        
Behaves like a filesystem

        
    
          
  • Real directories; files can be modified
    • 
          
  • Hard and symbolic links, file locks, atomic renames
    • 
          
  • Can run a task on the machine holding the data: saves bandwidth when the code is smaller than the data
    • 
        

      

      

        Object store
        
Behaves like a key-value store of big values

        
    
          
  • get and put; objects are immutable, so updating means rewriting the whole object. Appends only on Azure Blob and S3 Express One Zone
    • 
          
  • No fopen/fseek, no links, no locks. Rename = copy then delete, not atomic, one object at a time
    • 
          
  • Storage and compute are separate: more network traffic, but each scales on its own
    • 
        

      

    

    
Prefix listing is not a directory listing

    
    
      
  • Listing a prefix is recursive, like ls -R: objects in deeper “subdirectories” come back too.
    • 
      
  • No empty directories. Delete everything under …/03/14/ and 14 disappears from the listing. The usual trick: a zero-byte placeholder object.
    • 
      
  • Key-value stores (Chapter 4) are tuned for small values and frequent, low-latency access. DFSs and object stores are tuned for megabytes to gigabytes and fewer, bigger reads. That's changing: S3 Express One Zone offers single-digit-millisecond latency and pricing closer to key-value stores.
    • 
    

  






  

    

      Running the job
      
Distributed job orchestration

      Book: “Distributed Job Orchestration”, “Resource allocation”
    

    
On one machine the kernel starts processes, allocates memory, schedules CPU and enforces limits. In a cluster, a job orchestrator such as Kubernetes or Hadoop YARN does that job.

    
A framework asks the scheduler to start a job and sends: task count, CPU, memory and disk per task, a job ID, credentials, input and output parameters, hardware needs (GPUs, disk type), and where the executable code lives.

    

      Inside an orchestrator: Tasks Run Smoothly
      
    
        
  1. Task executors on every node (YARN NodeManager, Kubernetes kubelet): fetch code, start tasks, send heartbeats, report status. Isolate tasks with Linux cgroups
    2. 
        
  2. Resource manager: a global view of nodes, hardware, task status and network location. Keeps state in ZooKeeper (YARN) or etcd (Kubernetes)
    3. 
        
  3. Scheduler: decides which tasks run on which nodes, then tells the executors
    4. 
      

    

    
Application-specific subschedulers work alongside the central one: YARN calls them ApplicationMasters, Kubernetes calls them operators.


    
Try it: two jobs, 160 cores

    

      
My own simplified model, based on the book's scenario: 5 nodes, 160 cores (each square = 10 cores). Jobs A and B arrive together, each with 100 one-step tasks.

      

        
        
        
      

      

      
Job AJob BIdle

      

        
Job A done after–

        
Job B done after–

        
Cores idle while work waited–

      

      

    

    
    
      
  • Gang scheduling (all of a job's tasks at once) leaves cores idle while it waits, and two jobs both holding partial reservations can deadlock.
    • 
      
  • Just waiting for 100 free cores risks starvation: other jobs keep taking them. Preempting (killing) the first job's tasks frees cores but wastes work.
    • 
      
  • If job B arrives later, the scheduler is guessing: give everything to A now, or hold some back for a job that may never come?
    • 
      
  • Optimal allocation is NP-hard, so real schedulers use heuristics: FIFO, dominant resource fairness (DRF), priority queues, capacity/quota scheduling, bin-packing.
    • 
    

  






  

    

      Many jobs, and things going wrong
      
Scheduling workflows and handling faults

      Book: “Scheduling workflows”, “Handling faults”
    

    
One job's output often feeds several others: a workflow, or DAG of jobs. Workflows of 50 to 100 jobs are common. Job schedulers (YARN ResourceManager, Spark's scheduler) work one job at a time, so workflow schedulers such as Airflow, Dagster and Prefect handle the dependencies.

    

      Why split work into a workflow: TSM
      
    
        
  1. Teams: one output, many consumers owned by different teams, each on its own schedule
    2. 
        
  2. Switch tools: e.g. Spark writes to HDFS, then a Trino SQL query processes it and writes to S3
    3. 
        
  3. Multiple stages: stage 1 shards by one key so stage 2 can work on another
    4. 
      

    

    

      

        Pass data directly
        
Like a Unix pipe

        
    
          
  • A small buffer; a full buffer makes the producer wait (backpressure)
    • 
          
  • Spark and Flink can stream one task's output to the next over the network
    • 
        

      

      

        Write to shared storage
        
More common between jobs

        
    
          
  • Each job writes to the DFS or object store; the next reads it
    • 
          
  • Jobs are decoupled and can run at different times
    • 
          
  • A job with several inputs waits until all its producers succeed
    • 
        

      

    

    
Not to be confused with “workflows” in durable execution engines (Chapter 5): those run steps that make RPCs to other services; batch workflows run jobs that turn input data into output data.

    
Faults are normal

    
    
      
  • Long jobs with many tasks will hit hardware faults or network problems. They're also killed on purpose: preemption.
    • 
      
  • Batch jobs aren't urgent, so they suit cheap low-priority capacity: spot instances (EC2), spot VMs (Azure), preemptible instances (Google Cloud). That raises cluster utilization, but preemptions happen more often than hardware faults.
    • 
      
  • Output is regenerated from scratch, so recovery is simple: delete the partial output and rerun the task elsewhere. Tasks are kept independent so you retry one task, not the whole job.
    • 
    

    

      

        
EngineIntermediate data between tasksIf it's lost

        
          
MapReduceAlways written to the DFS; readers wait until the writer succeedsRobust even with heavy preemption, but lots of DFS writes

          
SparkKept in memory, spilling to local disk; only the final result goes to the DFSRecomputed from its recorded lineage

          
FlinkKept by the tasksRestored from periodic checkpoints of task state

        
      

    

  






  

    

      Processing models, part 1
      
MapReduce

      Book: “Batch Processing Models”, “MapReduce”, sidebar “MapReduce and Functional Programming”
    

    
MapReduce is the Unix pipeline made distributed. You write just two functions, map and reduce. The framework parses the input and does the sort in between for you.

    

      

        
StepUnix log exampleMapReduceWho writes it

        
          
1. Split into recordsOne line per record (\n)Input format parser over files (Parquet, Avro) in HDFS or S3Framework

          
2. Mapawk '{print $7}': URL as keyMapper emits key-value pairsYou

          
3. Sort by keyFirst sortImplicit: mapper output is always sortedFramework

          
4. Reduceuniq -cReducer gets each key with an iterator over its valuesYou

        
      

    

    

      

        Mapper
        
Once per input record

        
    
          
  • Extracts a key and value; may emit zero, one or many pairs
    • 
          
  • Stateless: each record handled on its own
    • 
          
  • Many mappers run in parallel on different parts of the input
    • 
          
  • Its role: get data into a sortable shape
    • 
        

      

      

        Reducer
        
Once per key

        
    
          
  • Gets all values for one key together
    • 
          
  • Emits output records (e.g. a count per URL)
    • 
          
  • Different keys reduce in parallel
    • 
          
  • Its role: process the sorted data
    • 
        

      

    

    
    
      
  • Need another sort, like ranking by count? Write a second MapReduce job that reads the first one's output.
    • 
      
  • From functional programming (Lisp's map and reduce/fold). No mutable state, so the framework can run calls anywhere, in parallel, and retry them safely.
    • 
      
  • Drawbacks: raw APIs are laborious (you write join algorithms yourself), and it's slow. File-based I/O between jobs rules out pipelining: downstream can't start until upstream finishes.
    • 
    

  






  

    

      Processing models, part 2
      
Dataflow engines

      Book: “Dataflow Engines”
    

    
Spark and Flink (descended from research systems Dryad and Nephele) treat a whole workflow as one job. Besides record-at-a-time functions they offer relational-style operators (join, group by, filter, aggregate) that can be combined freely, with no forced map, reduce, map, reduce rhythm.

    

      Why they beat MapReduce: Some Fast Lanes Improve Pipeline Reuse
      
    
        
  1. Sort only where needed, not between every stage
    2. 
        
  2. Fuse operators that don't change sharding (map, filter) into one task
    3. 
        
  3. Locality: the scheduler sees every dependency, so it can place a consumer next to its producer and share memory
    4. 
        
  4. Intermediate state in memory or on local disk, not replicated to the DFS
    5. 
        
  5. Pipelining: an operator starts as soon as its input is ready
    6. 
        
  6. Reuse processes instead of starting a new JVM per task
    7. 
      

    

    
They can run the same computations as MapReduce workflows, usually much faster.

  






  

    

      The core algorithm
      
Shuffling data

      Book: “Shuffling Data”, Figure 11-1
    

    
Sorting petabytes means sorting across machines, with input and output sharded. That distributed sort is the shuffle. Despite the name, it's not random: the result is sorted. Joins and aggregations are built on it.

    
Try it: a MapReduce job, step by step

    

      
My own data: page views on the bakery site, in three input shards. Map emits (url, 1); reduce sums the 1s. The partition rule is a simple string hash mod the number of reducers.

      

        

        
      

      

      

    

    
    
      
  • One map task per input shard (an HDFS file, or objects sharing a key prefix). The job's author picks the number of reduce tasks.
    • 
      
  • Each mapper writes one local file per reducer, choosing the file by a hash of the key, so every pair with the same key reaches the same reducer.
    • 
      
  • Files are sorted as they're written, LSM-style: sort in memory, write segments, merge them.
    • 
      
  • Reducers copy their file from every mapper, merge them in sorted order, then call reduce once per key. One output file per reducer becomes one output shard.
    • 
      
  • Modern engines go further. BigQuery keeps shuffle data in memory and uses an external, replicated sorting service.
    • 
    

  






  

    

      Using the shuffle
      
Joins and grouping

      Book: “Joins and Grouping”, Figures 11-2 and 11-3
    

    
To join activity events (the fact table) with user profiles (a dimension), when both are too big for one machine, make the user ID the key. The shuffle brings each user's profile and all their events to the same reducer.

    
Try it: a sort-merge join, then a group by

    

      
My own data. Question: which pages are popular with which birth decades?

      

      

      

    

    
    
      
  • Secondary sort: arrange values so the reducer sees the profile record first, then the events in time order.
    • 
      
  • The reducer keeps one user record in memory at a time and makes no network requests.
    • 
      
  • It's called a sort-merge join: mapper outputs are sorted by key, and reducers merge the sorted lists from both sides.
    • 
      
  • Grouping is the same trick: shuffle by the group key (URL), then count per group in the reducer.
    • 
    

  






  

    

      Processing models, part 3
      
Query languages and DataFrames

      Book: “Query Languages”, sidebar “Batch Processing and Cloud Data Warehouses Converge”, “DataFrames”
    

    
Running batch jobs on 10,000+ machines is basically a solved problem, so attention moved to usability. SQL became the common language of batch processing, and DataFrames serve data scientists.

    
    
      
  • SQL means less code than handwritten MapReduce, interactive exploration for analysts, PMs and finance teams, and better execution: cost-based optimizers in Hive, Trino, Spark and Flink choose join algorithms and reorder joins to keep intermediate state small.
    • 
      
  • Niche languages: Pig (step-by-step relational operators; Morel is a modern successor), JSON languages jq, JMESPath, JSONPath, and graph queries such as TinkerPop's Gremlin.
    • 
    

    

      

        Batch frameworks moved toward warehouses
        
SQL + columnar formats

        
    
          
  • Support SQL; fast on relational queries with Parquet and vectorized execution
    • 
          
  • Still better for what SQL handles badly: PageRank-style iterative graph work, complex ML, images/video/audio
    • 
          
  • Often cheaper for large jobs (Spark, Flink)
    • 
        

      

      

        Warehouses moved toward batch
        
Cloud scale + other APIs

        
    
          
  • Same scheduling, fault tolerance and shuffle techniques; often on a DFS
    • 
          
  • BigQuery DataFrames; Snowflake Snowpark with Pandas
    • 
          
  • Weak at row-by-row work on columnar storage; usually more expensive
    • 
        

      

    

    
How to choose usually comes down to cost, convenience, ease of implementation and availability. Big companies run many systems; small ones often get by with one.

    
DataFrames

    

      

        Local (R, Pandas)
        
In memory, one machine

        
    
          
  • Rows with typed columns, like a table; call functions for filter, join, sort, aggregate
    • 
          
  • Indexed and ordered
    • 
          
  • Pandas runs each call immediately
    • 
        

      

      

        Distributed (Spark, Flink, Daft)
        
Same style, cluster scale

        
    
          
  • Usually not indexed or ordered, so expect performance surprises when migrating
    • 
          
  • Spark turns the calls into a query plan, optimizes it, then runs it on the dataflow engine
    • 
          
  • Daft runs small operations on the client and large ones on the server; Arrow gives both one shared columnar data model
    • 
        

      

    

  






  

    

      Where batch is used
      
Batch use cases

      Book: “Batch Use Cases”, “Extract–Transform–Load”, “Analytics”, “Machine Learning”
    

    
Use batch wherever there's lots of data and freshness doesn't matter much: accounting and inventory reconciliation, demand forecasting, training recommendation models, and much of the US banking network.

    

      
ETL / ELT
Embarrassingly parallel transforms (filter, project). Schedulers retry, flag failures and ship connectors. Failed files are easy to inspect and rerun.
data mesh · data contracts · data fabric

      
Analytics
SQL engines over files in object storage, with table formats (Iceberg) and catalogs (Unity): a data lakehouse.
pre-aggregation · ad hoc queries

      
Machine learning
Feature engineering, model training (data in, weights out), batch inference. Spark MLlib, FlinkML.
Kubeflow · Flyte · Ray

      
Serving derived data
Build recommendations, reports and ML features, then move them into the databases that serve users.
see next section

    

    
    
      
  • ETL trend: pipelines used to belong to one data engineering team. Now any team can own its pipelines, and ETL often runs on the same engine as analytics (SparkSQL, Trino, DuckDB).
    • 
      
  • Analytics, two styles: pre-aggregation into OLAP cubes or data marts on a schedule (sometimes pushed to Druid or Pinot), and ad hoc queries where response time matters. BI tools (Tableau, Power BI, Looker, Superset) connect through SQL.
    • 
      
  • Graphs: the bulk synchronous parallel (BSP) or Pregel model repeatedly passes information along edges until nothing changes. Implemented by Giraph, Spark GraphX and Flink Gelly.
    • 
      
  • LLMs: extract text from HTML, remove low-quality and duplicate documents, tokenize and embed. OpenAI uses Ray in ChatGPT training. Notebooks (Jupyter, Hex) drive batch jobs through DataFrames or SQL.
    •

      Getting results out
      
Serving derived data

      Book: “Serving Derived Data”
    

    
The output sits in a DFS or object store, but users read from a production database, key-value store or search engine. How should you get it there?

    

      Why not write record by record from the job? SOS
      
    
        
  1. Slow: a network request per record is orders of magnitude slower than batch throughput
    2. 
        
  2. Overload: many parallel tasks can swamp the database and hurt live queries
    3. 
        
  3. Side effects: you lose the all-or-nothing guarantee. Partial results become visible, and retried tasks write duplicates
    4. 
      

    

    

      

        Option 1
        
Push through a stream (Kafka)

        
    
          
  • Built for sequential bulk writes
    • 
          
  • Acts as a buffer: consumers throttle their own read rate
    • 
          
  • One output, many consumers
    • 
          
  • A security boundary in a DMZ between batch and production networks
    • 
          
  • Ingested by Elasticsearch, Pinot, Druid, Venice, ClickHouse
    • 
          
  • All-or-nothing still needs a “job done” signal; until then consumers keep the data hidden, like read committed (Chapter 8)
    • 
        

      

      

        Option 2
        
Build the database inside the job

        
    
          
  • Write database files directly, then bulk-load them
    • 
          
  • TiDB Lightning, Pinot's Hadoop import, RocksDB SST ingestion
    • 
          
  • Very fast; atomic switch between dataset versions
    • 
          
  • Hard to do incremental updates
    • 
          
  • Hybrids exist: Venice supports both row updates and full swaps
    • 
        

      

    

    
Summary: a batch job reads immutable, bounded input and writes fresh output, so reruns are safe. Distributed batch has three layers: storage (a DFS or object store, with blocks, replication or erasure coding, and metadata), orchestration (executors, resource manager and scheduler for each job, plus workflow schedulers for DAGs of jobs) and computation (MapReduce, then dataflow engines, built on the shuffle). SQL and DataFrames made it easy to use and to optimize. It powers ETL, analytics, ML and derived datasets. Next is Chapter 12, where the input is unbounded and jobs never finish.
