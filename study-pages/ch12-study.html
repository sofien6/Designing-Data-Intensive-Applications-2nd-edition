Stream Processing

Batch jobs wait until the input is complete. But most data never stops arriving. Stream processing handles each event as it happens: how events are carried, how a database can become a stream, and how to compute on streams that never end.

Bounded vs unbounded input

Book: Chapter 12 introduction

Chapter 11's batch jobs assume the input has a known, finite size. Real data keeps coming: users act today and will act tomorrow. A stream processor drops the fixed time slices and handles every event as it happens.

Batch processing

Bounded input

  • Knows when it has read everything, so it can sort before writing output
  • Unbounded data must be chopped into artificial chunks: a day, an hour
  • Output lags input by up to a whole chunk: often too slow
  • Input and output are files
Stream processing

Unbounded input

  • Data is made available incrementally, over time, forever
  • Process each event soon after it occurs: low delay
  • No sorting the whole input, so no sort-merge joins
  • Input and output are event streams; brokers and logs play the filesystem's role
The chapter's path: The Data Pipe
  1. Transmit: how events are represented, stored and sent
  2. Databases: how databases and streams relate (CDC, event sourcing)
  3. Process: what to compute on streams, and how to survive faults
  • An event is a small, self-contained, immutable record of something that happened, usually with a time-of-day timestamp. A page view, a purchase, a sensor reading, a line of a log.
  • One producer (publisher, sender) creates it; many consumers (subscribers, recipients) may process it. Related events are grouped into a topic or stream.
  • You could connect them with a database and polling, but frequent polling is wasteful: the more often you poll, the fewer polls find anything new. Better to be notified. Database triggers exist but are limited.
Transmitting events

Messaging systems

Book: “Messaging Systems”, “Direct messaging from producers to consumers”, “Message brokers”, “Message brokers compared to databases”

A messaging system lets many producers send to a topic and many consumers receive from it (publish/subscribe). To tell systems apart, ask two questions.

Question 1

Producers faster than consumers?

  • Drop messages
  • Buffer them in a queue. What happens when it outgrows memory, or the disk fills?
  • Backpressure (flow control): block the producer. Unix pipes and TCP do this
Question 2

Nodes crash: are messages lost?

  • Durability needs disk writes and/or replication, which cost speed
  • Losing a sensor reading now and then may be fine; losing a counted event is not
  • Many silent drops make metrics wrong without anyone noticing
When the consumer is slow: Drop, Buffer, or Block
  1. Drop: lose messages
  2. Buffer: queue them up (log brokers: a huge, fixed-size buffer on disk)
  3. Block: backpressure the producer
No middleman

Direct messaging

  • UDP multicast for low-latency market feeds; the app re-requests lost packets
  • ZeroMQ, nanomsg: brokerless pub/sub over TCP or multicast
  • StatsD over UDP: counters only approximately right
  • Webhooks: register a callback URL; the other service calls it on each event
  • Assumes both ends are online. An offline consumer misses messages; a crashed producer loses its retry buffer
A server in between

Message broker (message queue)

  • A kind of database optimized for message streams
  • Clients may come, go and crash; durability is the broker's job
  • Usually unbounded queueing for slow consumers
  • Consumers are asynchronous: the producer only waits for the broker to buffer the message

Traditional brokers compared to databases

Standards: JMS and AMQP. Software: RabbitMQ, ActiveMQ, HornetQ, Qpid, TIBCO EMS, IBM MQ, Azure Service Bus, Google Cloud Pub/Sub. Some even take part in two-phase commit (XA/JTA). Using a database as a queue is possible but hard to tune.

Delivery

Multiple consumers, acks and redelivery

Book: “Multiple consumers”, “Acknowledgments and redelivery”
Load balancing

Each message to one consumer

  • Consumers share the work; add more to go faster
  • Good when messages are expensive to process
  • AMQP: several clients on one queue. JMS: shared subscription
Fan-out

Each message to every consumer

  • Independent consumers all “tune in” to the same broadcast
  • Like several batch jobs reading the same input file
  • JMS: topic subscriptions. AMQP: exchange bindings

Combine them with Kafka's consumer groups: load balancing inside a group, fan-out across groups.

  • Acknowledgments: a consumer tells the broker when it has finished a message, and only then is it removed. No ack before the connection closes or times out means the broker redelivers it to someone else.
  • The message might in fact have been processed, with only the ack lost. Handling that needs atomic commit, unless processing is idempotent or duplicates are acceptable.
  • Load balancing + redelivery = reordering. If one consumer crashes mid-message, that message is redelivered to another consumer, which has meanwhile moved on to later messages. Fix: one queue per consumer. Only matters if messages depend on each other causally.
  • Poison messages: a malformed message crashes every consumer that gets it, and redelivery repeats forever. With strict ordering the queue is stuck. A dead letter queue (DLQ) moves it aside; anything in the DLQ is an alert, and an operator drops, fixes and resends it, or fixes the consumer.
My own example: queue holds email-1, email-2, email-3. Worker X takes email-1, worker Y takes email-2. Y crashes. X finishes email-1, takes email-3, then gets email-2 redelivered. X sent them in the order 1, 3, 2.
Durable plus low latency

Log-based message brokers

Book: “Log-Based Message Brokers”, “Using logs for message storage”, “Logs compared to traditional messaging”, “Consumer offsets”, “Disk space usage”, “When consumers cannot keep up with producers”, “Replaying old messages”

Traditional brokers treat messages as transient: receiving one is destructive, so you can't rerun a consumer, and a new consumer only sees new messages. A log-based broker keeps the durability of a database with the notifications of messaging.

  • Producers append to the end of a log; consumers read it sequentially, then wait for more. Like tail -f.
  • To scale, the log is sharded. Kafka calls a shard a partition. A topic is a group of partitions.
  • Each message in a partition gets a monotonically increasing offset. Messages are totally ordered within a partition, not across partitions.
  • Apache Kafka, Amazon Kinesis Streams. (Google Cloud Pub/Sub is built similarly but offers a JMS-style API.) Millions of messages per second by sharding; fault tolerance by replication.
  • Need events for one user in order? Make the user ID the partition key, so they all land in one partition.

Downside of whole-shard assignment

Coarse load balancing

  • The broker assigns whole partitions to consumers in a group, not single messages
  • At most as many consumers as partitions; for more parallelism add partitions
  • One slow message holds up the rest of its partition: head-of-line blocking
Upside of offsets

Cheap bookkeeping

  • Everything below the consumer's offset is done; no per-message acks
  • Batching and pipelining raise throughput
  • On failure, resume from the last recorded offset, so some messages are seen twice
  • The offset is just like a replication log sequence number: broker = leader, consumer = follower
  • Disk space: the log is split into segments; old ones are deleted or archived. In effect a giant circular (ring) buffer on disk. A consumer that falls behind past a deleted segment misses messages.
  • Back of the envelope (my own numbers): a 12 TB disk written flat out at 200 MB/s fills in 12,000,000 ÷ 200 = 60,000 s, about 17 hours. Real deployments write far below full speed, so logs typically hold days or weeks.
  • Tiered storage: Kafka and Redpanda serve old messages from object storage; WarpStream, Confluent Freight and Bufstream keep everything there, often as Iceberg tables that batch jobs and warehouses can query directly.
  • A slow consumer hurts only itself. Monitor how far it lags and alert; there is time to fix it. A stopped consumer costs nothing but its stored offset. (Traditional brokers: delete abandoned queues or they eat memory.) You can safely read a production log for testing.
  • Replay: reading doesn't change the log; only the consumer's offset moves, and the consumer controls it. Start a copy at yesterday's offset, write output elsewhere, repeat with new code. Just like rerunning a batch job.

Databases and streams

Keeping systems in sync

Book: “Databases and Streams”, “Keeping Systems in Sync”

Every write to a database is an event. A replication log is a stream of writes; state machine replication is “same events, same order, same state”. Streams and databases are deeply connected.

  • Real apps combine an OLTP database, a cache, a search index and a warehouse, each with its own copy of the data in its own format. They must stay in sync.
  • Warehouses traditionally use ETL: dump, transform, bulk-load. A batch process, and slow.
  • Dual writes: the application writes to each system itself. Two serious problems:
Problem 1 · concurrency

Race condition

  • Two clients write the same key to the database and the index
  • Their writes arrive in different orders at each system
  • The two systems disagree forever, with no error. Nobody notices without version vectors
Problem 2 · fault tolerance

Partial failure

  • One write succeeds, the other fails
  • All-or-nothing across both is atomic commit: expensive (2PC)
  • Root cause: two leaders, neither following the other

    A database as a stream

    Change data capture

    Book: “Change Data Capture”, “Implementing CDC”, “Initial snapshot”, “Log compaction”, “API support for change streams”, “CDC versus event sourcing”, sidebar “Change Data Capture and Database Schemas”

    CDC observes every change written to a database and makes it available, in order, as a stream. The search index, cache and warehouse become consumers. The database decides the order once; everyone applies it in that order.

    • Replication logs used to be an internal detail, not a public API. CDC turns them into one.
    • CDC makes the source the leader and the derived systems followers. A log-based broker is a good transport because it keeps order.
    • Tools: Debezium (source connectors for MySQL, PostgreSQL, Oracle, SQL Server, Db2, Cassandra…), Kafka Connect, Maxwell (MySQL binlog), GoldenGate (Oracle), pgcapture (PostgreSQL). Built on logical (row-based) replication logs.
    • Usually asynchronous: the source doesn't wait for consumers. A slow consumer doesn't hurt it, but replication lag applies.
    • Initial snapshot: without the full history you need a consistent snapshot tied to a known log offset, then apply changes from there. Debezium uses Netflix's DBLog watermarking for incremental snapshots.
    • Change streams as an API: most databases now offer them natively (MySQL, PostgreSQL via their replication logs; Google Datastream). Quorum databases are harder: no single source of truth, so Cassandra exposes each node's raw log segments and the consumer merges them, like a quorum reader.

    Log compaction

    Keep only the latest value per key; a tombstone (null) deletes the key. Disk use then depends on the current contents, not the number of writes ever made. A new consumer reads a compacted topic from offset 0 and gets a full copy of the database, with no new snapshot. Kafka supports this, which lets a broker serve as durable storage.

    CDC versus event sourcing

    Change data capture

    Low-level, retrofitted

    • App uses the database mutably: update and delete at will
    • Changes extracted low down (replication log), in true write order
    • Added to an existing database with minimal change; the app may not even know
    • Each event holds the whole new record, so compaction works
    Event sourcing

    Application-level, by design

    • App logic is built on immutable events; updates and deletes discouraged
    • Events capture user intent (“seat booked”), not state mechanics
    • A big change to adopt
    • Later events don't override earlier ones, so you need the full history; no compaction. Snapshots only speed things up
    Schemas become APIs: CDC copies the source's table schema, so dropping a column can break other production services downstream, not just warehouse ETL. Use data contracts, or the outbox pattern: write to a separate outbox table with its own stable schema, in the same transaction as the real change, and expose only the outbox to CDC. It is a dual write, but inside one database, so it's atomic. Costs: maintaining the mapping, and extra writes.
    Two sides of one coin

    State, streams and immutability

    Book: “State, Streams, and Immutability”, “Advantages of immutable events”, “Deriving several views from the same event log”, “Concurrency control”, “Limitations of immutability”

    Current state is the result of the events that changed it. State = the integral of the event stream over time; the stream = the derivative of state. The changelog is the system of record; the database is a cache of the log's latest end.

    Advantages

    Why keep immutable events

    • Auditability, like an accountant's ledger: mistakes are fixed by a compensating entry, never erased
    • Recovery from bugs: bad code can't destroy history
    • More information: an item added to a cart then removed is gone from state but still in the log
    • Several views from one log (Druid reads straight from Kafka; Kafka Connect sinks). Build a new view beside the old, switch readers, delete the old: easier than a schema migration
    Write form ≠ read form

    CQRS and denormalization

    • Old fallacy: data must be written in the form it is queried
    • With a translation step, normalize vs denormalize debates mostly vanish: denormalize views freely
    • Home timelines are heavily denormalized, kept in sync by a fan-out process
    • Works with CDC events too, not only event sourcing

    Concurrency control

    • Downside: views are updated asynchronously, so a user may not see their own write. Synchronous view updates need a distributed transaction or waiting, usually impractical.
    • Upside: design one event as a self-contained description of a user action. Then an action is a single append, which is easy to make atomic, instead of a multi-object transaction.
    • If the log and the state are sharded the same way, a single-threaded consumer per shard needs no locking at all: the log defines a serial order (like actual serial execution).
    • Immutability also powers MVCC snapshots and Git, Mercurial and Fossil.

    Limitations

    • Churn: mostly-insert workloads are easy. Many updates and deletes on a small dataset make history huge; compaction and GC performance become critical.
    • Legal deletion (GDPR, leaked secrets): you must rewrite history as if the data was never written. Datomic: excision. Fossil: shunning.
    • True deletion is hard: SSDs, filesystems and storage engines write elsewhere instead of overwriting; backups are deliberately immutable.
    • Crypto-shredding: encrypt, then throw away the key. Moves mutability into the key store, and you must pick key granularity up front (all-or-nothing per key). Puncturable encryption is a more flexible but rare alternative.
    • Deletion is really “harder to retrieve”, not “impossible to retrieve”.
    Processing streams

    What stream processing is for

    Book: “Processing Streams”, “Uses of Stream Processing”, “Complex event processing”, “Stream analytics”, “Maintaining materialized views”, sidebar “Incremental View Maintenance”, “Search on streams”, “Event-driven architectures and RPC”

    Once you have a stream you can (1) write it to a store, (2) push it to humans (alerts, dashboards), or (3) turn input streams into output streams. Code doing (3) is an operator or job: it reads input read-only and appends output elsewhere.

    • Sharding, mapping and filtering work as in batch. The crucial difference: a stream never ends. No sorting, no sort-merge joins, and you can't restart a years-old job from the beginning after a crash.
    • Classic monitoring: fraud detection, trading, factory machines, military alerts.
    Four uses: CAMS
    1. Complex event processing: find patterns of events
    2. Analytics: windowed aggregates and statistics
    3. Materialized views: keep derived data up to date
    4. Search on streams: match single events against stored queries

    Database materialized views

    Periodic refresh

    • e.g. REFRESH MATERIALIZED VIEW, run on a schedule or on demand
    • Poor efficiency: recomputes everything, though most is unchanged
    • Stale: changes show up only at the next refresh
    • Hand-written triggers work only for naturally incremental cases (“revenue per day”)
    Incremental view maintenance (IVM)

    Recompute only what changed

    • Compiles SQL into incremental operators
    • Cheap enough to run very often: fresh views
    • Materialize, RisingWave, ClickHouse, Feldera
    • Recent events in memory + on-disk view, combined at read time; supports warehouse-style queries
    • Actors are not stream processors: actors manage concurrency; streams manage data. Actor messages are ephemeral and one-to-one; logs are durable and multi-subscriber. Actors may talk in cycles; stream jobs form acyclic pipelines. Overlap exists (Storm's distributed RPC), but many actor frameworks don't guarantee delivery after crashes.
    Whose clock?

    Reasoning about time

    Book: “Reasoning About Time”, “Event time versus processing time”, “Handling straggler events”, “Whose clock are you using, anyway?”

    A batch job uses the timestamps inside the events, so reruns give the same answer. Many stream frameworks window by the processing machine's clock. Fine if the lag is tiny; wrong as soon as processing falls behind.

    Event time

    When it happened

    • Timestamp recorded with the event
    • Deterministic: same input, same result
    • Problem: you never know if all events for a window have arrived
    Processing time

    When we got around to it

    • The processor's local clock
    • Simple
    • Delays come from queueing, network faults, contention, restarts, reprocessing after a bug fix
    • Delays also reorder events from different servers
    My own analogy: you mail postcards from a trip on Monday, Tuesday and Wednesday. They arrive Wednesday's, Monday's, Tuesday's. The postmark is the event time; the day each lands in the mailbox is the processing time. Reading in arrival order scrambles the story.

    My own numbers. The real rate is a steady 5 requests per second (50 per window). The processor goes down at 30 s, then catches up at up to 150 events per window.

    Stragglers

    • You can't be sure a window is complete. After a quiet spell you declare it done, then a straggler arrives. Two options: ignore it (count dropped events as a metric and alert if many), or publish a correction, possibly retracting the earlier output.
    • A producer can send a special message: “no more events before time t”. With many producers, consumers must track each one, and producers coming and going makes this harder.

    Device clocks can't be trusted

    An offline phone buffers events for hours or days: extreme stragglers. Its clock may be wrong by accident or on purpose; the server's clock is trustworthy but less meaningful. Record three timestamps:

    Three timestamps: Occurred, Sent, Received
    1. Occurred: by the device clock
    2. Sent to the server: by the device clock
    3. Received by the server: by the server clock
    My own numbers: occurred 09:12:00, sent 09:40:00 (device), received 09:43:30 (server). Offset = received − sent = +3 min 30 s, assuming negligible network delay. Estimated true time = 09:12:00 + 3:30 = 09:15:30, assuming the device clock's offset didn't change in between. Batch processing has the same problem; streams just make it visible.

    Types of windows

    Book: “Types of windows”
    Four windows: Tiny Hamsters Slide Sideways
    1. Tumbling: fixed length, no overlap, each event in exactly one
    2. Hopping: fixed length, overlapping (window size + hop size)
    3. Sliding: all events within an interval of each other
    4. Session: no fixed length; ends after a gap of inactivity, per user

    • Implementation hints: tumbling = round the timestamp down; hopping = tumble at the hop size, then combine adjacent windows; sliding = a time-sorted buffer, expiring old events; session = sessionization for web analytics.
    • State size: a count needs one number however big the window. Sliding windows and joins must buffer events, so big windows or busy streams need lots of memory or disk.
    Joining unbounded data

    Stream joins

    Book: “Stream Joins”, “Stream–stream join (window join)”, “Stream–table join (stream enrichment)”, “Table–table join (materialized view maintenance)”, “Time dependence of joins”

    All three join types keep state built from one input and query it when an event arrives on the other. They differ in what the inputs are and how long the state is kept.

    JoinInputsState keptOutput
    Stream–stream

    Table–table: the view it maintains (my own) 
    SELECT m.member_id, count(*) AS open_tickets

    • Stream–stream: embedding one event's details in the other is not a join. It only shows the cases that matched, never the ones that didn't (needed for rates like click-through).
    • Stream–table: querying a remote database per event is slow and can overload it, so keep a local copy and keep it fresh with CDC. Unlike a batch job's fixed snapshot, the table changes while the job runs.
    • Table–table, as calculus: view = u·v, so its change stream is (u·v)′ = u′v + uv′. A new ticket joins with the current team members; a new team member joins with the current tickets.

    Time dependence

    • Order matters: follow-then-unfollow differs from unfollow-then-follow. Kafka orders within a partition, not across streams or partitions.
    • Which version of the table row does an event join with, the one before or after a concurrent update? If cross-stream order isn't fixed, the join is nondeterministic: rerunning gives different results.
    • Warehouses call this a slowly changing dimension (SCD). Fix: give each version of the row its own ID and put that ID in the event (deterministic, but no log compaction), or denormalize the value into the event.
    My own example: payments in euros are converted using an exchange-rate table. Reprocessing last year's payments must use the rate on the day of each payment, not today's. Store the rate version ID (or the rate itself) on each payment event.

    Exactly-once, really effectively-once

    Fault tolerance

    Book: “Fault Tolerance”, “Microbatching and checkpointing”, “Atomic commit revisited”, “Idempotence”, “Rebuilding state after a failure”

    Batch jobs retry failed tasks and throw away their partial output, so the result looks as if each record was processed exactly once (better named effectively once). A stream never finishes, so you can't wait until the end to make output visible.

    Four techniques: Many Cooks Taste Ingredients
    1. Microbatching: ~1-second mini batches (Spark Streaming)
    2. Checkpointing: periodic state snapshots, triggered by barriers in the stream (Flink)
    3. Transactions: outputs, state and offset commit atomically (Dataflow, VoltDB, Kafka)
    4. Idempotence: doing it twice = doing it once
    Microbatching

    Small batches

    • Batch size ~1 s: smaller = more scheduling overhead, bigger = more delay
    • Implicit tumbling window of the batch size, by processing time
    • Bigger windows must carry state between batches
    Checkpointing

    Rolling snapshots

    • Write operator state to durable storage now and then
    • On crash: restart from the last checkpoint, discard output since then
    • No forced window size

    Both give exactly-once inside the framework. Once output leaves it (database writes, external messages, emails), a retry repeats the side effect.

    • Atomic commit revisited: all effects of an event (downstream messages, DB writes, state changes, the offset move) happen if and only if processing succeeds. Unlike XA across different technologies, these keep the transaction inside the framework and amortize it over several messages.
    • Idempotence: deleting a key is idempotent; incrementing a counter isn't. Make it idempotent by storing the offset of the message that caused the last write next to the value (Storm Trident works this way).
    • Idempotence assumes: replay gives the same messages in the same order (log brokers do), processing is deterministic, and no one else writes the same value concurrently. Use fencing when failing over, in case the “dead” node is alive.

      Summary: streams are batch processing on unbounded input, with brokers and logs as the filesystem. AMQP/JMS brokers hand out single messages, ack and delete them: a task queue. Log brokers hand out partitions, keep messages and track offsets: replayable and ordered. Database writes are a stream too (CDC, event sourcing); log compaction keeps a full copy. Uses: CEP, analytics, materialized views, stream search. Mind event time vs processing time and stragglers. Joins: stream–stream, stream–table, table–table. Fault tolerance: microbatches, checkpoints, transactions or idempotent writes.
