A Philosophy of Streaming Systems

The book's closing argument. No single tool does everything, so you combine several. Keep them in sync with ordered event logs instead of distributed transactions, push changes all the way to the user's screen, and protect integrity end to end.

Data integration

Book: “Data Integration”, “Combining Specialized Tools by Deriving Data”, “Reasoning about dataflows”, “Derived data versus distributed transactions”

Every tool, even a “general-purpose” database, is built for some usage pattern. A real application uses its data in many ways (transactions, search, analytics, caches, ML, notifications), so you end up combining several tools. The hard part is keeping them in sync.

The chapter's path: I Unbundle Carefully
  1. Integration: derive every view from one ordered log
  2. Unbundling: treat the whole organization's dataflow as one big database
  3. Correctness: integrity end to end, without distributed transactions
  • Be explicit about inputs and outputs: where is data written first, and which representation is derived from which?
  • A good pattern: write to a system of record first, capture its changes with CDC, and apply them to the search index in the same order. If CDC is the only way into the index, the index is fully derived from the database.
  • Letting the app write to both the database and the index (dual writes) means nobody decides the order. Two concurrent writes can land in different orders, and the two systems stay inconsistent forever.
  • The principle: funnel all input through one system that decides a total order, then derive everything else by replaying it in that order. This is state machine replication (Chapter 10). Whether it's CDC or event sourcing matters less.
  • Updating derived data from a log can usually be made deterministic and idempotent, so recovering from faults is easy.
Distributed transactions

Atomic commit

  • Changes applied atomically by a commit protocol (2PC)
  • Usually you can read your own writes right away
  • XA has poor fault tolerance and performance; a better standard is unlikely to arrive soon
  • Synchronous: if one participant fails, all abort, so failures spread
Log-based derived data

Deterministic retry + idempotence

  • Correctness comes from replaying an ordered log safely
  • Updated asynchronously, so reads may be stale by default
  • The book's pick: the most promising way to integrate different systems
  • Asynchronous: a fault stays contained in one place

Stale reads are a real cost. Telling people “eventual consistency is inevitable, deal with it” without saying how isn't helpful. The chapter later works toward a middle ground.

Where it gets hard

The limits of total ordering

Book: “The limits of total ordering”, “Ordering events to capture causality”

A totally ordered log is easy in a small system: a single-leader database already builds one. At scale it breaks down. Deciding a total order is total order broadcast, which is equivalent to consensus, and most consensus algorithms assume one node can handle every event.

Where total order breaks: Shy Geese Migrate Offline
  1. Shards: more events than one leader can handle, so the log is split, and order across shards is undefined
  2. Geography: a leader per region; events from two regions have no defined order
  3. Microservices: each service owns its state; events from two services aren't ordered
  4. Offline clients: client state changes before the server hears about it
  • No causal link between two events? Then order them any way you like.
  • Updates to the same object are easy: route them all to the same log shard.
  • The hard case is a causal dependency across systems. It behaves like a time-dependent join (Chapter 12).

    The integration tools

    Batch and stream processing

    Book: “Batch and Stream Processing”, “Maintaining derived state”, “Reprocessing data for application evolution”, “Unifying batch and stream processing”

    Batch and stream processors get data into the right form in the right places: consume, transform, join, filter, aggregate, train models, write outputs. The outputs are derived datasets. The key difference: stream input is unbounded, batch input has a known, finite size.

    Stream processing

    Low delay

    • A change in the input shows up in derived views quickly
    • Like batch, but operators can keep managed, fault-tolerant state
    Batch processing

    Reprocess history

    • Rerun over all accumulated history to derive a brand-new view
    • Functional style: deterministic pure functions, immutable inputs, append-only outputs
    • Deterministic functions with clear inputs and outputs help fault tolerance and make the organization's dataflows easier to reason about.
    • Derived data could be maintained synchronously, like a secondary index inside one transaction. But asynchrony is what makes log-based systems robust: a fault stays local, while distributed transactions abort everywhere when one participant fails.
    • Secondary indexes that cross shards are also most reliable and scalable when maintained asynchronously.

    Reprocessing lets applications evolve

    Without reprocessing

    Small schema changes only

    • Add an optional field, add a new record type
    • Existing data stays in its old shape
    With reprocessing

    Restructure everything

    • Rederive the whole dataset into a completely different model
    • Run old and new views side by side from the same data
    Gradual migration: build the new view next to the old one → send a few users to it and look for bugs and slowness → raise the share step by step → drop the old view. Every step can be undone, because a working system is always there to go back to. Less risk means you can move faster. (The book's analogy: 19th-century railways added a third rail so trains of both gauges could run while the track was converted.)

    Unifying batch and stream

    • Lambda architecture: an early proposal that ran batch and stream side by side. It had problems and has fallen out of use.
    • Kappa architecture: one system handles both reprocessing history and processing new events.
    One engine for both needs: REE (a referee rewinding the tape)
    1. Replay: feed historical events through the same engine (log brokers replay; some processors read object storage)
    2. Exactly-once: output as if no fault happened; discard partial output of failed tasks
    3. Event-time windows: processing time means nothing when replaying history (Apache Beam on Flink or Dataflow)
    Two philosophies

    Unbundling databases

    Book: “Unbundling Databases”, “Composing Data Storage Technologies”, “Creating an index”, “The meta-database of everything”, “Making unbundling work”, “Unbundled versus integrated systems”

    Databases, batch and stream processors, and operating systems all store data and let you process and query it. Unix and relational databases solved this with opposite philosophies. Unbundling tries to get the best of both.

    Unix

    Thin, low-level abstraction

    • Files and pipes: just sequences of bytes
    • “Simple” because it's a thin wrapper over the hardware
    • Small tools composed by a shell
    • NoSQL is a bit like applying this to distributed OLTP
    Relational databases

    High-level, integrated abstraction

    • SQL and transactions hide disk layout, concurrency, crash recovery
    • “Simple” because a short query uses a huge machine (optimizer, indexes, joins, replication)
    • One product that does it all

    CREATE INDEX is reprocessing

    Inside one database 
    CREATE INDEX:
1. scan a consistent snapshot
2. pull out the indexed values, sort
3. write the index
4. apply writes made since the snapshot
5. keep it current on every write
    Across systems (same steps) 
    new derived system:
1. initial snapshot of the source
2. transform it
3. load the new view
4. replay the change log since the snapshot
5. follow CDC from then on

    This is also how you set up a new follower replica (Chapter 6) and bootstrap CDC (Chapter 12).

    • The meta-database of everything: an organization's dataflow looks like one huge database. Batch, stream and ETL jobs act like index and materialized-view maintenance; stream processors act like triggers and stored procedures; derived systems act like different index types.
    • The difference: those parts are separate pieces of software, on different machines, run by different teams.
    Federated database / polystore

    Unify reads

    • One query interface over many storage engines
    • PostgreSQL foreign data wrappers, Trino, Hoptimator, Xorq
    • Relational tradition: elegant language, complicated implementation
    • No good answer for keeping writes in sync
    Unbundled database

    Unify writes

    • CDC and event logs keep every system in sync, even through faults
    • Unix tradition: small tools, one uniform low-level interface (the log), composed at a higher level
    • The harder problem, so the chapter focuses on it

    Making unbundling work

    • Inside one system, transactions are fine. Some stream processors use them internally for exactly-once.
    • Across technologies built by different groups, there's no standard transaction protocol. An ordered log with idempotent consumers is a much simpler abstraction to implement everywhere.
    Loose coupling · system level

    Faults stay contained

    • A slow or failed consumer? The log buffers its messages
    • Producer and other consumers keep running
    • The fixed consumer catches up without missing data
    Loose coupling · human level

    Teams work independently

    • Each team owns one component and does it well
    • The log is a well-defined interface between teams
    • Strong enough to carry ordering and durability, general enough for any data

    When not to unbundle

    • Databases don't go away: they hold stream processors' state and serve their outputs. Specialized engines (like warehouse query engines) stay important.
    • Every extra piece of infrastructure has a learning curve and quirks. Run as few moving parts as you can. One integrated product may also perform better and more predictably on its target workload.
    • Building for scale you don't need is premature optimization.
    • Unbundling is about breadth, not depth. If one product does everything you need, just use it.
    • Tools are improving: Debezium for change streams, Kafka's protocol as a de facto standard, incremental view maintenance engines.
    Spreadsheets, at scale

    Designing applications around dataflow

    Book: “Designing Applications Around Dataflow”, “Application code as a derivation function”, “Separation of application code and state”, “Dataflow: Interplay between state changes and application code”, “Stream processors and services”

    Change a cell in a spreadsheet and every formula that depends on it recalculates (VisiCalc did this in 1979). We want the same from data systems: change a record and every index, cache and aggregate built on it refreshes automatically. They also need to be fault-tolerant, scalable and durable, across many technologies.

    Derived datasetDerivation functionBuilt into databases?
    Secondary indexPick out the indexed fields, sort by themYes: CREATE INDEX
    Full-text indexLanguage detection, word segmentation, stemming or lemmatization, spelling fixes, synonyms → inverted indexBasics only; the rest needs domain tuning
    ML modelFeature extraction and statistics over training dataNo: very application-specific
    UI cacheAggregate data into the shape the screen showsNo: changes when the UI changes
    • Custom derivation code is where databases struggle. Triggers, stored procedures and UDFs were an afterthought.
    • Databases are poor places to deploy code: no good dependency management, version control, rolling upgrades, monitoring or calls to other services. Kubernetes, Docker and YARN do that job well.
    • Today's norm: stateless application servers, state in a database. “We believe in the separation of Church and state” (a joke: Alonzo Church's lambda calculus has no mutable state).
    Database as a variable

    Passive, polled

    • A mutable shared variable you reach over the network
    • You can read it, but you can't subscribe to it
    • To see changes you poll. Subscriptions are only starting to appear
    • (The observer pattern exists, but few languages build it in)
    Dataflow

    Code reacts to state changes

    • A change in one place triggers code that changes state elsewhere
    • Seen already in CDC, actors, triggers, incremental view maintenance
    • Stream operators compose like Unix pipes: streams of changes in, streams of changes out
    What derived data needs from the log: O·F
    1. Order: every view processes events in the same order, so the views agree
    2. Fault tolerance: lose one message and the view is out of sync forever

    Strict, but much cheaper and more robust than distributed transactions. Modern stream processors give both at scale.

    Try it: a service call vs a local stream join

    My own example: checkout needs the current sales-tax rate for the buyer's region. A request/response design asks the tax service at checkout time. A dataflow design subscribes to tax-rate changes ahead of time and keeps a local table.

    • The fastest, most reliable network request is no network request. RPC becomes a stream join between orders and tax-rate updates.
    • Caching the rate in the service also avoids the call, but keeping that cache fresh means polling or subscribing, which is the dataflow approach anyway.
    • The join is time-dependent: reprocess old orders later and you need the rate that applied then, whichever design you chose.
    • Microservices and dataflow both give loose coupling between teams. The difference is the mechanism: one-way asynchronous streams rather than synchronous request/response.
    Eager vs lazy

    The write path and the read path

    Book: “Observing Derived State”, “Materialized views and caching”, “Stateful, offline-capable clients”, “Pushing state changes to clients”, “End-to-end event streams”, “Reads are events too”, “Multishard data processing”

    The write path is the work done ahead of time, as soon as data arrives, whether or not anyone asks (eager evaluation). The read path is the work done only when someone asks (lazy evaluation). The derived dataset is where they meet. Indexes, caches and materialized views just move that meeting point.

    Extend the write path to the user's device

    • Single-page apps and mobile apps keep state on the device and work offline (local-first, Chapter 6). That state is a cache of server state: pixels are a materialized view of the client's model objects, which are a local replica of the datacenter's state.
    • A normal web page is a stale cache until you reload. RSS is just polling.
    • Server-sent events (EventSource) and WebSockets keep a connection open so the server can push changes.
    • Read once to get the initial state, then follow a stream of changes. A device that went offline reconnects like a log consumer resuming from its offset: each device is a tiny subscriber.
    • React and Elm already re-render when state changes. Feed server events into that and changes flow from one user's tap to another user's screen in under a second. Chat and online games already work this way.
    Today's default

    Request/response

    • Stateless clients, one request, one response
    • Baked into databases, libraries, frameworks and protocols
    • Few datastores let one request return a stream of responses
    The proposal

    Publish/subscribe dataflow

    • Subscribe to changes all the way to the UI
    • More responsive interfaces, better offline support
    • Requires rethinking how many systems are built

    Reads are events too

    • Some stream processors let outside clients query their internal state, which makes the processor a simple database.
    • Go further: send read requests as events through the same processor as writes. It answers on an output stream. That's a stream-table join between queries and the data, routed to the right shard like any copartitioned join.
    • A one-off read is a join that forgets the request right away. A subscription is a join that stays open for past and future events.
    • Logging reads records what the user saw before deciding (say, the delivery date and stock level shown before a purchase). That helps track causality and provenance, at a storage and I/O cost. It's still a research problem.
    • Multishard queries can reuse the processor's routing and joins: Storm's distributed RPC counted everyone who had seen a URL (the union of the followers of everyone who posted it); fraud checks join a purchase with several differently sharded reputation databases. A database with built-in multishard joins is usually simpler.
    Aiming for correctness

    The end-to-end argument

    Book: “Aiming for Correctness”, “The End-to-End Argument for Databases”, “Exactly-once execution of an operation”, “Duplicate suppression”, “Uniquely identifying requests”, “The end-to-end argument”, “Applying end-to-end thinking in data systems”

    A stateless service with a bug is easy to fix: restart it. A database remembers mistakes forever. And strong guarantees inside the database, like serializable transactions, don't make the application correct.

    • Transactions (ACID) have been the main tool for four decades, but weak isolation levels show how shaky that foundation is. Jepsen tests found big gaps between claimed and actual guarantees.
    • A bug that writes bad data or deletes good data won't be stopped by isolation. That's one argument for immutable, append-only data: faulty code can't destroy what's already there.
    • Exactly-once (effectively-once) means the final effect is as if no fault happened, even after retries. Processing twice is corruption: a double charge, a counter bumped twice.
    • Idempotence is the main tool. For operations that aren't naturally idempotent, it takes extra metadata (the IDs of operations already applied) and fencing on failover.

    TCPLost and duplicate packets, within one connectionThe connection drops after COMMIT is sent; the client reconnects and retries, a new transaction

    • Databases enforce unique constraints correctly even at weak isolation. An application-level check-then-insert can fail without serializability (write skew).
    • The transfers table is also an event log. The balance updates could be derived from it downstream, deduplicated by the same ID.

      • Skip transactions and you reimplement fault tolerance in app code, which is usually wrong: lost or corrupted data. We haven't found the right abstraction yet.
      Uniqueness and friends

      Enforcing constraints

      Book: “Enforcing Constraints”, “Uniqueness constraints require consensus”, “Uniqueness in log-based messaging”, “Multishard request processing”

      Unique usernames, file names and seats, but also “balance never negative”, “don't sell more than stock” and “no overlapping room bookings”: when requests conflict, something has to pick the winner. That needs consensus.

      • Usual answer: one leader decides. Raft and friends handle safe failover and prevent split brain.
      • Scale it by sharding on the unique value: hash of the username, or of the request ID.
      • Asynchronous multi-leader replication is ruled out: two leaders can each accept the same name.
      • Rejecting a violation immediately needs synchronous coordination.

      Uniqueness with a sharded log

      Append, Process, Watch
      1. Append each claim to the shard picked by hash(username)
      2. Process each shard on one thread, in order; a local DB tracks taken names; emit success or rejection
      3. Watch: the client waits on the output stream for its answer

      This is consensus built from a shared log (Chapter 10). More shards, more throughput: each shard is independent. The general rule: route writes that might conflict to the same shard and process them one at a time. The validation logic can be anything.

      Output stream

        Shard = (sum of the letters' character codes) mod 2, a toy hash. Claims for the same name always land in the same shard, so one thread sees them in one order.

        A payment across three shards, without atomic commit

        A transfer touches the request ID, the payer and the payee, which may sit on three different shards. Atomic commit across all three would tie those shards together and hurt throughput. Logs and stream processors get the same correctness.

        1. 1. The client gives the transfer a request ID and appends it to the payer's shard.
        2. 2. The payer's processor (state fully derived from its log) checks the funds, reserves the amount, and emits: outgoing payment → its own shard, incoming → payee's shard, incoming → fees shard. All carry the request ID.
        3. 3. The outgoing event comes back to the payer's processor, which executes the payment. Duplicates are ignored by request ID.
        4. 4. Payee and fees processors apply their incoming events, also deduplicating by request ID.

          • Atomicity comes from one append: once the request event is in the payer's log, every downstream event will eventually appear, maybe after crashes, maybe twice.
          • Requirements: each account's events processed in log order, at-least-once delivery, deterministic processors. Same-shard or different-shard doesn't matter.
          • After a crash, the processor sees the same request again, makes the same decision, and emits the same events with the same ID. Consumers drop the copies.
          • Exactly-once makes it easier: the processor's local state rolls back together with its input position.
          • To learn the outcome, the user subscribes to the payer's shard and waits for the outgoing (or “declined”) event.
          Two meanings of “consistency”

          Timeliness vs integrity

          Book: “Timeliness and Integrity”, “Correctness of dataflow systems”, “Loosely interpreted constraints”, “Coordination-avoiding data systems”

          “Consistency” mixes up two separate things. My slogan for it: late is annoying; wrong is forever.

          Timeliness

          Users see an up-to-date state

          • A stale read looks inconsistent, but only temporarily: wait and retry
          • CAP's “C” (linearizability) is a strong form; read-after-write is a weaker one
          • Eventual consistency allows violations
          Integrity

          No corruption

          • No lost data, no contradictory or false data; derived views are correct
          • Violations are permanent: waiting won't fix them; you must check and repair
          • ACID's “C” is usually app-specific integrity; atomicity and durability protect it
          • Integrity matters much more. A card purchase that hasn't appeared on your statement yet is normal. A statement whose total doesn't add up, or money charged to you but never paid to the shop, is a disaster.
          • ACID transactions give both, so the difference rarely mattered. Dataflow systems decouple them: no timeliness unless a consumer explicitly waits for the result, but integrity is central (exactly-once, dedup).

          Try it: timeliness or integrity?

          Integrity without distributed transactions: Some Days Rain Indoors
          1. Single message: the write is one event, appended atomically (fits event sourcing)
          2. Deterministic derivation: all other state updates are computed from it
          3. Request ID: made by the client, passed through every stage for dedup
          4. Immutable messages: reprocess derived data to recover from bugs

          Loosely interpreted constraints

          A traditional uniqueness constraint needs consensus, and streaming can't avoid that. But many businesses already allow “hard” constraints to be broken and fix it afterwards:

          ConstraintViolated on purpose (or anyway)The fix
          Stock ≥ ordersOversold, or a forklift crushed some boxesReorder, apologize, offer a discount
          One person per seatAirlines and hotels overbook on purposeRefunds, upgrades, a room next door
          Balance ≥ 0OverdraftFee plus repayment; daily withdrawal limits cap the risk
          Cross-organization dataInconsistencies are inevitableSettlement and correction processes
          • The fix is a compensating transaction. Whether the apology is cheap enough is a business decision. You can't unsend an email, but you can send a correction.
          • If it is, write optimistically and check the constraint afterwards. Do validate before anything that is expensive to undo (like cash leaving an ATM).
          • These apps still need integrity (no lost bookings, no vanishing money). They don't need timeliness in enforcing the constraint.

          Coordination-avoiding data systems

          Dataflow keeps integrity without atomic commit or linearizability. Many constraints can be loose. Put together: you can often skip coordination, keep strong integrity and get better performance and fault tolerance. For example, multi-leader across regions, replicating asynchronously, each region running on its own. Weak timeliness (not linearizable), strong integrity.
          • Serializable transactions are still useful, but at a small scope, where they work well. No XA needed.
          • Add synchronous coordination only where it's needed, e.g. before an operation you can't recover from.
          More coordination

          Fewer inconsistency apologies

          • Constraints enforced up front
          • But slower and less available, so more outage apologies
          Less coordination

          Fewer outage apologies

          • Fast, keeps running through faults
          • But more after-the-fact fixes for violated constraints

          You can't get apologies down to zero. Aim for the sweet spot between too many inconsistencies and too many outages.

          Auditing

          Trust, but verify

          Book: “Trust, but Verify”, “Maintaining integrity in the face of software bugs”, “Don't just blindly trust what they promise”, “Designing for auditability”, “The end-to-end argument again”, “Tools for auditable data systems”

          System models are binary: this can happen, that can't. Reality is probabilities. At scale, “can't happen” happens: corrupted memory, disks and network packets, and above all bugs. So check your data.

          • Even mature databases have had bugs: past MySQL versions failed to keep uniqueness constraints; PostgreSQL's serializable level once allowed write skew.
          • Application code has many more bugs, and many apps don't even use foreign-key or unique constraints properly.
          • ACID consistency assumes every transaction is bug-free. Use a weak isolation level unsafely and integrity is gone.
          • Auditing means checking data integrity. HDFS and S3 don't fully trust disks: background jobs keep reading files back, comparing replicas and moving data.
          • If you want to know your data is there, read it. Test-restore your backups, or you find out they're broken when it's too late.
          • The future may bring more self-validating systems that keep checking themselves.
          Mutating transactions

          Hard to audit

          • Inserts, updates and deletes across tables don't say why
          • The app logic that decided them ran once and is gone
          Event-based

          Built for auditing

          • Each user input is one immutable event; state is derived from it
          • Hash the event log to detect storage corruption
          • Rerun the derivation (or a second one in parallel) and compare
          • Reproduce exactly what happened: time-travel debugging
          • The end-to-end argument again: check whole pipelines. Every disk, network, service and algorithm along the path is then checked implicitly.
          • Like automated tests, continuous integrity checks let you change things faster because you aren't afraid.

          Tools for auditable systems

          • Audit tables: common, but hard to guarantee they match the data. Signing a log with an HSM makes it tamper-proof, but doesn't prove the right transactions went in.
          • Blockchains (Bitcoin, Ethereum): shared append-only logs with cryptographic checks; smart contracts are basically stream processors. Unlike Chapter 10's consensus, they're Byzantine fault-tolerant. Too much overhead for most apps.
          • Merkle trees: trees of hashes that efficiently prove a record is in a dataset.
          • Certificate transparency: verified append-only logs plus Merkle trees to check TLS certificates. A single leader per log, so no consensus needed.

          Try it: tamper with a Merkle tree

          Four log entries (my own). Each leaf is the hash of an entry; each parent is the hash of its two children. An auditor only needs the published root. Edit an entry and watch the changed hashes climb to the root.

          Root vs published root–

          Toy 32-bit hash (FNV-1a) so it fits on screen. Real systems use SHA-256.

          Summary: no single tool serves every need, so compose several. Pick a system of record, derive everything else from its ordered log with batch and stream processing, and reprocess to evolve. Think of it as unbundling a database: CDC and logs are the index-maintenance machinery, spread across teams and technologies. Build apps as dataflow, and push changes all the way to the user's screen. For correctness, use a request ID end to end and deterministic, idempotent processing. That keeps integrity without distributed transactions. Check constraints asynchronously where the business can apologize, and coordinate only where you can't undo. Finally, audit: trust, but verify.
